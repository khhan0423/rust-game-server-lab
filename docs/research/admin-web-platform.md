# One-line summary

**English** | [한국어](admin-web-platform.ko.md)

**As of 2026-11-19, start both tools with axum + Askama on a private network and use htmx only on screens that need it. If complex screens become central, choose a Vue static SPA + Rust API as the alternative.** Security depends more on access paths, per-operation permissions, auditing, and blast radius than on the framework name.

## Recommended Architecture

1. **Make the app and API inaccessible from the public internet.** Admin devices enter the private network only through a VPN or zero-trust access proxy that enforces device policies. Even in deployments that require a public entry point, expose only the authentication proxy and protect the origin with a private address and a firewall. Use mutual TLS (mTLS) and per-service identities between the proxy and the origin and between the web server and the admin API. The app does not allow an operation solely because the request came from the proxy.
2. **Enforce operator SSO and phishing-resistant MFA.** Use an operator IdP policy separate from customer login, and use a separate OIDC client for each app. Log in with Authorization Code + PKCE, and verify the issuer, audience, signature, expiration, `state`, and `nonce` on the server. Require WebAuthn passkeys or security keys, and require reauthentication immediately before grants and refunds. Keep tokens on the server and give the browser only per-app session cookies with `Secure`, `HttpOnly`, and `SameSite`. Suggested initial values are a 15-minute idle timeout and an 8-hour maximum. It must also be possible to invalidate app sessions when permissions are revoked. Limit the scope and lifetime of integration tokens and provide ways to issue and revoke them.
3. **Check authorization for each action in both the web UI and the domain API.** Start with deny by default and separate permissions for viewing, announcements and maintenance, kicks and sanctions, grants, customer support, account changes, refunds, and audit log viewing. The web server passes the authenticated operator's identity and the request identifier to the API in a verifiable manner. The API checks both the service identity and the operator's permissions. Do not rely on hiding buttons in the UI for authorization.
4. **Separate the two tools and their data boundaries.** Game operations requests announcements and maintenance, kicks and sanctions, grants, player lookups, and status lookups through a private game administration API. Do not give the game web app game DB credentials. The owner service handles commands through the existing path for changing game state. The publisher app requests platform account, login method, payment, refund, and support operations through the respective owner service APIs and sees only the information it needs. The two apps use separate deployments, private hostnames, cookies, OIDC clients, service accounts and secrets, permission sets, and network policies. Do not provide customer login information or payment credentials to game operations.
5. **Enforce approvals and duplicate prevention for grants and refunds in the domain API.** For item and currency grants above a defined limit, require approval from someone other than the requester, and use the same approach for high-risk refunds. Bind the target, quantity or amount, reason, and expiration to the approval so that any change requires reapproval. For grants, record a per-request idempotency key in the owner service's PostgreSQL database. Return the existing result if the key and contents match, and reject the request if the contents differ. Record the grant, audit event, and idempotency result in the same transaction so they cannot succeed independently. For external payment calls, use the payment provider's duplicate prevention together with a durable internal processing record. Do not store grant and refund ledgers or idempotency keys in Valkey.
6. **Require auditing of operator actions.** For views, downloads, changes, approvals, and denials, record who did what to which target and when (UTC), along with the reason, result, and request ID. For changes, record the actual before and after values in the owner service. For actions that cause no change, such as views and denials, record the before and after values as not applicable. Do not log raw passwords, tokens, or payment information, and mask personal information as needed. Protect audit records with separate permissions so operators cannot modify or delete them. Do not carry out risky changes if the audit event cannot be recorded durably.
7. **Narrow the browser boundary.** Do not handle state changes with `GET`, and verify the CSRF token and request origin on the server. Keep default HTML escaping and render customer support message bodies and player input as text. Use a CSP that allows only same-origin scripts by default, and apply `frame-ancestors 'none'`, `object-src 'none'`, and `form-action 'self'`. Use `Cache-Control: no-store` for sensitive responses and also disable htmx local history storage. Serve a reviewed htmx file without an external CDN and do not use dynamic script evaluation.
8. **Maintain lockfiles and update procedures.** Commit `Cargo.lock` and build with the locked versions. Check RustSec advisories with `cargo-audit` and use `cargo-deny` to check rules such as allowed sources and banned dependencies. Record the pinned htmx version and hash. If you choose an SPA, also review the npm lockfile and allow only necessary install scripts. Do not assume a new package is safe just because an advisory scan comes back clean. Do not give dependency installation or build processes access to production secrets, and assign someone to handle package changes and emergency patches.

## Recommendation and Alternatives

**Primary recommendation: axum + Askama for both tools.** Start with basic HTML forms and server-side processing, and use htmx to update only where needed, such as refreshing search results, paginating, and displaying status. The two tools can share common form and table code, but they do not share deployments or permissions. The team can use its familiar Rust deployment workflow while avoiding an npm build and an additional web runtime. For refunds and grants, time should go into approvals, auditing, and domain rules rather than the frontend framework.

**Alternative: Vue static SPA + same-origin Rust REST API.** Apply it to the tool in question if usability testing identifies complex multistep workflows or interactions within a single screen as a bottleneck. One example is when customer support staff need to move back and forth between several steps while cross-checking account and payment histories. Vue components can be used without running a Node server in production, while enforcement of approvals, sessions, and auditing remains in Rust. In return, the team must manage the npm supply chain and frontend testing.

## Remaining Decisions

- Decide on the operator IdP and private access method, requirements for administrative devices, the recovery procedure for lost passkeys, and target times for session expiration and revocation.
- Define the role matrix by task and environment, per-transaction and cumulative limits for grants and refunds, the second approver, the audit log retention period, and criteria for masking sensitive information.
- Before launch, verify in both apps that direct access to the private origin is blocked, access with the other app's permissions is denied, sessions can be revoked, CSRF is rejected, changes to request contents after approval are rejected, a retried grant is applied only once, and changes are rejected if an audit record is missing. Verification results for the actual deployment setup have not been confirmed.
- After verifying in usability testing that the basic search, lookup, and approval workflows are sufficient, decide whether an SPA is needed. The scope of the payment provider's support for idempotency keys and repeat lookups has not been confirmed.
