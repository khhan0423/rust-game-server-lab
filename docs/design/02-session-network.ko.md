## 1. 전체 구조

```
                          ┌───────────────┐   서버 간 링크   ┌─────────────────────────────┐
 클라이언트 ──TCP──┐      │  Gateway #1   │═════════════════>│ Game 서버 (샤드 1) ── DB 1  │
 클라이언트 ──TCP──┼──>   │  Gateway #2   │═════════════════>│ Game 서버 (샤드 2) ── DB 2  │
 클라이언트 ──TCP──┘      │  ...          │═════════════════>│ 전투 서버 풀 (던전, PvP)    │
                          └───────────────┘                  │ 클러스터 서비스             │
     ① 플레이어 엔드포인트          ② 서버 간 엔드포인트     └─────────────────────────────┘
```

| 서버 | 역할 | 엔드포인트 | 게임 상태 |
|---|---|---|---|
| **Gateway** | 접속, 인증 확인, 프레이밍, 패킷 크기와 빈도 제한, 하트비트, 재접속, 세션 관리, 라우팅 | ① + ② | 없음 |
| **Game 서버** (샤드) | 플레이어의 **본 샤드.** 컨텐츠(인벤토리, 재화, 우편 등), 로비, 길드 던전, MMO 필드, 길드 액터 | ② | 있음 + Game DB, Log DB, Common DB (04 문서) |
| **전투 서버 풀** | 인스턴스 던전, PvP 필드. 샤드와 무관하게 모든 플레이어를 받음 | ② | 있음 (일회성). DB 없음 |
| **거래 서비스** | 샤드 간 아이템 교환의 중계자(에스크로). 자체 DB (03 문서 6.3) | ② | 있음 + 거래 DB |
| **Redis 호환 저장소** | 계정 접속 상태(중복 로그인 판정), 세션 미러, InGameSpace Directory, 서버 등록과 발견, 파티, 채팅, 대기열, 플레이어 디렉터리 캐시, 랭킹 (03 문서 8장, 9장) | 자체 프로토콜 | 일시 상태, 캐시, 조정 |

어떤 InGameSpace가 어느 서버에 놓이고, 플레이어 데이터가 어디에 사는지는 `03-data-ownership.md`가 다룬다.

C++ 서버 구성으로 치면 프론트 서버(게이트, 프록시)와 존 서버를 나눈 구조다.

### 1.1 이 구조를 고른 이유

- **다른 서버의 InGameSpace로 이동할 때 연결을 끊지 않는다.** 던전(전투 서버 풀), 친구의 로비(다른 샤드), PvP로 갈 때 Gateway의 존 목적지만 바꾼다(6장). 클라이언트는 재접속하지 않는다.
- **느린 클라이언트 문제가 Gateway에서 끝난다.** 클라이언트별 송신 큐와 그 상한은 Gateway가 관리한다. 백엔드는 클라이언트 하나하나의 느림을 신경 쓰지 않는다.
- **백엔드의 네트워크 구조가 단순해진다.** 백엔드는 클라이언트 1만 개의 소켓이 아니라 Gateway 몇 개의 링크만 다룬다.
- **공격 표면이 줄어든다.** 외부에 노출되는 것은 Gateway뿐이다. 패킷 크기와 빈도 제한, 인증 확인을 Gateway에서 먼저 걸러낸다.

대가: 홉이 하나 늘어나 지연이 조금 늘어난다(같은 데이터센터 안이라면 보통 1ms 미만). 서버 종류도 하나 늘어난다.

### 1.2 두 종류의 엔드포인트

| 항목 | ① 플레이어 엔드포인트 | ② 서버 간 엔드포인트 |
|---|---|---|
| 노출 | **공인망** | **사설망(내부망)만.** 외부에서 닿지 않음 |
| 상대 | 믿을 수 없는 클라이언트 수만 개 | 믿을 수 있는 서버 수십 개 |
| 인증 | `login_token` / `session_key` (세션 계약 문서) | 서버 인증. mTLS 권장, 대안은 클러스터 공유 비밀키 + `ServerId` (4.4) |
| 암호화 | TLS (운영 필수) | 사설망이면 선택. mTLS를 쓰면 인증과 함께 해결 |
| 헤더 | 16바이트 (8.1) | 봉투 (4.2), 서버 간 메시지 (4.4) |
| 최대 프레임 | 64KB. 클라이언트 쪽 분할 금지 | 16MB (스냅샷, 플레이어 데이터 전달) |
| 빈도 제한 | 있음 | 없음. 큐 상한과 지표로 감시 |
| 연결 수 | 수천 ~ 수만 | 수십 |
| 유실 대비 | 세션 단위 seq/ack, 재전송 버퍼 (7장) | 메시지 단위 멱등 키 + outbox (03 문서) |
| 끊겼을 때 | 세션 Detached, 유예 | 링크 재연결(백오프). 그 링크를 쓰던 세션은 Resync 표시 |

프로세스 역할별 엔드포인트:

| 프로세스 | ① 플레이어 | ② 서버 간 |
|---|---|---|
| Gateway | **있음** (listen) | 있음 (백엔드로 connect) |
| Game 서버, 전투 서버 | 없음 | 있음 (listen + 다른 서버로 connect) |
| 클러스터 서비스 | 없음 | 있음 |
| 개발용 올인원 (한 프로세스에 전부) | 있음 | 프로세스 내부 채널로 대체 |

- 같은 바이너리를 역할(role) 설정으로 띄운다. 개발할 때는 올인원으로 PC 한 대에서 전부 돌린다.
- **Gateway에서는 두 엔드포인트를 격리한다.** 플레이어 엔드포인트로 접속 폭주가 들어와도 서버 간 링크가 느려지지 않게 하기 위해서다. 우선 동시 접속 수 상한과 IP별 접속 빈도 제한으로 시작하고, 부하 테스트 결과에 따라 두 엔드포인트를 별도 tokio 런타임으로 분리한다.

## 2. 세 가지 "세션"의 구분

C++에서는 보통 `Session` 하나가 소켓과 플레이어를 모두 대표한다. 이 설계에서는 수명이 다른 세 가지를 분리한다.

| 개념 | 어디에 있나 | 수명 | 식별자 |
|---|---|---|---|
| **Connection** | Gateway | TCP 소켓 하나의 수명. 끊기면 끝 | 내부용 |
| **ClientSession** | Gateway | 로그인부터 로그아웃(또는 재접속 유예 만료)까지. **재접속해도 유지** | `SessionId(u64)` |
| **Player** | Game 서버 또는 전투 서버의 InGameSpace 안 | 게임 입장(`EnterGame`)부터 로그아웃까지. 계정당 캐릭터 1개(07 문서). 연결이 끊겨도 유예 시간 동안 유지 | `PlayerId` (UUID v7) |

```
Connection (TCP)  ──────X  끊김         ┌──── 새 Connection (재접속)
ClientSession     ──────────────────────┴──────────────────────>  유지
Player            ──────────────────────────────────────────────>  InGameSpace에 계속 존재
                        │<── 유예 시간 ──>│
```

- Game 서버는 Connection을 전혀 모른다. Game 서버가 아는 것은 "Player P는 Gateway G의 Session S를 통해 연결되어 있다"는 사실뿐이다.
- 재접속은 새 Connection을 기존 ClientSession에 다시 붙이는 일이다. Player 쪽에서 보면 "잠깐 연결이 없었다"는 상태 변화만 있다.

### 2.1 식별자

| 식별자 | 의미 | 바뀌는 시점 | 형식 |
|---|---|---|---|
| **ConnId** | 소켓 하나 | 연결할 때마다 새로 받음. **재사용하지 않음** | Gateway 안에서 단조 증가 |
| **SessionId** | 주고받은 이력(seq, 재전송 버퍼)의 주인 | 재접속하면 **유지**, 새로 로그인하면 **새로 받음** | `[gateway_id: 16 | 순번: 48]`. 재사용하지 않음 |
| **session_key** | 재접속할 때 "같은 세션"임을 증명하는 키 | SessionId와 같음 (세션 동안 불변) | 세션 계약 문서 1장 |
| **PlayerId** | 캐릭터 | 같은 캐릭터라면 항상 같음 | 클러스터 전역 (03 문서 7장) |

- SessionId의 Gateway ID는 **세션을 발급한** Gateway다. 재접속으로 세션이 다른 Gateway로 옮겨 갈 수 있으므로(7.8), **지금 세션이 있는 Gateway**는 Redis의 `sess:{session}:owner`와 `online:{account}`로 찾는다(03 문서 9.3).
- ID를 재사용하지 않으므로, C++ 세션 풀에서 흔한 "끊긴 세션의 ID가 새 세션에 재사용됐는데 늦게 도착한 패킷이 새 세션으로 들어가는" 문제(ABA)가 생기지 않는다.

| 사건 | 새 연결이 내민 것 | ConnId | SessionId | seq | Player |
|---|---|---|---|---|---|
| 재접속 성공 (유예 안) | `session_key` | 새것 | **같음** | **이어짐** | 그대로 |
| 재접속 실패 (유예 만료 등) | `session_key` | 새것 | `ResumeFail` | - | 클라가 로그인으로 전환 |
| 중복 로그인 (앱 재실행, 다른 기기) | `login_token` | 새것 | **새것** | **1부터** | 같은 Player를 **인계** |
| 유예 만료 후 로그인 | `login_token` | 새것 | 새것 | 1부터 | DB에서 새로 로드 |

### 2.2 결합 모델

세션 관리의 핵심은 **결합(바인딩)**이고, 두 단계로 일어난다.

```
Connection ──(1단 결합)──> ClientSession ──(2단 결합)──> Player
```

| 결합 | 같은 시점에는 | 시간이 지나면 | 결합이 바뀌는 상황 | 판정하는 곳 |
|---|---|---|---|---|
| Connection → ClientSession | 1:1 | N:1 | 재접속 (`Resume`) | 같은 Gateway면 그 세션의 **ClientSession 액터**, 다른 Gateway면 새 Gateway가 Redis `SET sess:{session}:owner ... GET`으로 넘겨받고 옛 Gateway에 알림(03 문서 9.5) |
| ClientSession → Player | 1:1 | N:1 | 중복 로그인 (`Auth`) | **새 Gateway** (Redis `SET online:{account} ... GET`으로 옛 접속을 받아 판단. 03 문서 9.4) |

새 연결이 "나는 이 클라이언트다"라고 할 때 처리는 **새 연결이 내민 증명**과 **기존 세션 상태**로 정한다.

| 새 연결의 증명 \ 기존 세션 | 없음 | Detached | Active | Closing |
|---|---|---|---|---|
| **session_key** | `ResumeFail` | **재접속.** 결합하고 Replay | **재접속(half-open).** 옛 연결을 Superseded로 끊고 결합 | `ResumeFail` |
| **login_token** (새 연결) | **처음 접속** | **중복 로그인(조용한 인수).** 옛 세션 정리, Player 인계, Resync | **중복 로그인(경합).** 옛 연결에 `Close(DuplicateLogin)`, 정리 완료 후 Player 인계, Resync | 정리 완료 후 처리 |
| **login_token** (이미 결합된 연결) | - | - | **프로토콜 위반.** `Close` 없이 끊음 | - |

같은 계정의 판정이 한 줄로 처리되도록 1단 결합은 세션 액터가 결정한다. 2단 결합은 계정 키에 대한 `SET ... GET`(명령 하나로 새 값을 쓰면서 옛 값을 받음)이 순서를 정하고, 받은 옛 값을 보고 새 Gateway가 처리한다.

### 2.3 커넥션 상태와 끊김 이유

커넥션은 "이 소켓이 지금 살아서 데이터를 나를 수 있는가"를 다루고, 세션은 "어디까지 주고받았고 지금 누구인가"를 다룬다.

| 항목 | Connection | ClientSession |
|---|---|---|
| TCP 소켓, 송신 큐(256개 상한) | **소유.** 끊기면 송신 큐는 버림 | - |
| 프레이밍, 크기 검사, 빈도 제한, 하트비트, 인증 전 제한 시간 | **소유** | - |
| seq, ACK, 재전송 버퍼 | - | **소유.** 커넥션이 바뀌어도 유지 |
| 계정, 목적지(`Routes`), 상태, 유예 타이머 | - | **소유** |

송신 큐는 커넥션 것이고 재전송 버퍼는 세션 것이다. 커넥션이 죽어 송신 큐가 버려져도 Reliable 메시지는 세션의 재전송 버퍼에 있으므로 잃지 않는다.

```rust
enum ConnState {
    /// TCP 수락 직후. Auth 또는 Resume만 받는다
    Handshaking { deadline: Instant },
    /// 세션에 결합됨
    Bound { session: SessionId },
    /// 닫는 중. 마지막 프레임(종료 사유)을 내보내는 중
    Closing { reason: ConnCloseReason, flush_deadline: Instant },
}
// Closed는 상태가 아니다. 커넥션 task가 끝나는 것이 곧 Closed이고, 소켓과 송신 큐는 Drop으로 정리된다.

enum ConnCloseReason {
    PeerClosed,                    // EOF (읽기 Ok(0))
    PeerReset,                     // ConnectionReset, ConnectionAborted
    WriteFailed,                   // BrokenPipe 등
    KeepaliveTimeout,              // TimedOut
    HeartbeatTimeout,              // 침묵 (half-open)
    HandshakeTimeout,
    SendQueueOverflow,
    ProtocolViolation(ViolationKind),
    ClosedByServer(CloseReason),   // Logout 처리, Kick, 점검
    Superseded,                    // 재접속으로 새 커넥션에 밀려남
    LocalNetwork(std::io::ErrorKind), // NetworkDown 등 서버 쪽 문제
}
```

| 끊김 이유 | 세션 처리 |
|---|---|
| PeerClosed (직전에 `Logout` 있음) | Closing (정상 로그아웃) |
| PeerClosed (`Logout` 없음), PeerReset, WriteFailed, Keepalive/HeartbeatTimeout, SendQueueOverflow | **Detached** (유예) |
| ProtocolViolation | Closing (유예 없음, 사유 통지 없음) |
| ClosedByServer | 세션이 이미 결정한 대로 |
| **Superseded** | **아무것도 하지 않음** (이미 새 커넥션이 붙어 있음) |
| LocalNetwork | Detached + **운영 경보** (동시에 많이 생기면 서버 쪽 장애) |

- 서버는 소켓 에러만으로 "앱이 죽었는지, 잠깐 끊겼는지"를 확실히 구분할 수 없다. 그래서 클라이언트 쪽 원인은 모두 **Detached + 유예**로 처리하고, 같은 세션으로 돌아왔는지는 다음 연결이 증명하게 한다.
- 끊김 이유는 판정이 아니라 **기록**에 쓴다. 세션별 마지막 끊김 이유와 이유별 통계로 모바일 품질 문제(특정 기기, 통신사)를 찾는다.
- 서버가 사유를 보내야 하는 종료(`ClosedByServer`)는 송신 큐를 비울 시간(최대 3초)을 준다. 나머지는 즉시 끊는다.

### 2.4 ConnId 규칙: 늦게 도착한 옛 연결의 이벤트를 무시한다

재접속(half-open)으로 새 커넥션 B가 세션에 붙은 직후, 옛 커넥션 A가 뒤늦게 "끊겼다"를 통지할 수 있다. 세션이 이것을 믿으면 멀쩡한 B가 붙어 있는데도 Detached로 간다. C++ IOCP에서 재사용한 소켓 객체에 이전 소켓의 완료 통지가 늦게 도착하는 문제와 같다.

```rust
struct ClientSession {
    current_conn: Option<ConnId>,
    // ...
}

// 커넥션 → 세션 메시지에는 항상 ConnId가 붙는다
enum FromConnection {
    Frame { conn: ConnId, frame: Frame },
    Lost { conn: ConnId, reason: ConnCloseReason },
    Logout { conn: ConnId },
}

fn on_lost(&mut self, conn: ConnId, reason: ConnCloseReason) {
    if self.current_conn != Some(conn) {
        return; // 이미 교체된 옛 커넥션의 통지 → 무시
    }
    self.current_conn = None;
    self.enter_detached(reason);
}
```

- 프레임도 같다. 교체된 옛 커넥션에서 늦게 올라온 프레임은 버린다.
- **방향 규칙**: 커넥션은 사실만 알린다("끊겼다", "이런 프레임이 왔다"). 판단은 세션이 한다. 커넥션은 세션 상태를 모르고, 세션은 소켓을 직접 만지지 않는다.
- 클라이언트도 같은 규칙을 지킨다(세션 계약 C14).

## 3. Gateway 내부 구조

Gateway는 게임 상태가 없으므로 **존 스레드가 없다.** 전부 tokio 멀티스레드 런타임 위의 task다.

```
[Gateway 프로세스: tokio multi-thread]

  Acceptor task (플레이어 엔드포인트)
     │ accept
     ▼
  Connection × N  (TCP마다)                           ← 소켓. 끊기면 사라짐
     ├─ reader task:  ConnState 소유. 소켓 → 프레임 디코딩 → 크기/빈도 검사 → 세션 액터로
     └─ writer task:  송신 큐(bounded) → 소켓. 큐가 닫히면 남은 것을 내보내고 shutdown
          ▲ 붙었다 떨어졌다 함 (ConnId로 구분)
          │
  ClientSession 액터 × N  (세션마다 task 1개)          ← 세션의 본체. 재접속해도 유지
     - 상태, seq, ACK, 재전송 버퍼, Routes, 유예 타이머, 현재 ConnId
     - 입력: 커넥션의 프레임과 끊김 통지, 백엔드에서 온 프레임, Kick 등 제어, 타이머
         │ 생성/등록/해제
         ▼
  SessionRegistry (액터 1개)                           ← C++ SessionManager 자리
     - SessionId 발급, session_key → 세션 액터 핸들 (재접속 시 세션 찾기)
     - 이 Gateway에 없는 세션이면 Redis 세션 미러에서 이어받아 세션 액터를 새로 만듦 (03 문서 9.5)

  BackendLink × (백엔드 서버 수 × 링크 수)  (서버 간 엔드포인트)
     ├─ reader task:  봉투 해석 → 자기 맵에서 세션 액터 핸들을 찾아 전달
     └─ writer task:  송신 큐(bounded) → 백엔드 소켓
```

| 구성 요소 | 소유하는 것 | 수명 | C++ 대응 |
|---|---|---|---|
| Connection | 소켓, 읽기/쓰기 버퍼, 송신 큐 | 소켓이 끊기면 끝 | Socket 객체 |
| ClientSession 액터 | 세션 상태 전부 | 로그인부터 종료까지. 재접속해도 유지 | Session 객체 (소켓과 분리된 것) |
| SessionRegistry 액터 | ID 발급, 키로 세션 찾기 | 프로세스 수명 | SessionManager |
| 계정 디렉터리 (Redis 호환 저장소) | 계정 → (Gateway, SessionId) | 클러스터 수명 | 계정 서버의 접속자 목록 |

- **세션 상태는 ClientSession 액터만 만진다.** 모든 입력이 이 액터의 Job 큐로 한 줄로 들어오므로 락이 없다.
- **재접속은 새 Connection을 기존 세션 액터에 붙이는 것이다.** Registry가 `session_key`로 세션 액터를 찾아 `AttachConnection(새 ConnId, 송신 핸들)`을 보낸다. 옛 Connection이 살아 있으면 세션 액터가 `Superseded`로 닫는다.
- **매 패킷마다 Registry를 거치지 않는다.** 세션이 생기면 Registry가 그 세션을 담당하는 BackendLink(3.3)에 세션 핸들을 등록해 주고, 이후 패킷은 BackendLink가 자기 맵에서 바로 찾는다.
- **종료는 세션 액터가 스스로 한다.** `Closing` 처리가 끝나면 Registry와 BackendLink에 등록 해제를 보내고 task가 끝난다. 소유하던 버퍼와 핸들은 `Drop`으로 정리된다.
- 세션 하나에 task가 3개(세션 액터 1 + 커넥션 reader/writer 2)다. 동접 1만이면 task 3만 개로, tokio에서는 문제가 되지 않는 규모다. 세션 풀(미리 할당)은 만들지 않고, 측정해서 필요하면 추가한다.

### 3.1 ClientSession의 상태와 전이

#### 상태

```rust
enum SessionState {
    /// TCP 접속 직후. 인증(Auth) 또는 재개(Resume) 패킷만 받는다
    Unauthenticated,
    /// 인증 완료. 게임 입장(EnterGame) 전 단계
    Authenticated { account: AccountId },
    /// 백엔드(본 샤드와 현재 InGameSpace 호스트)에 연결되어 게임 중
    Active { account: AccountId, routes: Routes },
    /// 연결이 끊기고 재접속을 기다리는 중 (유예 시간)
    Detached { account: AccountId, routes: Routes, deadline: Instant },
    /// 종료 처리 중. 백엔드의 저장과 정리 완료를 기다린다
    Closing { reason: CloseReason },
}
```

상태마다 받을 수 있는 패킷이 다르다. 예를 들어 `Unauthenticated` 상태에서 게임 패킷이 오면 즉시 연결을 끊는다. 상태를 enum으로 두었기 때문에 "인증 안 된 세션에서 백엔드로 패킷이 넘어가는" 경로가 코드에 존재할 수 없다.

#### 전이도

```
                 Auth(login_token)                EnterGame      
 [TCP 접속] ──> Unauthenticated ─────────────> Authenticated ─────────────> Active
                     │                                                    │   ▲
                     │ Resume(session_key)                    비정상 끊김 │   │ Resume 성공
                     └──────────────────────────────────────────────┐      ▼   │
                                                                    └──> Detached
                                                                           │
     Logout / Kick / 유예 만료 / 중복 접속으로 교체                          │
 Active, Detached ─────────────────────────────────> Closing ──> (소멸) <───┘
```

#### 네 가지 상황

**1) 처음 접속**

1. 클라이언트가 TCP로 접속한다 → `Unauthenticated`.
2. `Auth { login_token }`을 보낸다. Gateway가 토큰을 검증하고, `SET online:{account} ... GET`(03 문서 9.4)으로 자기 세션을 기록하면서 기존 세션이 있었는지 받아 온다.
3. 기존 세션이 없으면 새 ClientSession을 만든다. seq는 1부터 시작한다 → `Authenticated`. 응답으로 `AuthOk { session_key }`을 보낸다.
4. 캐릭터를 선택하면 백엔드에 배정된다 → `Active`.

**2) 재접속 (같은 세션 이어가기)**

1. 클라이언트가 새 TCP로 접속해서 `Resume { session_key, last_server_seq }`를 보낸다.
2. 세션이 `Detached`이면 새 연결을 붙이고 `Active`로 돌아간다(7.5).
3. 세션이 아직 `Active`이면, 클라이언트는 끊김을 알았지만 서버는 아직 모르는 상태다(half-open). 이때는 **옛 연결을 닫고 새 연결로 교체**한 뒤 같은 절차를 밟는다.
4. 세션이 이 Gateway에 없으면 Redis의 세션 미러(`sess`, `rbuf`)에서 이어받는다(7.8, 03 문서 9.5). Redis에도 없으면(유예 만료, 이미 종료) `ResumeFail`을 보내고, 클라이언트는 처음 접속 절차로 간다.

**3) 중복 접속 (같은 계정의 새 로그인)**

같은 계정으로 `Auth`가 들어왔는데 기존 세션(`Active` 또는 `Detached`)이 있는 경우다. 다른 기기에서 로그인했거나, 모바일 앱이 강제 종료된 뒤 다시 실행되어 재개 정보가 없는 경우가 여기에 해당한다.

**정책: 나중 접속 우선.** 순서가 중요하다.

1. 계정 디렉터리의 원자적 판정이 기존 세션 정보를 돌려주면, 새 Gateway가 기존 세션의 Gateway에 `Kick { session, reason: DuplicateLogin }`을 보낸다(서버 간 링크).
2. 기존 Gateway는 옛 클라이언트에 종료 사유를 알리고 연결을 닫는다. **옛 세션에서 백엔드로 넘어가던 요청을 모두 흘려보낸 뒤** 세션을 `Closing`으로 바꾸고 "정리 완료"를 회신한다.
3. 그다음에 새 세션을 만든다. 정리 완료 전에 새 세션이 같은 Player에 붙으면, 옛 세션의 구매 요청과 새 세션의 요청이 엇갈릴 수 있기 때문이다.
4. 백엔드의 Player는 **로그아웃하지 않고 새 세션으로 넘겨받는다**(인계, `LinkEvent::Replaced`, 4.3). Player 객체와 위치, 전투 상태는 그대로이고 `PlayerLink`의 주소만 바뀐다. 저장과 재로드가 없으니 빠르다. 인계할 수 없는 경우(기획상 인계를 금지한 InGameSpace 등)에만 옛 Player를 저장하고 로그아웃한 뒤, **저장 커밋을 확인하고** 새로 로드한다(완전 재로그인).
5. 새 세션은 seq가 1부터 시작하므로 옛 세션의 재전송 버퍼는 쓸 수 없다. 새 클라이언트에는 **전체 스냅샷**(Resync)을 보낸다.

같은 계정의 세션이 동시에 둘이 되지 않도록, 계정 → 세션 대응은 계정 디렉터리 한 곳에서만 결정한다. 구현은 Redis 호환 저장소의 계정 키에 대한 `SET ... GET` 명령이다(03 문서 9.4).

**4) 접속 해제**

| 종류 | 계기 | 전이 | 유예 |
|---|---|---|---|
| 정상 종료 | 클라이언트의 `Logout` | `Active` → `Closing` → 소멸. 백엔드가 저장하고 Player를 제거 | 없음 |
| 비정상 끊김 | 소켓 에러, 하트비트 타임아웃, 송신 큐 초과 | `Active` → `Detached` | **있음** (7.4) |
| 유예 만료 | 유예 시간 안에 재개 없음 | `Detached` → `Closing` → 소멸 | - |
| 서버 강제 종료 | 중복 접속, 제재, 점검, 프로토콜 위반 | 종료 사유 통지 후 `Closing` → 소멸 | 없음 |

- 종료 사유는 `CloseReason` enum으로 정의하고, 클라이언트에 코드로 알린다. 클라이언트는 사유에 따라 다르게 안내한다(예: "다른 기기에서 접속했습니다", "점검 중입니다").
- 프로토콜 위반(크기 초과, 인증 전 게임 패킷, 클라이언트의 `FRAGMENT` 프레임 등)은 사유를 알리지 않고 바로 끊는다. 공격자에게 정보를 주지 않기 위해서다.

### 3.2 라우팅: 메시지 카테고리와 목적지 두 개

클라이언트 메시지는 세 카테고리로 나뉜다.

| 카테고리 | 예 | 처리하는 곳 |
|---|---|---|
| **System** | `Auth`, `Resume`, `Ping`, `Ack`, `Suspend`, `Logout` | **Gateway 자신** |
| **Content** | 구매, 인벤토리 정리, 우편, 퀘스트 보상 수령, 길드 요청 | 플레이어의 **본 샤드** (세션 동안 고정). 길드 요청은 본 샤드가 길드 액터로 전달 (04 문서 5.1) |
| **Zone** | 이동, 스킬, 루팅, 장착 요청, NPC 상호작용 | 플레이어가 지금 있는 **InGameSpace의 호스트** (이동함) |

- 카테고리는 스키마(`.proto` 메시지 옵션)에서 선언하고, 코드 생성기가 **카테고리별 ID 대역 안에서** 메시지 ID를 매긴다.

| 메시지 ID 대역 | 카테고리 |
|---|---|
| `0x0000` ~ `0x0FFF` | System |
| `0x1000` ~ `0x7FFF` | Content |
| `0x8000` ~ `0xFFFF` | Zone |

- Gateway는 메시지 ID의 **범위만 비교해서** 목적지를 정한다. 페이로드를 해석하지 않으므로 **Gateway는 게임 패킷의 형식을 몰라도 된다.** 게임 패킷이 추가되어도 Gateway를 고칠 필요가 없다.
- 목적지는 ClientSession의 `Routes`에 있다.

```rust
struct Routes {
    /// 플레이어의 본 샤드. 세션 동안 바뀌지 않는다
    content: BackendId,
    /// 지금 있는 InGameSpace의 호스트. 배정 전에는 None
    zone: Option<BackendId>,
}
```

- 다른 서버의 InGameSpace로 이동하면 `zone`만 바뀐다(6장). `content`는 그대로라서, 던전이나 친구 로비에 있는 동안에도 구매와 우편은 본 샤드로 간다.
- `zone`이 `None`인데(로딩 중) Zone 메시지가 오면 버리고 경고 로그를 남긴다.
- **카테고리 사이의 순서는 보장하지 않는다.** Content 메시지와 Zone 메시지는 서로 다른 서버로 가기 때문이다. 같은 카테고리 안에서는 순서가 지켜진다. 두 카테고리에 걸친 의존(예: 구매 후 장착)은 서버 쪽 흐름이 처리한다(03 문서). 클라이언트는 응답을 받은 뒤 다음 요청을 보내는 방식으로 이 의존을 다룬다.

### 3.3 백엔드 링크와 순서 보장

- Gateway와 백엔드 서버 사이에는 TCP 링크를 **여러 개**(설정값, 기본 4) 둔다. 링크 하나에서 생기는 head-of-line blocking을 줄이기 위해서다.
- 한 ClientSession의 패킷은 항상 **같은 링크**로 보낸다(`session_id % 링크 수`). 그래서 세션 하나 안에서는 패킷 순서가 보장된다.

### 3.4 제한과 보호 (Gateway에서 처리)

| 항목 | 기본값 (설정값) | 초과 시 |
|---|---|---|
| 최대 패킷 크기 | 64KB | 즉시 연결 종료 |
| 클라이언트가 보낸 `FRAGMENT` 프레임 | 허용 안 함 (8.3) | 즉시 연결 종료 |
| 초당 패킷 수 (세션별) | 60 | 경고 후 초과가 지속되면 종료 |
| 인증 제한 시간 | 접속 후 10초 | 연결 종료 |
| 하트비트 | 클라이언트가 10초마다 전송 | 30초 동안 수신이 없으면 연결 끊김으로 처리 (Detached로 전환) |
| 클라이언트 송신 큐 | 256 패킷 | 느린 클라이언트로 판단하고 연결 종료 (Detached로 전환) |
| 재전송 버퍼 (세션별, Reliable만) | 256 프레임 또는 64KB | 버퍼를 비우고 재동기화 필요 표시 (7.3) |

## 4. 백엔드(Game 서버, 전투 서버) 쪽 구조

백엔드는 클라이언트 소켓이 없다. Gateway와 다른 서버들의 링크만 있다.

```
[백엔드: I/O 런타임]
  GatewayLink × (Gateway 수 × 링크 수)
     ├─ reader task: 봉투 해석 → 페이로드 역직렬화와 검증 → 카테고리에 따라
     │                 Content → 플레이어 액터 (라우팅 테이블의 액터 핸들)
     │                 Zone    → 존 스레드 (라우팅 테이블)
     └─ writer task: 송신 큐(bounded) → Gateway 소켓
  ServerLink × (다른 서버 수 × 링크 수): 서버 간 메시지 (4.4)

[컨텐츠 런타임 (tokio)]  플레이어 액터 × 접속자 수. 플레이어 컨텐츠 상태. Game 서버(본 샤드)에만 있음 (01 문서 5장)
[존 스레드 × Kz]      InGameSpace
```

- **역직렬화와 검증은 I/O 스레드에서 한다.** 여러 I/O 워커가 병렬로 처리하고, 존 스레드와 플레이어 액터는 타입이 정해진 검증된 메시지만 받는다(가이드 7장 "경계에서 검증").
- 전투 서버에는 플레이어 액터가 없다. 컨텐츠 메시지는 항상 본 샤드로 가기 때문이다.
- 스레드 구성의 상세는 `01-threading.md`를 따른다.

### 4.1 라우팅: 어느 스레드로 보내나

- **Content**: 플레이어의 컨텐츠를 담당하는 것은 **플레이어 액터**다(01 문서 5장). GatewayLink의 라우팅 테이블이 `SessionId → 액터 핸들`을 들고 있고, 게임 입장 때 `RouteUpdate`로 등록된다.
- **Zone**: GatewayLink reader는 패킷마다 "이 세션의 Player는 어느 존 스레드에 있나"를 알아야 한다.
  - **각 GatewayLink reader task가 자기 링크로 들어오는 세션들의 라우팅 테이블(`HashMap<SessionId, ZoneIndex>`)을 단독으로 소유한다.** 링크 하나에 들어오는 세션은 그 링크만 담당하므로(3.3) 테이블을 공유할 필요가 없다. 락이 없다.
  - 테이블은 메시지로 갱신한다. Player가 InGameSpace에 배정되거나 다른 존 스레드로 이동하면, 존 스레드나 InGameSpaceManager가 해당 GatewayLink에 `RouteUpdate { session, zone }` 제어 메시지를 보낸다.
  - 이동 중(테이블 갱신 전)에 도착한 패킷은 출발 존 스레드로 간다. 출발 존 스레드는 그 Player가 이미 떠났으면 패킷을 도착 존 스레드로 넘긴다(forward). 이동 중의 짧은 구간에만 생기는 일이다.

### 4.2 봉투(Envelope) 형식: Gateway ↔ 백엔드

```
+----------+----------+---------------+----------+-------------+
| len: u32 | kind: u8 | session: u64  | msg: u16 | payload ... |
+----------+----------+---------------+----------+-------------+
  kind: 0 = 클라이언트 패킷 중계
        1 = 제어 메시지 (세션 연결됨, 끊김, 재접속됨, 교체됨, 라우팅 전환 등)
```

- 클라이언트 패킷 중계(kind 0)의 `msg`와 `payload`는 클라이언트가 보낸 것을 **그대로** 담는다. Gateway는 바이트를 복사만 한다.
- 제어 메시지(kind 1)는 서버끼리만 쓰므로 Rust 쪽 형식을 자유롭게 정할 수 있다. 클라이언트 엔진과 무관하다.

### 4.3 연결 이벤트 (LinkEvent)

백엔드는 연결과 세션을 갖지 않는다. Player는 **주소**만 들고 있다.

```rust
struct PlayerLink {
    gateway: GatewayId,
    session: SessionId,
    state: LinkState,   // Linked / Suspended / Unlinked
}
```

Gateway는 세션에 일어난 **사실**을 제어 메시지로 알리고, 백엔드는 이것을 `LinkEvent`로 바꿔 전달한다.

```rust
enum LinkEvent {
    Detached { reason: ConnCloseReason },             // 끊김 (유예 시작)
    Suspended,                                        // 백그라운드 예고
    Resumed { mode: ResumeMode, gateway: GatewayId }, // 같은 세션으로 복귀 (다른 Gateway로 왔을 수 있음)
    Replaced { gateway: GatewayId, session: SessionId }, // 중복 로그인으로 새 세션이 인계
    Closed,                                           // 유예 만료 또는 정상 종료
}
```

| 받는 곳 | 하는 일 |
|---|---|
| 존 스레드의 InGameSpace | 게임적인 결과를 **모드별 정책**으로 결정 (무적, AI 대리 전투, PvP 몰수패 타이머 등). `01-threading.md`의 InGameSpace 구조 참고 |
| 본 샤드의 플레이어 액터 | `Closed`이면 로그아웃 절차 (저장 후 정리) |

- **역할 분리**: Gateway는 사실만 알리고, 결과는 InGameSpace 모드가 결정한다.
- **게임 쪽 타이머는 Gateway의 유예 시간에 기대지 않는다.** PvP 몰수패 타이머는 PvP 모드가 직접 잰다. Gateway 유예 시간을 바꿔도 게임 규칙이 따라 바뀌지 않게 하기 위해서다.
- **순서 보장**: 제어 메시지는 그 세션의 게임 패킷과 같은 링크로 흐른다(3.3). "끊김 직전에 보낸 스킬 사용"과 "끊김 이벤트"의 순서가 뒤바뀌지 않는다.
- `Replaced`(새 기기가 다른 Gateway로 들어온 경우)나 `Resumed`(다른 Gateway에서 재개한 경우)로 Gateway가 바뀌면 `PlayerLink`의 주소를 바꾸고 라우팅 테이블을 갱신한다.

### 4.4 서버 간 링크 규칙

클라이언트 세션에서 정한 규칙이 서버 간 링크에도 같은 모양으로 반복된다.

| 클라이언트 세션 | 서버 간 링크 |
|---|---|
| `Auth` 핸드셰이크 | `ServerHello { server_id, role, protocol_version }` + 서버 인증 |
| 중복 로그인 | **중복 링크.** 두 서버가 동시에 서로 연결하면 하나만 남김 |
| 재접속 | 링크 재연결 (지수 백오프) |
| ConnId로 늦은 이벤트 무시 | **링크 세대 번호**로 옛 링크의 늦은 이벤트 무시 |
| 커넥션 상태 | `Handshaking → Active → Reconnecting` |

- **ServerId**: `{ shard: u16, role: ServerRole, instance: u16 }`. 클러스터 전체에서 유일하다.
- **연결을 시작하는 쪽**: Gateway → 백엔드는 항상 Gateway가 시작한다. 그 밖의 서버끼리는 **ServerId가 작은 쪽**이 시작한다. 그래서 중복 링크가 생기지 않는다. 경합으로 둘 다 생기면 작은 쪽이 시작한 링크를 남긴다.
- **링크 수**: 상대 서버당 여러 개(기본 2). 메시지는 키(PlayerId 등)의 해시로 링크를 고르므로, 같은 키의 메시지는 순서가 지켜진다.
- **신뢰성**: 링크 자체에는 seq가 없다. 유실되면 안 되는 서버 간 메시지(`GrantItem`, 거래 입금과 지급 등)는 `03-data-ownership.md`의 **outbox + 멱등 키**로 보장한다. 링크가 끊기면 재연결 후 outbox에서 미확인 메시지를 다시 보낸다.
- **서버 목록(발견)**: 어떤 서버가 떠 있는지는 Redis의 `server:{id}` 목록에서 얻는다(03 문서 9.7). 서버가 죽으면 TTL로 목록에서 빠진다. 클러스터 구성의 상세는 06 문서에서 다룬다.

## 5. 접속과 로그인 흐름

```
Client            Gateway                    Redis (online:{account})  Game 서버
  │──TCP 접속──────>│ [Unauthenticated]
  │──Auth(token)───>│──토큰 검증──────────────>│
  │                 │<─AccountId, 중복 접속 확인─│
  │<─AuthOk(session_key)─│ [Authenticated]
  │──EnterGame───────>│──(본 샤드)─────────────────────────────────────────>│ InGameSpaceManager: 로비 입장
  │                 │<─────────────────── SessionBound(player, routes) ─────│
  │                 │ [Active]
  │<═══════════════ 게임 패킷 (Gateway는 헤더만 보고 중계) ═══════════════>│
```

- 게임 `login_token`은 게임 **Entry 서버**가 발급한다. Entry 서버는 퍼블리셔 Login 서버의 입장 티켓을 퍼블리셔 A​PI로 확인하고, 게임 Account DB에서 캐릭터와 본 샤드를 정한다. 본 샤드는 토큰 안에 들어 있다. 상세는 `07-login-account.md`.
- **중복 접속**: 같은 계정으로 새 로그인이 들어오면 3.1의 중복 접속 절차를 따른다(나중 접속 우선).
- `session_key`는 재접속할 때 같은 세션임을 증명하는 키다. 세션이 끝날 때까지 바뀌지 않는다. 발급, 보관, 사용 규칙은 `docs/protocol/session-contract.md` 1장을 따른다.

## 6. 존 목적지 전환 (다른 서버의 InGameSpace로 이동)

클라이언트 연결은 그대로 두고, Gateway가 들고 있는 **존 목적지(`Routes.zone`)만** 바꾼다. 컨텐츠 목적지(본 샤드)는 바뀌지 않는다. 던전 입장(전투 서버 풀), 친구 로비 방문(다른 샤드), PvP 입장이 모두 이 흐름이다.

```
1. 출발 InGameSpace: 이동 결정 (예: 던전 입장)
2. Directory: 도착 InGameSpace를 찾거나 배치 (03 문서, 05 공간 수명 문서)
3. 본 샤드 컨텐츠 → 도착 호스트: CombatProfile 전달 (03 문서)
4. 도착 호스트: 수락 → Gateway에 제어 메시지 SwitchZone { session, to: 도착 호스트 }
5. Gateway: Routes.zone = 도착 호스트
            이후 이 세션의 Zone 메시지는 도착 호스트로 감. Content 메시지는 계속 본 샤드로
6. 돌아올 때: 같은 방식
```

- 전환하는 순간 Gateway가 "전환 중" 표시를 하고, 그동안 도착한 Zone 메시지는 잠시 보관했다가 전환이 끝나면 새 목적지로 보낸다. 패킷이 옛 서버로 새어 나가지 않게 하기 위해서다.
- **같은 서버 안에서** 다른 존 스레드로 옮기는 것은 Gateway와 무관하다. 그 서버 안의 라우팅 테이블만 바뀐다(4.1).
- 플레이어 데이터가 서버 간에 어떻게 다뤄지고 결과가 어떻게 본 샤드로 돌아오는지는 `03-data-ownership.md`가 다룬다.

## 7. 끊김, 재접속, 패킷 유실 복구 (N2, N9, N10)

### 7.0 유실은 어디서 생기나

- **TCP 연결이 살아 있는 동안에는 유실도 순서 뒤바뀜도 없다.** TCP가 보장한다. 그래서 연결 중에는 재전송 요청이 필요 없다.
- **유실은 연결이 끊기는 순간에 생긴다.**
  - 서버는 보냈지만 아직 네트워크나 커널 버퍼에 있던 데이터는 소켓과 함께 사라진다. 서버는 "보냈다"고 생각하는데 클라이언트는 받지 못해서 양쪽 상태가 어긋난다.
  - 모바일 앱이 백그라운드에서 **일시정지(suspend)**되면 연결이 동작하지 않는다. iOS에서 문제는 "백그라운드에 있는가"가 아니라 "일시정지되었는가"다. Android의 Doze 모드도 백그라운드 네트워크 접근을 제한한다.
  - Wi-Fi와 LTE가 바뀌면서 IP가 바뀌면 TCP 연결 자체가 끊긴다.
- **해결: 놓치면 안 되는 메시지에만 시퀀스 번호, ACK, 재전송 버퍼를 둔다.** 나머지는 재접속할 때 최신 상태로 덮어쓴다.
  - 같은 방식을 쓰는 선례로 ASP.NET Core SignalR의 stateful reconnect(.NET 8)와 MQTT의 persistent session(QoS 1)이 있다.

### 7.1 전달 등급: Reliable과 Volatile (N10)

모든 메시지에 시퀀스를 붙일 필요는 없다. 기준은 **"놓쳤을 때 다시 만들어 낼 수 있는가"**다.

| 등급 | 기준 | 예 | seq와 재전송 | 끊겼다가 재개하면 |
|---|---|---|---|---|
| **Reliable** | 놓치면 다시 만들 수 없는 **사건과 거래의 결과** | 상점 구매 결과, 보상 지급, 재화 변동, 우편 도착, 거래 성립, 퀘스트 완료 | **있음** | 빠진 것을 원래 순서대로 재전송 |
| **Volatile** | 최신 상태로 **덮어쓰면 되는 것** | 이동, 전투 연출, HP 변화, 주변 오브젝트 출현/소멸 | 없음 | 버림. 재개할 때 InGameSpace 스냅샷으로 최신 상태를 받음 |

클라이언트 → 서버 요청도 같은 기준이다.
- **Reliable 요청**: 구매, 보상 수령, 거래 확정. 재전송되고, Gateway가 중복을 걸러 **정확히 한 번** 처리된다.
- **Volatile 요청**: 이동 입력, 스킬 사용. 끊긴 순간의 입력은 버려진다. 플레이어가 다시 입력하면 된다.

참고로 Volatile 메시지도 순서는 지켜진다. 같은 TCP 연결 위에 있기 때문이다. 등급이 가르는 것은 "순서"가 아니라 **"연결이 끊겼을 때 다시 보낼 가치가 있는가"**다.

**등급은 스키마에서 메시지마다 선언한다.** `.proto`의 메시지 옵션(예: `option (delivery) = VOLATILE;`)으로 표시하고, 코드 생성기가 송신 시 헤더의 `RELIABLE` 플래그를 자동으로 설정한다. 게임 코드는 등급을 신경 쓰지 않는다.

**기본값은 Reliable이다.** Volatile은 명시해야 한다. 표시를 깜빡했을 때 Reliable로 처리되면 대역폭과 메모리가 조금 더 들 뿐이지만, Volatile로 처리되면 보상이 사라질 수 있기 때문이다.

### 7.2 시퀀스와 ACK

| 항목 | 규칙 |
|---|---|
| 대상 | **Reliable 프레임만.** Volatile과 제어 프레임(인증, 재개, 하트비트, ACK 전용)은 `seq = 0` |
| 번호 공간 | 방향별로 따로(서버→클라, 클라→서버). `u32`, ClientSession 생성 시 1부터. Reliable 프레임만 세므로 번호가 빈틈없이 이어진다 |
| 서버→클라 seq를 매기는 곳 | **Gateway.** 백엔드가 `RELIABLE` 플래그를 켠 프레임에 Gateway가 번호를 매긴다. Game 서버가 보낸 것이든 Gateway가 보낸 것이든 하나의 번호 공간이라서, 존 목적지 전환(6장)을 해도 번호가 끊기지 않는다 |
| 클라→서버 seq를 매기는 곳 | 클라이언트 네트워크 계층 |
| 조각 프레임 (8.3) | Reliable 메시지가 분할되면 조각마다 각자 seq를 받는다 |
| ACK | 모든 프레임 헤더의 `ack` 필드 = "상대가 보낸 Reliable 중 **처리 완료한 마지막 seq**"(누적 ACK). Volatile 프레임에도 실어 보낸다. 보낼 프레임이 없으면 1초마다 ACK 전용 프레임을 보낸다 |
| 처리 완료 기준 (클라) | 게임 로직에 반영한 뒤에 ACK한다. 받기만 하고 처리 전에 앱 프로세스가 죽으면 메모리가 모두 사라지므로 어차피 중복 접속 경로(3.1)로 간다 |
| 연결 중 seq가 건너뜀 | TCP에서는 일어날 수 없으므로 버그나 변조로 본다. 연결을 끊고 재개 절차(7.5)를 밟는다 |

### 7.3 재전송 버퍼

| 위치 | 담는 것 | 비우는 시점 |
|---|---|---|
| **Gateway** (ClientSession마다) | 클라에게 보냈지만 ACK를 받지 못한 **Reliable** 프레임 (원래 seq 그대로) | 클라의 ACK를 받으면 그 seq까지 앞에서 제거 |
| **클라이언트** | 서버에 보냈지만 ACK를 받지 못한 **Reliable** 요청 프레임 | 서버의 ACK를 받으면 제거 |

- 한도(설정값): 세션당 **256 프레임 또는 64KB** 중 먼저 닿는 쪽. Volatile이 빠지면서 버퍼에 들어가는 것은 구매, 보상 같은 드문 메시지뿐이라 작게 잡아도 된다. 최악의 경우 메모리는 동접 1만 × 64KB = 약 640MB이고, 실제로는 훨씬 작다.
- **Gateway의 재전송 버퍼는 Redis(`rbuf:{session}`)에 미러된다.** Reliable 프레임은 Redis에 기록한 뒤 클라이언트로 보내고, ACK를 받으면 Redis에서도 제거한다. 다른 Gateway에서 재개할 때 쓰인다(7.8).
- **끊겨 있는(Detached) 동안** Gateway는 백엔드가 보내는 프레임 중 **Reliable만 버퍼에 쌓고, Volatile은 버린다.**
- **한도를 넘으면** 버퍼를 비우고 그 세션에 "재동기화 필요" 표시를 한다. 재개할 때 전체 스냅샷 경로(7.5의 Resync)로 간다.
- Gateway와 백엔드 사이의 링크가 끊기면 그 링크로 흐르던 프레임이 사라질 수 있다. 그래서 해당 링크에 속한 세션은 모두 "재동기화 필요"로 표시한다.

### 7.4 끊김

1. Gateway가 연결 끊김을 감지한다(소켓 에러, 하트비트 타임아웃, 송신 큐 초과).
2. ClientSession을 `Detached`로 바꾸고 유예 마감 시각을 기록한다(`resume_grace` 기본 120초. 직전에 `Suspend`를 받았으면 `suspend_grace` 기본 600초. 설정값). seq와 재전송 버퍼는 그대로 유지한다.
3. 백엔드에 제어 메시지 `SessionDetached { session }`을 보낸다.
4. 백엔드의 Player는 InGameSpace에 **그대로 남는다.** 백엔드는 평소처럼 패킷을 보내고, Gateway가 Reliable만 버퍼에 쌓는다(7.3). 백엔드는 Detached인 세션에 Volatile 전송을 생략해서 링크 대역폭을 아낄 수 있다. 전투 중 처리(무적, 자동 전투, 그대로 노출 등)는 게임 기획에 따른다.

### 7.5 재개(Resume) 핸드셰이크

```
Client  ── Resume { token, last_server_seq }  ──────────────>  Gateway
            (last_server_seq: 클라가 처리 완료한 서버 Reliable 프레임의 마지막 seq)

Gateway: 토큰 검증 → 기존 ClientSession에 새 Connection을 붙임 (3.1의 재접속)

  [버퍼에 last_server_seq + 1부터 빠짐없이 있을 때]  → Replay 모드
Gateway ── ResumeOk { mode: Replay, last_client_seq } ─────>  Client
Gateway ── 버퍼의 Reliable 프레임을 원래 seq 그대로 재전송 ──>  Client
Gateway ── SessionResumed { resync: false } ───────────────>  Backend
Backend ── InGameSpace 스냅샷 (Volatile 상태: 위치, HP, 주변 오브젝트) ──>  Client

  [버퍼에 없을 때 (한도 초과, 링크 장애, Redis 미러에도 없음)]  → Resync 모드
Gateway ── ResumeOk { mode: Resync, last_client_seq } ─────>  Client
Gateway ── SessionResumed { resync: true } ────────────────>  Backend
Backend ── 전체 스냅샷 (InGameSpace 상태 + 플레이어 상태: 인벤토리, 재화, 우편 등) ──>  Client

Client  ── last_client_seq 이후의 미확인 Reliable 요청을 원래 seq 그대로 재전송 ──>  Gateway
Gateway: 이미 받은 seq 이하는 버림 (중복 처리 방지)
```

- **두 모드 모두 InGameSpace 스냅샷은 항상 보낸다.** 끊긴 동안의 Volatile 메시지는 버렸기 때문이다. 차이는 Reliable 결과를 재전송으로 채우느냐(Replay), 플레이어 상태 전체를 다시 보내느냐(Resync)다.
- Replay 모드에서는 **Reliable 재전송이 먼저, InGameSpace 스냅샷이 나중**이다. 클라이언트가 보상 지급 같은 결과를 먼저 반영한 뒤 화면 상태를 최신으로 맞추게 하기 위해서다.
- **클라이언트 요청의 중복 처리 방지**: Gateway가 "받은 마지막 클라 seq"를 기억하고, 그 이하의 seq는 백엔드로 넘기지 않는다. 그래서 끊기기 직전에 보낸 구매 요청이 재전송되어도 **같은 세션 안에서는 정확히 한 번** 처리된다.
- **세션을 넘어서는 중복은 이 계층이 막지 못한다.** 중복 접속(3.1)이나 유예 만료 후 재로그인으로 세션이 바뀐 경우가 그렇다. 그래서 구매, 거래, 보상 수령 같은 요청은 애플리케이션 수준에서 **요청 ID(멱등 키)**를 따로 두고 DB에서 중복을 확인한다. 이 부분은 DB 설계와 `03-data-ownership.md`에서 다룬다.
- 클라이언트도 재전송된 서버 프레임 중 이미 처리한 seq 이하는 버린다. 정상이라면 생기지 않지만 안전장치로 둔다.

### 7.6 클라이언트가 재연결을 시작하는 시점

| 트리거 | 동작 |
|---|---|
| 소켓 에러, 연결 종료 감지 | 즉시 재개 시도 |
| 하트비트 응답 없음 (15초) | 연결이 죽었다고 보고 재개 시도 |
| **앱이 포그라운드로 복귀** (Unity `OnApplicationPause(false)`, Unreal `FCoreDelegates::ApplicationHasEnteredForegroundDelegate` 등) | 연결 상태를 믿지 않고 즉시 핑으로 확인. 응답이 없으면 바로 재개 시도 |
| 네트워크 변경 (Wi-Fi ↔ LTE) | 기존 연결은 죽었다고 보고 바로 재개 시도 |

- 재시도 간격은 지수 백오프에 지터를 더한다(0.5초, 1초, 2초, ... 최대 10초).
- 유예 시간(`resume_grace` 120초, 백그라운드였다면 `suspend_grace` 600초)이 지나거나 `ResumeFail`을 받으면 재개를 포기하고 처음 접속 절차로 간다. 기존 Player가 남아 있다면 중복 접속 경로(3.1)로 이어받는다.

### 7.7 유예 만료

- 유예 시간 안에 재개하지 않으면 Gateway가 ClientSession과 재전송 버퍼를 정리하고 `SessionClosed { session }`을 보낸다.
- 백엔드는 정상 로그아웃 절차를 밟는다(저장 후 InGameSpace에서 제거).

### 7.8 어느 Gateway로든 재접속할 수 있다

- 세션 정보와 Reliable 재전송 버퍼는 Redis에 **미러**된다(03 문서 9.5). Reliable 프레임은 Redis에 기록한 **뒤에** 클라이언트로 보내므로, 클라이언트가 볼 수 있었던 프레임은 모두 Redis에 있다.
- 그래서 클라이언트는 **아무 Gateway로나** 재접속해도 된다(로드밸런서가 고른 곳). 새 Gateway는 `SET sess:{session}:owner ... GET`으로 세션을 넘겨받으면서 옛 Gateway를 알아내고, 옛 Gateway에 **Superseded** 메시지를 보낸다(서버 간 링크). 그리고 `rbuf`에서 Replay한다(03 문서 9.5).
- 원래 Gateway가 죽었거나 스케일 인으로 내려간 경우에도 Replay가 가능하다. 백엔드는 Gateway 링크가 끊어진 것을 보고 소속 Player 전원을 유예 상태로 두고, 다른 Gateway에서 재개되면 `LinkEvent::Resumed { gateway }`로 주소를 바꾼다.
- 원래 Gateway로 다시 온 경우는 메모리의 버퍼로 바로 처리한다. Redis가 멈춘 경우에도 이 경로는 동작한다(03 문서 9.10).

## 8. 패킷 형식

### 8.1 프레이밍 (확정): 클라이언트 ↔ Gateway

```
+----------+----------+------------+----------+----------+-------------+
| len: u32 | msg: u16 | flags: u16 | seq: u32 | ack: u32 | payload ... |
+----------+----------+------------+----------+----------+-------------+
  len   : 헤더(16바이트)를 포함한 전체 길이. 최대값을 넘으면 즉시 연결 종료
  msg   : 메시지 ID. Gateway는 이 값만 보고 라우팅한다
  flags : bit0 = FRAGMENT (8.3), bit1 = RELIABLE (7.1). 나머지 비트는 예약 (압축, 암호화 표시 등)
  seq   : Reliable 프레임의 시퀀스 번호 (7.2). Reliable이 아니면 0
  ack   : 상대가 보낸 Reliable 중 처리 완료한 마지막 seq (7.2)
  바이트 순서: little-endian 고정
```

헤더는 형식이 단순해서 Unity(C#), Godot(GDScript/C#), Unreal(C++) 어디서나 수십 줄이면 구현할 수 있다.

### 8.2 페이로드 형식 (확정: Protobuf + `prost`)

- 조사 근거: `docs/research/packet-format.md`
- 스키마 원본은 `proto/` 디렉터리 하나에 둔다. 서버(Rust, `prost`)와 클라이언트(Unity C#, Godot C#, Unreal C++)가 모두 여기서 코드를 생성한다.
- 메시지 ID(`msg u16`)와 메시지 타입의 대응표도 스키마에서 생성한다. 손으로 관리하지 않는다. 생성 방식(메시지 옵션 또는 별도 매핑 파일)은 구현 단계에서 정한다.
- Godot은 웹 export를 하지 않으므로 C#(`Google.Protobuf`)으로 처리한다. GDScript 코드 생성은 필요 없다.
- 스키마 작성 규칙은 조사 문서 5장을 따른다(필드 번호 재사용 금지, `reserved`, 좌표 양자화, 생성 타입을 `game` 크레이트로 들이지 않기).
- 이 결정은 `protocol` 크레이트 안에 갇혀 있다. 나중에 형식을 바꿔도 Gateway, 봉투, 게임 로직은 바뀌지 않는다.

### 8.3 큰 메시지 자동 분할 (Fragmentation)

예: `ReqPlayerItem` → `PlayerItemAck`의 아이템이 수천 개라서 직렬화 결과가 최대 프레임 크기(64KB)를 넘는 경우.

**원칙: 게임 코드는 분할을 모른다.** 서버 게임 코드는 `PlayerItemAck` 하나를 보내고, 클라이언트 게임 코드는 `PlayerItemAck` 하나를 받는다. 나누고 합치는 일은 서버의 `net` 계층과 클라이언트의 네트워크 계층에서만 한다.

#### 조각 프레임 형식

```
+----------+----------+--------------+------------------+------------+------------+---------+
| len: u32 | msg: u16 | flags: u16   | transfer_id: u32 | index: u16 | count: u16 | chunk.. |
|          |          | (FRAGMENT=1) |                  |            |            |         |
+----------+----------+--------------+------------------+------------+------------+---------+
  msg         : 원래 메시지 ID. 모든 조각이 같은 값
  transfer_id : 세션 안에서 단조 증가하는 분할 전송 번호
  index/count : 조각 순번(0부터)과 전체 조각 수. index == count - 1 이면 마지막 조각
```

그림에서는 `seq`와 `ack`를 생략했다. 실제로는 8.1의 공통 헤더(16바이트) 뒤에 조각 헤더가 온다. Reliable 메시지라면 조각마다 각자 seq를 받는다.

#### 송신 (서버)

1. `protocol` 인코더가 메시지 전체를 직렬화한다.
2. 크기가 최대 페이로드 이하면 일반 프레임 하나로 보낸다.
3. 넘으면 조각 크기로 잘라 `count`개의 조각 프레임을 만든다.
4. 모든 조각을 **하나의 송신 단위**로 큐에 넣는다. 그래서 조각 사이에 다른 게임 메시지가 끼지 않는다.

분할은 메시지를 만든 백엔드(Game 서버 또는 전투 서버)에서 한다. Gateway는 조각도 일반 프레임처럼 헤더만 보고 그대로 중계하므로 **Gateway는 고칠 것이 없다.**

#### 수신 (클라이언트)

1. `FRAGMENT` 프레임을 받으면 `transfer_id`별 버퍼의 `index` 위치에 저장한다.
2. `count`개가 모두 모이면 이어 붙여서 **한 번** 역직렬화하고, 게임 코드에 `PlayerItemAck` 하나로 전달한다.

조각마다 따로 역직렬화하는 방식은 쓰지 않는다. 조각의 경계는 바이트 단위로 임의로 잘린 것이라서 조각 하나만으로는 Protobuf 메시지가 되지 않기 때문이다. 조각마다 따로 해석되어야 하는 경우는 아래의 페이지 분할로 설계한다.

#### 순서 보장

- 게임 메시지의 순서는 보존된다. `PlayerItemAck`의 조각들 사이에 다른 게임 메시지가 끼지 않는다.
- Gateway 자체 메시지(하트비트 응답 등)는 조각 사이에 끼어들 수 있다. 그래서 클라이언트는 `FRAGMENT`가 아닌 프레임을 받아도 재조립 버퍼를 버리지 않는다.

#### 제한

| 항목 | 기본값 (설정값) | 초과 시 |
|---|---|---|
| 서버 → 클라 메시지 최대 전체 크기 | 4MB | 서버에서 에러 로그 + 전송 거부. 설계 버그로 취급 |
| 클라 재조립 타임아웃 | 30초 | 버퍼 폐기 후 재요청 또는 재접속 |
| 클라 → 서버 분할 | **허용하지 않음** | Gateway가 `FRAGMENT` 플래그가 붙은 클라이언트 프레임을 받으면 즉시 연결 종료. 서버 메모리를 고갈시키는 공격을 막기 위해서다. 클라이언트 요청은 작게 설계한다 |

#### 자동 분할과 페이지 분할의 역할 구분

| | 자동 분할 (이 절) | 페이지 분할 (애플리케이션 설계) |
|---|---|---|
| 형태 | 메시지 하나를 바이트 단위로 자름 | `PlayerItemPage { page, total, items }`처럼 독립된 메시지 여러 개 |
| 게임 코드 | 분할을 모름 | 페이지를 알고 처리 |
| 클라 처리 | 전부 도착 후 한 번에 | 도착하는 대로 표시 가능, 마지막 페이지에서 완료 처리 |
| 용도 | **안전망.** 예상보다 커진 메시지도 안전하게 전달 | **원래 큰 데이터의 설계 선택.** 피크 메모리가 작고 진행 표시가 가능 |

기준: 정상 크기가 수백 KB를 넘을 수 있는 응답(전체 인벤토리, 우편함 등)은 처음부터 페이지 메시지로 설계한다. 자동 분할은 그 밖의 모든 메시지를 위한 안전망으로 항상 켜 둔다.

큰 메시지를 보내는 동안에는 같은 연결의 이동, 전투 패킷이 그 뒤에서 기다린다(head-of-line). 그래서 대량 데이터 요청은 로딩 화면이나 메뉴처럼 전투가 아닌 시점에 하도록 클라이언트 쪽 가이드로 둔다.

#### 엔진 구현 검증

재조립 로직은 엔진별 네트워크 계층(C#, C++)에 한 번씩 구현한다. 서버 쪽에서 **바이트 샘플(테스트 벡터)**을 생성해 제공하고, 각 엔진 구현이 같은 결과를 내는지 이것으로 검증한다.

### 8.4 클라이언트 안 WebView 미니게임

클라이언트 안의 WebView(JavaScript)에서 미니게임이 돌아갈 수 있다.

**확정: 브리지 방식.** 미니게임은 혼자 플레이하고 결과(점수, 보상 요청)만 서버에 제출하는 형태다. WebView는 서버에 직접 접속하지 않는다. 호스트 클라이언트의 JS 브리지로 메시지를 넘기고, 호스트가 기존 TCP 연결로 중계한다.

- 인증과 세션을 그대로 재사용한다. WebView 쪽에 별도 로그인이 필요 없다.
- 서버에 WebSocket 같은 새 전송 계층이 필요 없다. N3(TCP만)이 유지된다.
- 재접속, 분할 같은 네트워크 처리를 호스트가 이미 하고 있으므로 미니게임은 메시지만 다룬다.
- 미니게임 메시지도 같은 `proto/` 스키마에 정의한다. JS 쪽은 Protobuf JS 코드 생성(예: protobuf-es)을 쓰거나, 호스트가 JSON과 Protobuf 사이를 변환한다.

실시간 대전형 미니게임이 생기면 그때 전용 백엔드(HTTP/WebSocket)를 따로 설계한다. 그 경우는 Gateway를 거치지 않는다.

미니게임 결과는 클라이언트가 계산한 값이므로 **그대로 믿지 않는다.** 보상 지급은 Content 메시지로 본 샤드가 처리하고, 점수 상한, 플레이 시간 같은 서버 쪽 검증을 거친다.

## 9. 크레이트 구성 변경

```
crates/
├─ protocol/   # 클라이언트 패킷(헤더 + 페이로드 코덱), 봉투, 제어 메시지
├─ net/        # (신규) 프레이밍 코덱, 링크 송수신 task 등 Gateway와 백엔드가 공유하는 네트워크 코드
├─ game/
├─ db/
├─ gateway/    # (신규) Gateway 바이너리
├─ server/     # 서버 바이너리. 역할(role) 설정으로 Game 서버, 전투 서버, 클러스터 서비스, 올인원을 띄운다
└─ bot/
```

의존 방향에 추가되는 것: `gateway → net → protocol`, `server → net`. `game`은 여전히 네트워크를 모른다.
