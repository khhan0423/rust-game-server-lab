# 설계 07. 로그인과 계정: 퍼블리셔 Login과 게임 Entry

[English](07-login-account.md) | **한국어**

- 상태: **초안** (2026-11-18)
- 관련 문서: `02-session-network.md` (Gateway, 세션), `04-database.md` (DB 구성), `docs/protocol/session-contract.md` (게임 `login_token` 이후의 흐름)

직접 퍼블리싱한다. 그래서 **퍼블리셔 영역**(플랫폼 계정, 여러 게임 공용)과 **게임 영역**(이 게임)을 분리한다. 대형 퍼블리셔 플랫폼이나 Steam과 같은 구조다.

## 0. 결정 요약

| # | 결정 | 내용 |
|---|---|---|
| L1 | 기본 로그인 | **게스트로 시작하고, 나중에 플랫폼 로그인을 연동**한다. 처음부터 플랫폼으로 로그인하는 것도 같은 구조로 지원한다 |
| L2 | 지원 플랫폼 | **Google, Apple, Steam** + 게스트. 모두 열어 두되 **Steam을 먼저 구현한다** (소유자 결정, 2026-11-19). 스팀 로그인 절차는 09 문서 1.1 |
| L3 | 계정과 로그인 수단 | **분리.** 퍼블리셔 계정 하나에 로그인 수단 여러 개를 연결한다 (2장) |
| L4 | 캐릭터 | **이 게임의 계정당 캐릭터 1개.** 서브컬처 게임이다. 성별 외형 프리셋 2개는 그 캐릭터의 속성이다 (5장) |
| L5 | 연동 충돌 | **자동 병합하지 않는다.** 기존 계정으로 전환하거나 취소 (2.3). 확정 |
| L6 | 영역 분리 | **Login 서버는 퍼블리셔 서비스(웹 서버) + LoginDB.** 게임은 **로드밸런서부터** 시작한다. 게임은 퍼블리셔 API로 "진짜 사용자, 진짜 계정, 이 게임 회원인가"만 확인한다 (1장) |
| L7 | 게임의 계정 DB | 게임의 **AccountDB**는 퍼블리셔가 넘겨준 **AccountID를 유니크 키**로 한다. 여기에 이 게임의 캐릭터(`PlayerId`)와 본 샤드를 기록한다 (6장) |
| L6a | 게임 Entry 서버 | 게임 쪽 첫 관문으로 **Entry 서버를 따로 둔다**(퍼블리셔 티켓 확인, 캐릭터 생성, 본 샤드 배정, 게임 `login_token` 발급). Gateway는 DB 없이 서명만 확인. 2026-11-18 확정 |
| L8 | 본 샤드 배정 | 처음 들어온 사람의 본 샤드는 **게임 Entry 서버**가 정한다. 이미 있는 사람은 AccountDB에 기록된 본 샤드를 그대로 쓴다 (6장) |

## 1. 전체 구조

```
 ┌──────────────────── 퍼블리셔 영역 ────────────────────┐
 │                                                       │
 │  클라 ──로그인(게스트/Google/Apple/Steam)──> Login 서버 (웹 서버)
 │                                               │ LoginDB: 퍼블리셔 계정, 로그인 수단,
 │                                               │          보유 게임, 회원 여부, 플랫폼 제재
 │  클라 <── 게임 입장 티켓 + 게임 입장 주소 ─────┘
 │                                                       │
 └───────────────────────────────────────────────────────┘
 ┌──────────────────── 게임 영역 ────────────────────────────────────────────────┐
 │                                                                               │
 │  클라 ──티켓──> 로드밸런서 ──> Entry 서버 (게임 로그인)                          │
 │                                 ① 티켓 확인 ──퍼블리셔 API──> Login 서버       │
 │                                 ② AccountDB: AccountID로 조회. 없으면 캐릭터     │
 │                                    생성 + 본 샤드 결정                          │
 │  클라 <── 게임 login_token + Gateway 주소 ──┘                                  │
 │                                                                               │
 │  클라 ──TCP──> 로드밸런서 ──> Gateway ──> Game 서버 ...  (02 문서 이후 그대로)    │
 └───────────────────────────────────────────────────────────────────────────────┘
```

| | 퍼블리셔 Login 서버 | 게임 Entry 서버 |
|---|---|---|
| 영역 | 퍼블리셔. 여러 게임이 같이 씀 | 이 게임 전용 |
| 형태 | 웹 서버 (HTTPS) | 웹 서버 (HTTPS). 상태 없음, 로드밸런서 뒤에 여러 대 |
| 담당 | 퍼블리셔 계정 생성, 로그인 수단과 연동, 보유 게임, 회원 여부, 플랫폼 제재, 게임 입장 티켓 발급, 티켓 확인 API | 티켓 확인 요청, 이 게임의 계정과 캐릭터, 본 샤드 배정, 게임 내 제재 확인, 게임 `login_token` 발급, 점검과 버전 확인, 로그인 대기열 |
| DB | **LoginDB** | **AccountDB** (게임) |
| 게임 데이터 | 모름 | 캐릭터 존재와 본 샤드까지만 |

- **Gateway는 지금처럼 DB 없이 게임 `login_token`의 서명만 확인한다.** 퍼블리셔 API 호출(외부 HTTP)과 DB 쓰기는 Entry 서버가 한다. 그래서 세션 계약 문서와 02 문서의 Gateway 설계는 바뀌지 않는다.
- 로드밸런서는 연결을 나누고, Entry 서버는 본 샤드를 정하고, Gateway는 토큰에 적힌 목적지로 보내기만 한다. 세 역할은 겹치지 않는다.

## 2. 퍼블리셔 Login 서버 (퍼블리셔 영역)

이 장은 게임 서버 구현 범위가 아니다. 게임이 기대하는 **계약**만 적는다.

### 2.1 계정과 로그인 수단

```
퍼블리셔 계정 (AccountID)          ← 퍼블리셔 전체에서 유일, 바뀌지 않음
   ├─ 로그인 수단: Guest  (서버가 발급한 비밀값)
   ├─ 로그인 수단: Google (subject = Google 사용자 ID)
   ├─ 로그인 수단: Apple  (subject = Apple 사용자 ID)
   └─ 로그인 수단: Steam  (subject = SteamID64)
```

로그인은 항상 같은 규칙으로 동작한다: **"이 로그인 수단 `(provider, subject)`에 연결된 계정을 찾고, 없으면 새 계정을 만든다."**

| 경우 | 처리 |
|---|---|
| 처음 게스트로 시작 | Guest 수단 생성 → 새 계정 + 연결 |
| 게스트가 플랫폼 연동 | 지금 계정에 플랫폼 수단을 **추가** |
| 처음부터 플랫폼으로 로그인 | 그 수단이 없으므로 새 계정 + 연결. 게스트 시작과 같은 경로 |
| 다른 기기에서 플랫폼으로 로그인 | 그 수단으로 기존 계정을 찾아 같은 계정으로 들어감 |

규칙: 한 계정에 플랫폼당 수단 하나, 마지막 수단은 해제 불가, `(provider, subject)`는 한 계정에만 연결(유니크).

### 2.2 인증 방식

| provider | 클라이언트가 받는 것 | Login 서버의 검증 |
|---|---|---|
| Guest | 처음 시작할 때 서버가 발급한 무작위 비밀값 (iOS Keychain, Android Keystore에 보관) | 비밀값의 해시와 비교. DB에는 해시만 |
| Google | Google ID 토큰 | Google 공개키로 서명, 발급 대상, 만료 확인 |
| Apple | Apple identity token | Apple 공개키로 서명, 발급 대상, 만료 확인 |
| Steam | Steam 인증 티켓 | Steam Web API로 검증 |

- 게스트를 기기 ID(광고 ID 등)로 식별하지 않는다.
- iOS에서 소셜 로그인을 제공하면 Apple 심사 가이드라인상 Sign in with Apple(또는 동등한 로그인)을 함께 제공해야 한다. 출시 전에 최신 가이드라인을 확인한다.

### 2.3 연동과 예외 상황

| 상황 | 처리 |
|---|---|
| 연동하려는 플랫폼 수단이 이미 다른 계정에 붙어 있음 | **자동 병합하지 않는다.** ① 그 기존 계정으로 전환 ② 취소 중 선택 |
| 게스트가 연동 전에 앱을 지우거나 기기를 바꿈 | 계정을 잃는다. 게임 안에서 연동을 권장(연동 보상 등) |
| 마지막 수단 해제 시도 | 거부 |
| 탈퇴 | 퍼블리셔 정책. 게임에는 통지(2.5)로 알린다 |

### 2.4 LoginDB 스키마 (초안, 퍼블리셔 소유)

```sql
CREATE TABLE accounts (
    account_id   text PRIMARY KEY,             -- 퍼블리셔 AccountID (게임으로 넘어가는 키)
    status       smallint NOT NULL,            -- 정상 / 플랫폼 제재 / 탈퇴 대기
    created_at   timestamptz NOT NULL
);

CREATE TABLE account_identities (
    provider     smallint NOT NULL,            -- Guest / Google / Apple / Steam
    subject      text NOT NULL,
    account_id   text NOT NULL REFERENCES accounts(account_id),
    secret_hash  bytea,                        -- Guest만
    linked_at    timestamptz NOT NULL,
    PRIMARY KEY (provider, subject),
    UNIQUE (account_id, provider)
);

CREATE TABLE game_memberships (                -- 어떤 게임을 가졌나, 그 게임의 회원인가
    account_id   text NOT NULL REFERENCES accounts(account_id),
    game_id      text NOT NULL,
    status       smallint NOT NULL,            -- 회원 / 해지 / 게임별 플랫폼 제재
    joined_at    timestamptz NOT NULL,
    PRIMARY KEY (account_id, game_id)
);
```

여기에 약관 동의 기록, 개인정보, 결제 수단 같은 퍼블리셔 정보가 더해진다.

### 2.5 게임과의 계약

| 계약 | 내용 |
|---|---|
| **게임 입장 티켓** | 짧은 수명(예: 1분), **1회용**, `game_id`가 묶인 불투명 값 |
| **티켓 확인 API** (게임 → 퍼블리셔) | `VerifyTicket(ticket, game_id)` → `{ account_id, 회원 상태, 플랫폼 제재 여부, 필수 정보(국가, 연령 구분 등) }`. 확인과 동시에 티켓을 소모 처리 |
| **통지** (퍼블리셔 → 게임, webhook) | 플랫폼 제재, 탈퇴, 회원 해지. 게임은 해당 플레이어를 Kick하고 상태를 반영 |
| 게임 → 퍼블리셔 인증 | 서버 간 인증 (API 키 또는 mTLS). 사설망 또는 허용 목록 |

### 2.6 파일럿 구현: 게스트 로그인 API

파일럿에서는 Login 서버를 게스트 수단만으로 만든다. 다른 수단은 나중에 같은 구조에 붙인다. 서버는 `publisher` 크레이트이고, SQL은 `db` 크레이트의 `login` 모듈에 둔다. 게임 쪽 크레이트는 LoginDB에 접근하지 않는다.

요청과 응답은 모두 HTTP 위의 JSON이다. 에러 응답은 `{ "error": "<코드>" }`이고 상태 코드는 아래 표와 같다.

| 호출 | 누가 부르나 | 요청 | 성공 응답 |
|---|---|---|---|
| `POST /v1/guest/accounts` | 클라이언트, 처음 실행할 때 | `{}` | `201` `{ "guest_id", "secret" }`. 비밀값은 이때 한 번만 내려간다 |
| `POST /v1/guest/login` | 클라이언트 | `{ "guest_id", "secret", "game_id" }` | `200` `{ "ticket", "expires_in_secs", "entry_url" }` |
| `POST /v1/tickets/verify` | 게임 Entry 서버, `x-api-key` 헤더와 함께 | `{ "ticket", "game_id" }` | `200` `{ "account_id", "membership", "sanction" }`. 확인하면 티켓이 소모된다 |

| 에러 코드 | 상태 | 언제 |
|---|---|---|
| `invalid_request` | 400 | 본문에 필드가 빠졌거나 형식이 틀림 |
| `invalid_credentials` | 401 | 모르는 게스트 ID이거나 비밀값이 틀림. 두 경우를 구분하지 않는다 |
| `unauthorized` | 401 | 확인 호출에 API 키가 없거나 틀림 |
| `account_blocked` | 403 | 계정이 플랫폼 제재 중이거나 탈퇴 대기 중 |
| `unknown_game` | 404 | `game_id`가 Login 서버 설정에 없음 |
| `ticket_invalid` | 404 | 모르는 티켓, 만료된 티켓, 이미 쓴 티켓, 다른 게임용 티켓. 경우를 구분하지 않는다 |
| `internal_error` | 500 | DB에 접속할 수 없는 경우처럼 서버 쪽 사정으로 실패함. 자세한 내용은 운영 로그에 남기고 호출한 쪽에는 주지 않는다 |

- 클라이언트로 가는 응답에는 계정 번호가 없다. 내부 키는 서버 쪽에만 둔다(5.1절). 서버끼리 부르는 확인 호출만 `account_id`를 돌려준다.
- `account_id`와 `guest_id`는 UUID v7 문자열이다. `secret`과 `ticket`은 무작위 32바이트를 16진수 64자로 적은 것이다.
- LoginDB에는 비밀값과 티켓의 SHA-256 해시만 저장한다. 파일럿에서는 DB의 내장 `sha256()`으로 해시를 계산한다. 이 서버가 실제 유저를 받기 전에 해시 계산을 서버 프로세스 안으로 옮겨, 원래 값이 DB까지 가지 않게 한다.
- 확인 응답의 `membership`은 `"member"`, `"canceled"`, `"sanctioned"` 중 하나(그 게임에서의 계정 상태)이고, `sanction`은 `"none"`, `"sanctioned"`, `"closing"` 중 하나(계정의 플랫폼 상태)다. 둘 다 문자열이라 DB의 숫자 표현이 드러나지 않고, 나중에 값을 추가할 수 있다.
- 확인은 유효한 티켓을 항상 소모하고 현재 상태를 알려 준다. 제재 때문에 거절하지는 않는다. 판단은 게임의 Entry 서버가 하고, `membership`이 `"member"`이고 `sanction`이 `"none"`일 때만 입장시킨다.
- Login 서버가 거절하는 곳은 로그인이다. 계정이 활성 상태가 아니거나 그 게임의 멤버십이 제재 상태면 `account_blocked`로 답한다. 해지된 멤버십은 로그인하면 다시 멤버가 된다.
- 티켓의 수명은 기본 60초(설정값)이고 한 번만 쓸 수 있다. 소모는 조건부 `UPDATE` 한 번이고, 바뀐 행 수로 성공을 판단한다.
- 어떤 게임에 처음 로그인하면 그 계정의 멤버십이 만들어진다. 유료 게임의 보유 확인은 스팀 수단과 함께 넣는다.
- 확인 호출의 API 키와 LoginDB 접속 문자열은 비밀값이라 환경 변수에서 읽는다.
- 티켓은 2.4의 초안에 없던 테이블에 저장한다.

```sql
CREATE TABLE entry_tickets (
    ticket_hash  bytea PRIMARY KEY,
    account_id   text NOT NULL REFERENCES accounts(account_id),
    game_id      text NOT NULL,
    expires_at   timestamptz NOT NULL,
    consumed_at  timestamptz
);
```

## 3. 게임 Entry 서버 (게임 영역)

### 3.1 입장 흐름

```
클라 ──EnterRequest(ticket)──> 로드밸런서 ──> Entry 서버
Entry: ① 퍼블리셔 VerifyTicket(ticket, game_id)
          실패, 비회원, 플랫폼 제재 → 거절
       ② 점검 중, 클라이언트 버전 확인
       ③ AccountDB: account_id로 조회
            있음 → 기록된 player_id, home_shard 사용. 게임 내 제재 확인
            없음 → 캐릭터 생성 + 본 샤드 결정 (4장) → AccountDB 기록 (한 트랜잭션)
       ④ 동접 상한 초과면 로그인 대기열 (03 문서 9.8)
       ⑤ 게임 login_token 발급 (서명)
클라 <── login_token + Gateway 주소 ──
클라 ──TCP──> 로드밸런서 ──> Gateway ──Auth(login_token)──> ... (세션 계약 문서)
```

- **클라이언트가 보낸 계정 정보는 믿지 않는다.** 게임은 반드시 퍼블리셔 API **응답**에 들어 있는 `account_id`와 정보만 쓴다.
- 퍼블리셔 API는 **입장할 때 한 번만** 부른다. 패킷마다 부르지 않는다.
- 재접속(`Resume`)은 Entry 서버를 거치지 않는다. `session_key`로 Gateway에서 바로 이어진다(세션 계약 문서).

### 3.2 게임 `login_token`

- Entry 서버가 서명한 짧은 수명의 토큰이다. 안에 `account_id`, `player_id`, 본 샤드, 만료 시각, 서명 키 ID가 들어 있다.
- Gateway는 **서명만 확인**하고 DB를 조회하지 않는다(04 문서 2장).
- 퍼블리셔의 입장 티켓과는 다른 것이다. 퍼블리셔 티켓은 Entry 서버에서 소모되고 끝난다.

## 4. 본 샤드 배정

| 결정 | 기간 | 기준 | 누가 |
|---|---|---|---|
| TCP 연결을 어느 Gateway가 받나 | 연결 하나 동안 | 지금 연결 수 | 로드밸런서 |
| **이 플레이어의 본 샤드** | **영구** (처음 입장할 때 한 번) | 샤드별 **누적 인원**, 운영자 추천 지정 | **Entry 서버** |
| 메시지를 어느 서버로 보내나 | 메시지마다 | 토큰과 세션에 적힌 목적지 | Gateway (판단 없이 따라감) |

- **친구 코드 (소유자 결정, 2026-11-19):** 처음 입장할 때 친구 코드를 넣으면 그 친구의 본 샤드로 배정한다. 그 샤드가 신규를 받지 않는 상태면 아래 기본 규칙을 따르고 그 사실을 알려 준다.
- 기본 규칙 (친구 코드가 없을 때): **열려 있는 샤드 중 누적 인원이 가장 적은 곳.** 운영자가 "추천 샤드"를 지정했으면 그곳을 우선한다. 샤드 목록과 열림 상태는 Common DB의 설정에서 읽는다.
- 지금 순간의 부하가 아니라 **누적 인원**을 보는 이유: 배정이 영구적이기 때문이다. 새벽에 한가한 샤드에 신규를 몰면 저녁에 그 샤드가 넘친다.
- 샤드 하나에 Game 서버 프로세스가 여러 대일 때 "이 플레이어의 컨텐츠를 어느 프로세스가 맡나"는 별도 문제로 06 클러스터 문서에서 다룬다.

## 5. 캐릭터

- **이 게임의 계정당 캐릭터 1개다.** 처음 입장할 때 Entry 서버가 `PlayerId`(UUID v7)를 만들고 AccountDB에 기록한다. 캐릭터의 게임 데이터 초기값은 본 샤드의 Game DB에 만든다(본 샤드 Game 서버에 생성 요청, 멱등).
- `AccountId`(퍼블리셔 것)와 `PlayerId`(게임 것)는 따로 둔다. 퍼블리셔 ID 형식에 게임 데이터가 묶이지 않게 하고, 서버 이전 같은 작업에서 둘을 다르게 다루기 위해서다.
- **성별 외형 프리셋 2개**는 캐릭터 하나의 속성이다. 두 프리셋의 외형 데이터와 "지금 쓰는 프리셋"을 Game DB의 캐릭터 데이터에 저장한다. 전환은 Content 메시지로 본 샤드에서 처리하고, 결과(`CombatProfile`의 외형)를 현재 InGameSpace에 반영한다.
- 캐릭터 선택 단계가 없다. 게임 입장은 `EnterGame`이다(02 문서).

### 5.1 유저 태그와 닉네임 (소유자 결정, 2026-11-20)

친구 요청, 귓속말, 초대를 하려면 유저가 서로를 가리킬 방법이 필요하다. 내부 키로는 할 수 없다. 한번 알려지면 바꿀 수 없고, `PlayerId`와 `AccountId`에는 계정을 만든 시각이 드러나며, 36자를 입력할 사람은 없다. 그래서 캐릭터마다 공개용 이름을 두 개 두고, 내부 키는 게임 클라이언트에 보내지 않는다.

| | 유저 태그 | 닉네임 |
|---|---|---|
| 용도 | 유저 한 명을 정확히 찾기: 친구 요청, 친구 코드, 고객 문의 | 월드, 채팅, 랭킹에 보이는 이름 |
| 누가 정하나 | Entry 서버가 무작위로 | 유저가 처음 입장할 때 |
| 유일성 | 게임 전체에서 유일 | 게임 전체에서 유일 |
| 변경 | 재발급으로 가능 | 정책 미정 |

**유저 태그**

- 영문 대문자와 숫자에서 `0`, `O`, `1`, `I`, `L`을 뺀 글자(31개)로 무작위 9자리를 만든다(약 26조 가지). 화면에는 `K7Q-M2X-RP4`처럼 세 자리씩 끊어 보여 준다. 저장할 때는 하이픈을 뺀다. 입력은 하이픈이 있든 없든, 대문자든 소문자든 받는다.
- 순번으로 주지 않는다. 그래서 태그로 유저 수를 짐작할 수 없고, 태그를 차례로 훑을 수도 없다.
- Entry 서버가 처음 입장할 때 발급한다. 유일성은 AccountDB의 유니크 제약이 지키고, 겹치면 다시 뽑는다.
- **친구 코드가 곧 유저 태그다.** 신규 유저가 친구의 샤드에 들어가려고 넣는 친구 코드(4장)는 그 친구의 태그다.
- 유저는 30일에 한 번(설정값) 태그를 재발급받을 수 있고, 운영자는 언제든 재발급할 수 있다. 옛 태그는 바로 쓸 수 없게 된다. 친구 관계는 `PlayerId`로 저장하므로 재발급해도 유지된다.
- 태그 조회에는 유저별 횟수 제한을 둔다. 태그를 대량으로 넣어 보며 맞히지 못하게 하기 위해서다.

**닉네임**

- 샤드별이 아니라 게임 전체에서 유일하다. 서로 다른 샤드의 유저가 필드, 던전, 파티에서 만나므로 이름만으로 구분할 수 있어야 한다.
- AccountDB에 표시용으로 입력한 그대로의 이름과, 정규화한 형태(대소문자를 접고 유니코드를 정규화해서, 비슷하게 보이는 표기를 같은 이름으로 본다)를 별도의 유니크 컬럼에 저장한다. 두 유저가 동시에 같은 이름을 요청하면 유니크 제약이 누가 가져갈지 정한다.
- 허용 글자, 길이, 금지어 목록, 이름 변경 정책은 아직 정하지 않았다(8장).

**게임 클라이언트가 받는 것**

- 다른 유저에 대해서는 닉네임과 유저 태그를 받는다. 장소 안에서는 그 장소에서만 통하는 번호로 유저를 가리키고, 이 번호는 들어갈 때마다 새로 받는다.
- `PlayerId`와 `AccountId`는 게임 클라이언트에 보내지 않는다. 본인 것도 보내지 않는다.

**첫 입장에는 닉네임이 필요하다**

티켓은 한 번만 쓸 수 있어서, Entry 서버가 닉네임을 물어본 뒤 같은 티켓을 다시 확인할 수 없다. 그래서 첫 입장은 두 단계로 한다.

1. 클라이언트가 티켓을 보낸다. Entry 서버가 확인한다. AccountDB에 그 계정의 캐릭터가 없으면 "캐릭터 필요"라고 답하면서, 그 계정용으로 서명한 짧은 수명의 생성 토큰을 준다.
2. 클라이언트가 생성 토큰, 닉네임, 그리고 있으면 친구 코드를 보낸다. Entry 서버가 계정 행, 유저 태그, 닉네임을 한 트랜잭션으로 넣는다. 닉네임이 이미 있으면 그렇게 답하고, 클라이언트는 같은 토큰으로 다른 이름을 다시 시도한다.

## 6. AccountDB 스키마 (초안, 게임 소유)

```sql
CREATE TABLE game_accounts (
    account_id   text PRIMARY KEY,             -- 퍼블리셔가 넘겨준 AccountID (유니크 키)
    player_id    uuid NOT NULL UNIQUE,         -- 캐릭터 1개. 게임 클라이언트에 보내지 않는다
    player_tag   text NOT NULL UNIQUE,         -- 공개용 태그이자 친구 코드 (5.1절)
    tag_issued_at timestamptz NOT NULL,        -- 재발급 간격 계산용
    nickname     text NOT NULL,                -- 입력한 그대로, 표시용
    nickname_key text NOT NULL UNIQUE,         -- 정규화한 형태. 유일성을 정한다
    home_shard   smallint NOT NULL,            -- 플레이어 디렉터리의 정답 (03 문서 7.2)
    status       smallint NOT NULL,            -- 게임 내 제재, 퍼블리셔 통지 반영 상태
    created_at   timestamptz NOT NULL
);

CREATE TABLE game_sanctions (
    account_id   text NOT NULL REFERENCES game_accounts(account_id),
    kind         smallint NOT NULL,
    until_at     timestamptz,
    reason       text NOT NULL,
    created_at   timestamptz NOT NULL
);
```

- **처음 입장이 동시에 두 번 들어오는 경우**(두 기기에서 동시에 첫 입장): `account_id` 기본 키 덕분에 한쪽 `INSERT`만 성공한다. 실패한 쪽은 다시 조회해서 먼저 만들어진 캐릭터를 쓴다(`INSERT ... ON CONFLICT DO NOTHING` 후 조회).
- Game 서버의 플레이어 디렉터리 조회(`PlayerId → 본 샤드`)는 Redis 캐시(`home:{player}`)를 먼저 보고, 없으면 Entry 서버에 묻는다. AccountDB의 주인은 Entry 서버다.
