## 1. DB 종류

```
  [퍼블리셔 영역]     ┌──────────────┐
                      │   LoginDB    │   퍼블리셔 계정, 로그인 수단, 보유 게임, 회원 여부 (Login 서버 소유)
                      └──────────────┘
  [게임 영역]
                      ┌──────────────┐
                      │  Account DB  │   전역 1개. 퍼블리셔 AccountID → 이 게임의 캐릭터, 본 샤드
                      └──────────────┘
        ┌──────────────┐  ┌──────────────┐  ┌──────────────┐
        │  Game DB 1   │  │  Game DB 2   │  │  Game DB N   │   샤드마다
        │  Log DB 1    │  │  Log DB 2    │  │  Log DB N    │   샤드마다
        └──────────────┘  └──────────────┘  └──────────────┘
                      ┌──────────────┐
                      │  Common DB   │   전역 1개 (전 서버 공유)
                      └──────────────┘
```

| DB | 개수 | 들어가는 것 | 쓰는 주인 |
|---|---|---|---|
| **Login** (퍼블리셔) | 퍼블리셔에 1 | 퍼블리셔 계정, 로그인 수단(게스트, Google, Apple, Steam), 보유 게임, 회원 여부, 플랫폼 제재. 스키마는 07 문서 2.4 | 퍼블리셔 Login 서버 (게임은 접속하지 않음) |
| **Account** | 전역 1 | **퍼블리셔 AccountID(유니크 키) → 이 게임의 캐릭터(`PlayerId`, 1개)와 본 샤드** = 플레이어 디렉터리의 정답, 게임 내 제재. 스키마는 07 문서 6장 | 게임 Entry 서버 |
| **Game** | 샤드마다 | 플레이어 컨텐츠(인벤토리, 지갑, 장비, 퀘스트, 우편), 로비 상태, 거래성 로그(아이템/재화 변동 내역), 멱등 키, outbox | 그 샤드의 Game 서버 (플레이어 액터, 로비 host) |
| **Log** | 샤드마다 (나누는 방식은 Fluent Bit 라우팅 설정) | 게임 분석 로그 (접속, 이동, 전투 통계 등) | **Fluent Bit**가 쓴다. 게임 서버는 직접 붙지 않음 (1.1) |
| **Common** | 전역 1 | 전 서버가 공유하는 정보: **길드**, 길드 던전 상태, 친구 관계, 샤드 간 거래 상태, 샤드 목록과 설정, 시즌, 랭킹 보관 기록, 공지 | 항목별 주인 액터 (5장) |

### 1.1 로그 세 종류와 경로

코드 쪽 규칙(운영 로그 `tracing`, 분석 로그 타입 이벤트)과 Fluent Bit 구성(에이전트 + 집계기, Log DB 파티셔닝)은 `08-operations-observability.md`를 따른다.

| 종류 | 예 | 경로 | 이유 |
|---|---|---|---|
| **거래성 로그** | 아이템 생성/삭제, 재화 변동 | **Game DB, 같은 트랜잭션** (Fluent를 거치지 않음) | "팔렸는데 로그가 없다"가 생기면 안 된다. CS 대응의 근거 |
| **게임 분석 로그** | 접속, 이동, 전투 통계, 아이템 획득 분석 | 서버는 **JSON 파일에만 쓴다** → **Fluent Bit**가 수집 → 규칙에 따라 **Log DB** 또는 파일 보관 | 양이 많고, 잃어도 게임에 영향이 없다 |
| **운영 로그** | 에러, 경고, 틱 초과 (`tracing`) | 서버는 **JSON 파일/표준 출력에만** → Fluent Bit → **파일 보관**(기본). **어떤 DB에도 쓰지 않는다.** 검색이 필요해지면 로그 전용 저장소(Loki 등)를 붙이는 것은 선택 (08 문서) | 서버 상태 확인용 |

```
게임 서버 ──(거래성 로그, 같은 트랜잭션)──────────────> Game DB
게임 서버 ──(분석 로그) → game-analytics.jsonl ─┐
게임 서버 ──(운영 로그) → ops.jsonl ────────────┤
                                               ▼
                                    Fluent Bit (서버마다 하나)
                                    태그별 라우팅 규칙 (설정 파일)
                                      ├─ analytics.* ──> Log DB (pgsql 출력 플러그인, JSONB)
                                      ├─ analytics.* ──> 파일 보관 (압축, 장기 보관)
                                      └─ ops.*       ──> 파일 보관 (DB에 쓰지 않음. 검색이 필요하면 Loki 등을 선택적으로)
```

- **게임 서버는 Log DB에 직접 붙지 않는다.** 로그를 파일에 쓰기만 하고, 어디로 보낼지는 **Fluent Bit 설정**이 정한다. 그래서 로그 목적지를 바꾸거나 늘려도(파일, Log DB, 나중에 분석 저장소) 게임 코드는 바뀌지 않는다.
- 로그가 느리거나 Log DB가 멈춰도 게임은 영향을 받지 않는다. 파일 쓰기는 버퍼를 둔 별도 작업으로 하고, Fluent Bit는 자기 버퍼(파일 시스템 버퍼 권장)로 재전송한다.
- 각 로그 줄에는 **종류 태그**(`log_type`), 샤드, 서버 ID, 시각, `player_id` 같은 공통 필드를 넣는다. 라우팅과 조회가 이 필드로 이루어진다.
- Fluent Bit의 PostgreSQL 출력 플러그인은 로그 한 줄을 테이블의 JSONB 컬럼 하나에 저장한다. 분석용 정형 테이블이 필요하면 Log DB 안에서 주기적으로 변환한다.
- 분석 로그는 **최소 한 번** 전달이라 중복이 있을 수 있다. 분석 용도에는 문제가 없고, 정확해야 하는 기록은 거래성 로그(Game DB)에 둔다.

---|---|---|---|
| **거래성 로그** | 아이템 생성/삭제, 재화 변동 | **Game DB, 같은 트랜잭션** | "팔렸는데 로그가 없다"가 생기면 안 된다. CS 대응의 근거 |
| **분석/행동 로그** | 접속, 이동, 전투 통계 | **Log DB** | 양이 많고, 잃어도 게임에 영향이 없다 |

분석 로그는 게임 처리 경로를 막지 않는다. 별도 커넥션 풀로 모아서 한 번에 쓰고(batch), Log DB가 느리거나 멈추면 버퍼가 넘치는 만큼 버리고 지표만 남긴다.

## 2. 서버별 접속 DB

| 서버 | Account | Game | Common | Log |
|---|---|---|---|---|
| **Entry 서버** | **읽기/쓰기** | - | 읽기 (샤드 목록, 점검 설정) | - |
| **Gateway** | - | - | - | - |
| **Game 서버 (샤드 N)** | - | **N번만** | 읽기/쓰기 (길드 액터, 친구 등 자기가 주인인 항목만) | - |
| **전투 서버** | - | - | 읽기 (설정) | - |
| **거래 서비스** | - | - | 읽기/쓰기 (거래 테이블만) | - |
| **Fluent Bit** | - | - | - | **쓰기** |

모든 게임 서버는 로그를 파일에만 쓴다. Log DB에 쓰는 것은 Fluent Bit뿐이다(1.1).

**샤드와 Game 서버의 대응 (소유자 승인, 2026-11-19)**

```
게임서버1 ── 게임DB1   (샤드 1)
게임서버2 ── 게임DB2   (샤드 2)
게임서버3 ── 게임DB3   (샤드 3)
```

- 처음에는 **샤드당 Game 서버 1대(1:1)**로 시작한다. Game 서버 N은 Game DB N에만 연결한다.
- 유저는 처음 입장할 때 배정받은 샤드에 영구 소속된다(07 문서 4장). 그 샤드의 Game 서버만 그 유저의 데이터를 쓴다.
- 다른 샤드 유저와 얽히는 일(우편, 보상, 방문 보상)은 상대 샤드의 Game 서버에 멱등 메시지를 보낸다(03 문서 3장). 던전과 PvP는 샤드와 상관없이 전투 서버 풀에서 같이 하고, 보상은 각자의 본 샤드로 돌아간다.
- 한 샤드에 Game 서버를 2대 이상 두는 방법은 06 클러스터 문서에서 정한다.

- **퍼블리셔 LoginDB에는 어떤 게임 서버도 붙지 않는다.** 게임은 퍼블리셔 A​PI(티켓 확인)로만 퍼블리셔와 대화한다(07 문서 2.5).
- **Gateway는 DB를 쓰지 않는다.** 게임 `login_token`은 Entry 서버가 서명해서 발급하고, Gateway는 서명만 검증한다. 접속 상태는 Redis(03 문서 9.4)에 있다.
- **전투 서버는 Game DB에 쓰지 않는다**(03 문서 3.4). 분석 로그는 다른 서버와 똑같이 파일에 쓰고, Fluent Bit가 어느 Log DB로 보낼지 정한다.
- Game 서버가 플레이어 디렉터리를 조회할 때는 Redis 캐시(`home:{player}`)를 먼저 보고, 없으면 **Entry 서버에 묻는다.** Game 서버는 Account DB에 직접 붙지 않는다(Account는 Entry 서버가 주인).

### 2.1 다른 샤드 DB에 붙지 않는 이유

- 플레이어 데이터의 주인은 그 플레이어의 본 샤드 플레이어 액터 하나다(03 문서 2장). 다른 서버가 그 DB를 직접 고치면 메모리 상태와 DB가 어긋난다.
- 샤드 간 일은 DB 직접 접근이 아니라 **멱등 메시지**로 한다(03 문서 3장). 2번 샤드 플레이어에게 보상을 주려면 2번 DB에 쓰지 않고 2번 서버에 `GrantItem`을 보낸다.
- 서버마다 모든 샤드 DB에 풀을 열면 PostgreSQL 커넥션이 금방 바닥난다.

## 3. 커넥션 풀

DB 전용 스레드 풀은 없다. `sqlx`는 비동기 드라이버라서 쿼리를 기다리는 동안 스레드가 멈추지 않는다. 동시 쿼리 수는 **커넥션 풀 크기**가 정한다(01 문서의 DB task, I/O 런타임 위에서 동작).

| C++ (블로킹 드라이버) | Rust + sqlx (비동기) |
|---|---|
| 쿼리를 기다리는 동안 스레드가 멈춤 → DB 스레드 풀 필요 | 기다리는 동안 스레드는 다른 일 → 커넥션 풀(`PgPool`)만 필요 |
| 동시 쿼리 수 = DB 스레드 수 | 동시 쿼리 수 = 커넥션 풀 크기 |

### 3.1 설정값 (출발값, 가정)

| 풀 | 서버당 크기 | 비고 |
|---|---|---|
| Game DB | 16 ~ 32 | 샤드당 Game 서버 수 × 풀 크기가 그 DB의 `max_connections` 안에 들어가야 함 |
| Common DB | 4 ~ 8 | 모든 Game 서버가 붙으므로 작게 |
| Account DB (Entry 서버) | 8 ~ 16 | 입장할 때만 쓰므로 크지 않음 |

| 항목 | 값 |
|---|---|
| 커넥션 빌리기 대기 한도 | 수 초. 넘으면 에러 + 지표 |
| 쿼리 타임아웃 | PostgreSQL `statement_timeout`으로 설정 |
| 서버 수가 많아지면 | **PgBouncer**(커넥션 공유 프록시)를 DB 앞에 둔다 |

- 같은 플레이어의 DB 작업 순서는 커넥션 풀이 아니라 **플레이어 액터**가 지킨다(01 문서 5.3: 액터는 명령 하나를 끝내야 다음 명령을 꺼내므로, 같은 플레이어의 트랜잭션이 동시에 돌지 않는다).
- 블로킹 라이브러리를 써야 하는 예외적인 경우에만 `tokio::task::spawn_blocking`을 쓴다. PostgreSQL + sqlx에는 해당하지 않는다.

### 3.2 DB마다 타입을 나눈다

풀을 `PgPool` 여러 개로 두면, 샤드 쿼리를 Common 풀로 보내는 실수도 컴파일된다. 그래서 DB마다 newtype으로 감싼다.

```rust
pub struct AccountDb(PgPool);
pub struct GameDb(PgPool);
pub struct CommonDb(PgPool);

pub async fn sell_item(db: &GameDb, ...) -> Result<SellOutcome, DbError>;   // GameDb만 받음
// sell_item(&ctx.common_db, ...)  → 컴파일 에러
```

- 서버 역할별 `ServerContext`(01 문서 8장)에는 **그 역할이 쓰는 DB 타입만** 들어간다. 전투 서버의 컨텍스트에는 `GameDb`가 없으므로, 전투 서버 코드에서 Game DB에 쓰는 코드는 컴파일되지 않는다.
- `db` 크레이트 안에서도 모듈을 DB별로 나눈다(`db::game`, `db::common`, `db::log`, `db::account`).

## 4. 마이그레이션

- DB 종류마다 마이그레이션 디렉터리를 따로 둔다: `migrations/account/`, `migrations/game/`, `migrations/log/`, `migrations/common/`.
- Game DB는 **모든 샤드에 같은 마이그레이션**을 적용한다. Log DB도 같은 스키마를 쓴다(Fluent Bit가 쓰는 JSONB 테이블 + 변환용 테이블). 샤드마다 스키마가 달라지지 않게 배포 도구가 전 샤드를 순서대로 올린다.
- `sqlx`의 컴파일 검사용 오프라인 데이터(`.sqlx/`)도 DB 종류별로 만든다.
- 스키마 변경은 무중단 배포를 위해 **추가 → 코드 전환 → 제거**의 단계로 나눈다(컬럼을 바로 지우거나 이름을 바꾸지 않는다).

## 5. Common DB의 쓰기 주인

Common DB는 전 서버가 공유하므로, **항목마다 쓰기 주인을 하나로** 정한다. 주인이 아닌 서버는 읽기만 하거나, 주인에게 메시지를 보낸다.

| 항목 | 쓰기 주인 | 비고 |
|---|---|---|
| **길드** (정보, 멤버, 직위, 길드 재화) | **길드 액터** (길드마다 하나) | 5.1 |
| 길드 던전 상태 | 길드 던전 InGameSpace의 host | 길드 액터의 허가를 받아 생성. 저장은 fencing 포함 (01 문서 6.4) |
| 친구 관계 | 친구 요청/수락을 처리하는 쪽 | 관계 한 행을 조건부 쓰기로 처리. 양쪽 플레이어에게 알림 |
| 샤드 간 거래 | **거래 서비스** | 03 문서 6.3 |
| 샤드 목록, 설정, 시즌, 공지 | 운영 도구 | 서버는 읽기만 |

### 5.1 길드 액터

- 길드 하나의 판정(가입, 탈퇴, 직위 변경, 정원, 길드 재화 사용, 길드 던전 생성 권한)은 **길드 액터 하나**가 Job 큐로 한 줄씩 처리한다. 파티 액터(03 문서 9.8)와 같은 방식이고, 차이는 상태가 **Common DB에 영구 저장**된다는 점이다.
- 길드 액터는 그 길드원 중 누군가가 접속해 있을 때 **아무 Game 서버에** 뜬다. 위치는 Redis에 `SET guild:{id} 서버 NX PX`로 적고 주기적으로 연장한다. InGameSpace 선점(03 문서 9.6)과 같은 방식이다.
- 길드 액터가 Common DB에 쓸 때도 **fencing 번호**를 붙인다(`INCR guild_epoch:{id}`로 받은 번호). 옛 서버에 남은 길드 액터의 늦은 쓰기는 DB가 거부한다.
- 길드원이 모두 나가면 액터는 저장 후 내려간다. 다음에 누가 접속하면 다시 뜬다.
- **길드 활동으로 플레이어 개인이 받는 보상**(길드 보상, 출석 보상 등)은 길드 액터가 정하고, 지급은 그 플레이어의 본 샤드에 멱등 메시지로 보낸다(03 문서 3장). 플레이어 인벤토리는 Common DB에 두지 않는다.

#### 5.1.1 길드 컨텐츠 범위 (소유자 결정, 2026-11-19)

| 항목 | 내용 | 저장 |
|---|---|---|
| 정원 | **약 30명** (설정값) | Common DB |
| 길드 창고 | **길드 재화와 아이템** 모두 넣고 꺼낼 수 있다. 꺼내기는 직위별 권한과 하루 한도로 제한하고, 넣고 뺀 기록을 모두 남긴다 | Common DB (창고, 입출금 기록) |
| 길드 타운 꾸미기 | 나중에 추가. 길드 전용 장소(InGameSpace)와 배치 데이터로 만든다 | Common DB |
| 길드 랭킹 | 길드 점수(영향력)를 길드 액터가 관리하고, 랭킹판은 Redis `rank:{board}`(03 문서 9.3)에 올린다. 점수의 정답은 Common DB | Common DB + Redis(표시용) |
| 길드원이 아무도 없을 때 생긴 일 | 가입 신청처럼 그때그때 생기는 일은 길드 액터를 잠깐 깨워 처리한다. 주간 정산처럼 시각이 정해진 일은 배치 작업이 처리한다 | - |

**창고에 아이템을 넣고 빼는 흐름.** 플레이어 인벤토리는 본 샤드 Game DB에, 창고는 Common DB에 있다. 두 DB를 한 트랜잭션으로 묶지 않고 03 문서 3장의 "한 단계에 DB 하나 + 멱등 메시지"를 따른다.

```
넣기: 플레이어 액터  ─ Game DB: 아이템 삭제 + outbox(멱등 키)  ──메시지──►  길드 액터 ─ Common DB: 창고에 추가 + 멱등 키
빼기: 길드 액터    ─ 권한·한도 확인, Common DB: 창고에서 삭제 + outbox  ──메시지──►  본 샤드 플레이어 액터 ─ Game DB: 지급
```

두 방향 모두 아이템은 "한 곳에서 빠진 뒤 다른 곳에 들어간다". 중간에 죽어도 outbox 재전송과 멱등 키로 결국 한 번만 들어간다.

### 5.2 길드 던전 배치 변경

길드가 특정 샤드에 속하지 않게 되었으므로, 길드 던전 InGameSpace의 host는 **"길드의 샤드"가 아니라 부하가 낮은 아무 Game 서버**로 정한다(03 문서 5장). 상태는 Common DB에서 로드하고 Common DB에 저장한다.

### 5.3 샤딩과 Common DB의 관계, 그리고 부하

**샤딩하는 것은 플레이어 개인 데이터다.** 인벤토리, 지갑, 퀘스트처럼 양이 많고 플레이어마다 독립적인 데이터는 Game DB에 나눠 담는다. 반대로 **여러 샤드의 플레이어를 잇는 관계(길드, 친구, 거래)**는 나눌 수 없으므로 Common DB 하나에 둔다. 샤딩한 게임에서 소셜과 거래만 전역으로 두는 것은 흔한 혼합 구조다.

길드, 친구, 거래가 모두 Common DB 하나에 모이므로, 동접이 커지면 이 DB가 먼저 병목이 될 수 있다.
- 처음에는 하나로 시작한다.
- 부하가 문제가 되면 **기능별로 먼저 떼어 낸다**(거래 테이블 → 별도 Trade DB, 길드 → 별도 Guild DB). 그래도 부족하면 **ID 기준으로 나눈다**(길드 ID, 친구 관계는 플레이어 ID). 데이터 ID가 UUID이고 테이블마다 쓰기 주인이 하나라서(5장) 나누기가 어렵지 않다.
- 거래는 재화가 걸리므로, Common DB를 나누더라도 **거래 테이블과 거래 서비스는 한 덩어리**로 움직인다.
