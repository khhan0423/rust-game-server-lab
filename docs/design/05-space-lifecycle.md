## 1. 장소 종류별 수명

| 종류 | 언제 뜨나 | 언제 내리나 | 저장 |
|---|---|---|---|
| 개인/커뮤니티 로비 | 주인이나 방문자가 들어올 때 | 아무도 없는 상태로 **언로드 유예**(L1)가 지나면 | 주기 저장 + 언로드 시 최종 저장 (01 문서 6.4) |
| MMO 필드 채널 1 | 서버 시작 시 | 내리지 않음 | 없음 (플레이어 상태만) |
| MMO 필드 채널 2 이상 | 기존 채널이 차서 새로 열 때 (3장) | 아무도 없는 상태로 **채널 유예**가 지나면 | 없음 |
| 길드 던전 | 개설(4장) 또는 길드원 입장 | 비면 언로드 유예 후 메모리에서 내림. **기간이 끝날 때까지 DB에는 남아 있다** | Common DB, fencing 포함 |
| 인스턴스 던전, PvP | 입장 시 전투 서버에서 생성 | 클리어, 이탈, 매치 종료 즉시 | 결과만 본 샤드로 |

## 2. 언로드 유예 (L1, L2)

### 2.1 "비었다"의 기준

- 접속이 끊겼지만 재접속을 기다리는 유저(Detached, 02 문서)는 **아직 안에 있는 것으로 센다.** 그 유저의 세션이 완전히 끝나야(재접속 유예 `resume_grace` 120초, 일부러 앱을 내린 경우 `suspend_grace` 600초, 세션 계약 문서) 그 장소에서 빠진다.
- 로비는 주인이 없어도 방문자가 있으면 비지 않은 것이다(L2).
- 마지막 사람이 빠진 순간부터 언로드 유예가 시작된다. 그동안 누가 다시 들어오면 유예를 취소한다.

### 2.2 왜 10분인가

모바일 회선이나 스팀 링크 같은 원격 플레이 환경에서는 연결이 자주 끊긴다. 유예가 짧으면 잠깐 끊겼다 돌아올 때마다 로비를 DB에서 다시 읽어야 한다. 로딩 화면이 길어지고 DB 부하도 생긴다. 10분은 `suspend_grace`(600초)와 같은 길이라, 앱을 잠깐 내렸다 돌아온 유저도 로비가 그대로 남아 있다.

메모리 비용: 잠든 InGameSpace는 틱을 돌지 않으므로(01 문서 4.6) 비용은 메모리뿐이다. 로비 하나의 크기와 유예 중인 로비 수는 지표로 보고(5장) 필요하면 설정을 줄인다.

### 2.3 서버가 메모리 압박을 받을 때

유예 중인 InGameSpace가 너무 많아 메모리 한도(설정값)를 넘으면, **유예가 가장 오래된 것부터** 앞당겨 내린다. 언로드 절차(최종 저장 → 커밋 확인 → Directory 키 삭제)는 같다.

## 3. MMO 필드 채널 (L3)

### 3.1 왜 채널이 필요한가

필드 하나는 존 스레드 하나, 즉 CPU 코어 하나가 처리한다. 한곳에 사람이 몰리면 처리량이 사람 수의 제곱으로 늘어나므로(서로에게 서로를 보여 줘야 하므로) **필드마다 정원이 있어야 한다.** 정원이 차면 같은 필드를 하나 더 띄우고(채널), 사람을 나눠 넣는다.

### 3.2 정원 두 단계

| 값 | 의미 | 기본값 |
|---|---|---|
| `soft_cap` | 이 이상이면 새로 오는 사람을 다른 채널로 보낸다. 파티원이나 친구를 따라오는 경우만 예외 | 필드별 설정 (부하 테스트 B 시나리오로 정함) |
| `hard_cap` | 이 이상은 누구도 못 들어온다. host가 입장을 거절한다 | `soft_cap`의 120% |

- 정원 숫자는 필드마다 기획 데이터 또는 설정으로 둔다. 처음 값은 부하 테스트에서 "틱 p99 50ms 이하"를 지키는 인원으로 정한다.

### 3.3 자동 배정 순서

입장하는 사람의 채널을 고를 때:

1. **파티원**이 있는 채널 (`hard_cap` 미만이면)
2. **친구**가 있는 채널 (`soft_cap` 미만이면)
3. `soft_cap` 미만인 채널 중 **가장 많이 찬 채널** (사람이 너무 흩어져 텅 빈 채널이 여럿 생기지 않게)
4. 모두 `soft_cap` 이상이면 **새 채널을 연다**

- 채널별 인원은 각 채널의 host가 주기적으로 Redis에 적는다: `HSET fieldpop:{shard}:{field} {channel} {인원}` (단일 명령, 03 문서 9.1). 입장시키는 쪽은 `HGETALL`로 읽고 고른다.
- 이 숫자는 몇 초 늦을 수 있다. 그래서 여러 명이 동시에 같은 채널을 고르면 조금 넘칠 수 있다. 진짜 상한은 **host가 `hard_cap`으로 판정**한다. 거절되면 다음 후보로 다시 고른다.
- 새 채널은 `MmoField(FieldId, Channel)` 키로 선점한다(01 문서 6.1). 두 서버가 동시에 "채널 3"을 열려고 해도 선점은 하나만 성공한다.

### 3.4 수동 이동

- 유저는 채널 목록(채널 번호와 혼잡도)을 보고 옮길 수 있다. 대상 채널이 `hard_cap` 미만이어야 한다.
- 전투 중 이동, 연속 이동을 막기 위해 **쿨다운**(설정값, 예: 30초)을 둔다.

### 3.5 채널 닫기

- 채널 1은 닫지 않는다.
- 채널 2 이상은 비면 **채널 유예**(설정값, 기본 5분) 뒤에 닫는다. 필드는 저장할 상태가 없으므로 그냥 내린다.
- 사람이 적은 채널을 강제로 합치지는 않는다. 사람이 빠지면 자연히 비고 닫힌다.

## 4. 길드 던전 (L4, L5)

### 4.1 개설

```
길드원 ──"길드 던전 열기"──> 본 샤드 플레이어 액터 ──> 길드 액터 (04 문서 5.1)
   길드 액터 판정: 이 사람이 길드장이거나 "길드 던전 개설" 권한이 있나?
                   지금 열린 길드 던전이 한도(L5) 미만인가?
                   개설 비용(길드 재화 등)이 있나?
   통과 → Common DB에 길드 던전 행 기록 (만료 시각 포함, 길드 재화 차감과 같은 트랜잭션)
       → 부하가 가장 낮은 Game 서버의 InGameSpaceManager에 생성 요청 (03 문서 5장)
```

- 권한은 길드 액터가 가진 **길드 직위와 권한 목록**으로 판정한다. "길드 던전 개설"을 길드장이 직위별로 줄 수 있는 권한 항목 하나로 둔다.
- 길드 재화 차감과 던전 행 기록은 같은 Common DB 트랜잭션이다(한 단계에 DB 하나, 03 문서 3장).

### 4.2 기간과 만료

| 종류 | 열리는 기간 | 예 |
|---|---|---|
| 요일 던전 | 그 요일에만 | 월요 던전, 화요 던전 ... |
| 상시 던전 | 항상 | |
| 주말 스페셜 던전 | 토요일과 일요일 이틀 | |

- 어느 요일에 어떤 던전이 열리는지, 각 던전의 내용은 기획 데이터가 정한다. 서버는 만료 시각을 개설 때 기획 데이터로 계산해 DB에 기록한다(예: 요일 던전은 그날 자정).
- 동시에 열린 던전 수는 종류와 상관없이 길드당 최대 5개다.

01 문서 6.5를 따른다. 만료 시각은 DB 값이 기준이고, 서버가 재시작돼도 유지된다. 메모리에서 내려가 있는 동안 만료되면 다음 입장 시도 때 거절하고, 정리는 배치 작업이 한다.
