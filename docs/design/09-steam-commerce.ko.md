## 1. 전체 구조

```
                       ┌───────────── 스팀 (Valve) ─────────────┐
                       │ 사용자 인증   인게임 구매   인벤토리    │
                       │ (UserAuth)   (MicroTxn)   (Inventory)  │
                       │                             장터       │
                       └───▲──────────────▲────────────▲─────────┘
                           │ HTTPS + 퍼블리셔 키 (서버에서만)
 클라이언트 ── Steamworks SDK (오버레이, 콜백)
     │
     │ (게임 패킷)
     ▼
  Gateway ─► 본 샤드 Game 서버 ── 플레이어 액터 ──메시지──► Commerce 서비스 ──► Commerce DB
                                   ▲                         │
                                   └──── GrantItem / Revoke ─┘ (멱등 메시지, outbox)
```

- **클라이언트는 스팀 Web API를 직접 부르지 않는다.** 퍼블리셔 키가 필요한 호출(지급, 회수, 주문 확정)은 반드시 서버에서 해야 한다(인벤토리 Web API 문서의 NOTE). 클라이언트가 쓰는 것은 Steamworks SDK의 오버레이(결제 승인 창)와 콜백뿐이다.
- **Commerce 서비스**는 03 문서 8장의 클러스터 서비스(거래 서비스 등)와 같은 종류다. async 서비스이고, 스팀 호출은 기다림이 대부분이라 액터 + `.await`로 처리한다(01 문서 5장과 같은 방식).
- **Commerce DB**는 주문과 스팀 아이템 작업 기록을 둔다. 플레이어의 본 샤드와 무관한 전역 데이터라 샤드 Game DB에 두지 않는다. 별도 DB로 둘지 Account DB 안의 스키마로 둘지는 S9에서 정한다.

### 1.1 로그인과의 관계

스팀 게임에서는 **스팀 계정이 곧 로그인 수단**이다.

1. 클라이언트가 `ISteamUser::GetAuthTicketForWebApi`로 티켓을 받는다.
2. 서버가 `ISteamUserAuth/AuthenticateUserTicket`으로 티켓을 확인하고 SteamID(64비트)를 얻는다.
3. 필요하면 `ISteamUser/CheckAppOwnership`으로 게임을 샀는지 확인한다.

이 흐름은 07 문서의 "퍼블리셔 Login 서버"를 대신하거나, 거기에 스팀을 로그인 수단 하나로 추가하는 형태가 된다. 07 문서는 모바일 전제(Guest, 기기 보관 비밀값)로 쓰여 있으므로 **스팀 전제로 고쳐야 한다**(S7, 소유자 승인 필요). 이 문서는 "계정에 SteamID가 연결돼 있다"는 것만 전제로 한다.

## 2. (A) 인게임 구매: 우리 상품을 스팀 지갑으로 판다

### 2.1 흐름

공식 문서의 순서를 우리 구조에 맞춘 것이다.

```
클라이언트          플레이어 액터           Commerce 서비스               스팀
1. 상점에서 구매 ──► 2. 상품, 가격 확인 ──► 3. 주문 생성 (Commerce DB)
                                              order_id(u64), 상태 Created
                                           4. InitTxn ───────────────────► 오버레이에 승인 창
                                              상태 InitSent
5. 오버레이에서 승인
6. MicroTxnAuthorizationResponse 콜백
   (order_id, 승인 여부) ──────────────────► 7. FinalizeTxn ──────────────► 결제 확정
                                              성공: 상태 Finalized
                                           8. 같은 트랜잭션에 outbox 기록:
                                              GrantItem{order_id 기반 멱등 키}
                     9. GrantItem 받음 ◄──── (커밋 후 전송)
                        Game DB에 지급(멱등 키와 같은 트랜잭션)
                        클라이언트에 결과
                                          10. 지급 확인 → 상태 Granted
```

- **5~6단계의 클라이언트 콜백은 신호일 뿐이다.** 결제가 정말 됐는지는 서버의 `FinalizeTxn` 성공으로만 판단한다. 클라이언트가 "승인했다"고 거짓말해도 `FinalizeTxn`이 실패하면 지급하지 않는다.
- **주문 번호는 64비트다.** 스팀이 64비트 Order ID를 요구하므로 UUID v7(128비트, 03 문서 7장)을 그대로 쓸 수 없다. Commerce DB의 시퀀스로 만든다.
- 가격은 서버가 정한다. 클라이언트가 보낸 가격은 쓰지 않는다. 사용자의 국가와 통화는 `GetUserInfo`로 얻는다.
- 개발 중에는 샌드박스(`ISteamMicroTxnSandbox`)를 쓴다. 실제 돈이 빠지지 않는다.

### 2.2 주문 상태

```rust
enum OrderState {
    Created,      // DB에 기록, 스팀 호출 전
    InitSent,     // InitTxn 성공, 사용자 승인 대기
    Finalized,    // FinalizeTxn 성공 = 돈이 빠짐. 이제 반드시 지급해야 함
    Granted,      // 본 샤드가 지급 완료를 확인함
    Failed,       // 거절, 취소, 시간 초과
    Reversed,     // 환불, 차지백 (2.4)
}
```

### 2.3 끊김과 장애 (가장 중요)

돈이 걸린 일이라 "중간에 끊기면?"을 단계마다 정한다.

| 끊긴 시점 | 상황 | 처리 |
|---|---|---|
| 4 이전 | 주문만 있음 | 일정 시간 후 `Failed` |
| 4~6 사이 | 사용자가 승인했는지 모름 (클라이언트 종료, 콜백 유실) | 일정 시간 뒤 `QueryTxn`으로 상태를 묻는다. `Approved`면 `FinalizeTxn`, 아니면 `Failed`. 공식 문서는 웹 결제에서 사용자가 돌아오지 않으면 포기하라고 하고, 인게임 결제의 경우는 명시하지 않는다. **샌드박스에서 동작을 확인한 뒤 확정한다** |
| 7 응답 전 | `FinalizeTxn`이 됐는지 모름 (타임아웃) | `QueryTxn`으로 확인한다. `Succeeded`면 `Finalized`로 진행 |
| 7 이후 | 돈은 빠졌고 지급 전 | outbox가 DB에 있으므로 재시작 후에도 재전송된다. 지급은 멱등 키로 한 번만 반영된다 |
| 9 실패 (본 샤드 장애) | 지급 메시지 미확인 | outbox 재전송. 03 문서 3장 규칙 그대로 |

정리하면 **`Finalized` 이후에는 무슨 일이 있어도 결국 지급된다**는 것이 이 설계의 약속이다.

### 2.4 환불, 차지백, 회수

- 스팀은 사용자 환불, 카드 분쟁(차지백), 사기 의심 환불을 `GetReport`의 상태 변화로 알려 준다. 공식 문서는 최소 하루 한 번, 길게는 1분마다 호출해도 된다고 한다. Commerce 서비스가 **5분마다** 호출한다(설정값).
- 상태가 `Refunded`, `PartialRefund`, `Chargedback`, `RefundedSuspectedFraud`, `RefundedFriendlyFraud`가 되면 주문을 `Reversed`로 바꾸고, 본 샤드에 **회수 메시지**(`Revoke{order_id}`, 멱등)를 보낸다.
- 공식 문서는 "가능하면 아이템을 회수하라"고 한다. **이미 써 버린 재화를 어떻게 할지**는 정책 문제다(S8).
- 우리가 직접 환불할 때는 `RefundTxn`을 쓴다. 운영 도구(08 문서 `/admin`)에서 Commerce 서비스로 요청한다.

## 3. (B) 스팀 아이템과 커뮤니티 장터

### 3.1 무엇이 가능한가 (공식 자료 기준)

- 아이템 종류(ItemDef)를 스팀웍스에 올린다. 각 정의에 `marketable`(장터 판매 가능), `tradable`(유저 간 교환 가능)을 켤 수 있다.
- 유저가 장터에서 팔면 **판매 대금은 판매자의 스팀 지갑으로 간다. 현금으로 출금할 수 없다**(장터 FAQ). 지갑 돈은 스팀에서 게임 등을 사는 데 쓴다. "돈이 들어온다"는 것은 이 의미다.
- 수수료(장터 FAQ): 구매자가 **스팀 수수료 5%**를 낸다. 여기에 **게임별 수수료**가 붙는데, 이것은 게임 퍼블리셔가 정하고 퍼블리셔가 가져간다. Valve 게임(TF2, Dota 2, CS2)은 10%다. **이 게임별 수수료가 우리 수익원이다.** 우리 게임의 수수료를 정하는 화면은 파트너 사이트 로그인 뒤에 있어 공개 문서로는 확인하지 못했다.
- 장터 참여 여부는 개발사가 정한다.
- 유저 쪽 제한(장터 FAQ): 7일 지난 구매 이력이 있어야 하고, Steam Guard를 15일 이상 켜 둬야 한다. 지갑 잔액은 약 2,000달러까지, 매물 하나는 약 1,800달러까지다.

### 3.2 정답 데이터의 주인이 바뀐다

이것이 이 기능의 핵심 쟁점이다.

- 스팀 아이템은 **스팀 서버에 있다.** 유저는 게임 밖(스팀 웹, 장터)에서 언제든 팔고, 교환하고, 받을 수 있다. 우리 서버는 그 순간을 알지 못한다.
- 그래서 "정답은 우리 DB"(03 문서, AGENTS.md)라는 원칙이 스팀 아이템에는 적용되지 않는다. 우리 DB에 있는 것은 **마지막으로 확인한 사본**이다.

| 구분 | 정답 | 우리 DB | 예 |
|---|---|---|---|
| 게임 아이템, 재화 | 우리 Game DB | 정답 | 무기, 방어구, 골드, 유료 재화 |
| 스팀 아이템 | 스팀 인벤토리 | 사본 (`steam_item_cache`) | 의상, 무기 외형, 탈것 외형, 이모트 |

### 3.3 스팀 아이템이 생기는 길

| 길 | 방법 | 비고 |
|---|---|---|
| 게임 플레이 보상 (서버가 결정) | Commerce 서비스가 `IInventoryService/AddItem` | `requestid`를 주면 **같은 요청은 한 번만 실행된다**(공식 문서). 우리 멱등 키를 그대로 쓴다 |
| 구매 | 스팀 아이템 상점(웹) 또는 인게임에서 `ISteamInventory` 구매 | 가격을 ItemDef에 넣는다. 이 경우 결제와 지급을 스팀이 한다 |
| 플레이 시간 드롭 | 클라이언트가 `TriggerItemDrop`, 확률과 빈도는 스팀이 관리 | 클라이언트를 믿지 않아도 되는 방식 |
| 장터, 교환 | 게임 밖 | 우리는 다음 동기화 때 안다 |

- 인게임 구매(2장)로 스팀 아이템을 팔 수도 있다. 그 경우 2장의 `GrantItem` 자리에 `AddItem`이 들어간다.

### 3.4 사본 동기화

- **로그인할 때** Commerce 서비스가 `GetInventory`로 전체를 읽어 사본을 갱신하고 플레이어 액터에 넘긴다.
- **게임 중에는** 일정 주기(예: 5분)와 아이템을 쓰는 순간(장착 화면 열기 등)에 다시 읽는다.
- 사본에서 사라진 아이템이 장착돼 있으면 다음 동기화 때 해제한다. 외형만이라면 이것으로 충분하다.
- 아이템을 소모시키는 일(강화 재료로 쓰기 등)은 `ConsumeItem`에 `requestid`를 붙여 서버가 한다. 스팀이 "이미 없다"고 하면 실패로 처리한다. 순서는 **스팀에서 먼저 소모 → 성공하면 게임 효과 적용**이다.

### 3.5 게임 아이템을 스팀 아이템으로 바꾸기 (선택)

"게임에서 얻은 아이템을 장터에 올리고 싶다"를 지원하려면, 게임 아이템을 스팀 아이템으로 **꺼내는** 기능이 필요하다.

```
1. 플레이어 액터: 게임 아이템 삭제 + outbox에 "스팀으로 꺼내기" 기록 (한 트랜잭션)
2. Commerce 서비스: AddItem(requestid = 그 멱등 키)
3. 성공하면 완료. 실패하면 재시도 (requestid 덕분에 두 번 생기지 않음)
```

반대 방향(스팀 아이템 → 게임 아이템)은 `ConsumeItem` 후 게임 아이템을 지급한다. 이 기능을 열면 **게임 경제가 현실 가치(지갑 돈)와 직접 연결된다.** 작업장, 매크로, 해킹의 목표가 되므로 S4처럼 범위를 좁히는 것을 권한다.

### 3.6 왜 외형만 권하는가 (S4)

- 스팀 아이템은 우리가 통제하지 못하는 곳에서 움직인다. 전투력 아이템이면 "장터에서 산 무기가 동기화 전까지 안 보인다", "판 무기를 동기화 전까지 계속 쓴다" 같은 문제가 바로 게임 밸런스 문제가 된다.
- 사냥으로 얻은 전투 아이템이 지갑 돈으로 바뀌면, 사냥 자체가 돈벌이가 되어 작업장이 몰린다.
- 외형만이면 동기화가 늦어도 "옷이 늦게 바뀐다" 정도로 끝난다.

| 테이블 | 내용 |
|---|---|
| `steam_orders` | `order_id`(u64, 시퀀스), `player_id`, `steam_id`, 상품, 금액(정수, 최소 단위), 통화, 상태, 스팀 `transid`, 시각들 |
| `steam_order_items` | 주문의 상품 목록 (스팀 Item ID는 우리 상품 번호, 32비트) |
| `steam_inventory_ops` | 스팀 인벤토리 작업 기록: 종류(AddItem/ConsumeItem), `requestid`, 대상, 상태 |
| `steam_report_cursor` | `GetReport`를 어디까지 읽었는지 |
| `outbox` | 본 샤드로 보낼 `GrantItem`, `Revoke` (03 문서 3장) |

### 4.2 Game DB 쪽 추가

- 지급 멱등 키(이미 있음, 03 문서)
- `steam_item_cache`: 플레이어별 스팀 아이템 사본과 마지막 동기화 시각

### 4.3 돈 표현

- 금액은 스팀 규칙대로 **최소 단위 정수**(센트 단위)로 저장한다. 실수 금지(가이드 4.4). 통화별로 소수점이 없는 통화가 있다(공식 문서 Supported Currencies).
- 금액 타입은 newtype으로 만든다(`MinorUnits(i64)` + `Currency`).

## 5. 보안

- 스팀 퍼블리셔 키는 Commerce 서비스만 가진다. 저장 위치는 08 문서 8장(비밀은 저장소 밖)을 따른다. 이 키가 새면 누구든 아이템을 만들어 낼 수 있다.
- 지급과 회수는 모두 서버가 결정한다. 클라이언트가 보낸 상품 번호, 가격, 결과 콜백은 신호로만 쓴다.
- 결제 관련 요청은 02 문서의 Reliable 등급과 멱등 키를 쓴다.
- 결제와 지급 내역은 거래성 로그로 Game DB에 남긴다(04 문서 1.1). CS 조회와 환불 대응에 쓴다.

## 6. 구현 순서 (나중에)

1. 스팀 로그인(티켓 확인) — 07 문서 수정과 함께
2. 인게임 구매, 샌드박스로 끝까지 (생성 → 승인 → 확정 → 지급)
3. `GetReport` 폴링과 회수
4. 스팀 아이템: ItemDef 몇 개, 로그인 시 동기화, 서버 지급(`AddItem`)
5. 장터 공개 (스팀웍스 경제 설정, 게임별 수수료 설정)
6. (선택) 게임 아이템 꺼내기
