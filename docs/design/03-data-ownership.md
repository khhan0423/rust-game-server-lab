## 1. 본 샤드와 호스트 샤드

| | 플레이어의 **본 샤드** (home) | InGameSpace의 **호스트** (host) |
|---|---|---|
| 의미 | 플레이어 데이터가 사는 곳 | InGameSpace가 돌아가는 곳 |
| 바뀌나 | **바뀌지 않는다** | InGameSpace마다 다르다 |
| 들고 있는 것 | 인벤토리, 재화, 장비, 퀘스트, 개인 진행도 | 위치, 전투 상태, 몬스터, InGameSpace 자체의 상태 |
| 서버 | Game 서버 (샤드) + Game DB | Game 서버(로비, 필드, 길드 던전) 또는 전투 서버(던전, PvP) |

### 1.1 존재(presence)는 대리 객체로 만든다

플레이어가 어떤 InGameSpace에 들어가면, 호스트에는 **전투용 대리 객체**가 생긴다. 대리 객체는 본 샤드 컨텐츠가 보내 준 **`CombatProfile`**로 만든다.

```rust
struct CombatProfile {
    player: PlayerId,
    home_shard: ShardId,       // 본 샤드. 보상과 결과를 돌려보낼 곳 (7.2)
    version: u64,              // 장비가 바뀔 때마다 증가 (4.2)
    stats: CombatStats,        // 장비, 버프 등을 반영한 최종 스탯
    visuals: EquipmentVisuals, // 외형
    // 전투 중 쓸 수 있는 정보만. 인벤토리 전체는 보내지 않는다
}
```

- **같은 서버의 InGameSpace에 들어갈 때도 똑같이 만든다.** 로컬과 원격을 구분하지 않으면 코드 경로가 하나가 되고, 샤드 간 플레이가 특별한 경우가 아니게 된다.
- 스탯 계산은 `game` 크레이트의 순수 함수 하나(`compute_combat_profile`)로 두고 **컨텐츠에서만** 호출한다. 존은 계산 결과만 받는다. 두 곳에서 계산이 어긋나지 않게 하기 위해서다.

## 2. 컨텐츠와 존의 분리

| | 컨텐츠 (Content) | 존 (Zone) |
|---|---|---|
| 다루는 것 | 인벤토리, 재화, 상점 구매, 우편, 퀘스트 보상 (길드 자체는 길드 액터, 04 문서 5.1) | 이동, 전투, HP, 몬스터, 루팅 판정, NPC 상호작용 |
| 성격 | **영구 데이터.** DB가 정답 | **일시적 시뮬레이션** |
| 위치 | 본 샤드 고정 | InGameSpace 호스트 (이동) |
| 실행 단위 | 플레이어 액터 (async, 01 문서 5장) | 존 스레드 (동기) |
| 메시지 카테고리 | Content (`0x1000` ~ `0x7FFF`) | Zone (`0x8000` ~ `0xFFFF`) |

클라이언트 메시지의 카테고리와 라우팅은 `02-session-network.md` 3.2를 따른다. Gateway가 Content 메시지는 본 샤드로, Zone 메시지는 현재 호스트로 보낸다.

### 2.1 판단의 주인을 쪼갠다

하나의 행동에 컨텐츠와 존이 모두 걸리는 경우가 있다(루팅, 장착). 이때는 **행동을 판단 단위로 쪼개고, 각 판단의 주인을 하나로** 정한다.

| 판단 | 주인 |
|---|---|
| 이 드롭을 누가 가져가나 (선착순, 파티 분배) | **존** |
| 지금 전투 중에 장착을 바꿔도 되나 (시전 중 금지 등) | **존** |
| 인벤토리에 자리가 있나, 이 아이템을 소유하고 있나 | **컨텐츠** |
| DB 기록 | **컨텐츠** (본 샤드 DB) |
| 장비 변경 결과를 전투에 적용 | **존** |

그래서 경계를 넘는 행동은 모두 **"존이 먼저 판단 → 컨텐츠가 확정(DB) → 존이 결과 적용"** 흐름이 된다.

## 3. 핵심 원칙: 한 단계에 DB 하나

### 3.1 규칙

1. **어떤 단계도 두 DB를 동시에 쓰지 않는다.** 분산 트랜잭션(2PC)은 쓰지 않는다.
2. 한 단계는 DB 하나에만 쓰고, 다음 단계는 **멱등 키가 붙은 메시지**로 넘긴다.
3. 메시지는 **보내기 전에 기록**하고(outbox), 상대의 확인을 받을 때까지 재전송한다.
4. 받는 쪽은 멱등 키로 중복을 걸러낸다. DB의 유니크 제약으로 보장한다.

금융 쪽으로 치면 분산 트랜잭션이 아니라 **사가(saga) + 전문번호(멱등 키) + 미송신 전문 재전송**이다.

### 3.2 공통 기반 (한 번만 만든다)

```
[공통 기반]  서버 간 전송(02 문서 4.4) + outbox + 멱등 처리
     │
     ├─ 한 방향 전달: 직접 메시지 (루팅, 보상, 방문자 보상, 우편 배달)
     │
     └─ 양방향 교환: 거래 서비스(중계자, 에스크로) + 위의 직접 메시지로 입금/지급
```

| 구성 요소 | 내용 |
|---|---|
| outbox | 보낼 메시지를 먼저 저장. DB가 있는 본 샤드는 DB의 outbox 테이블, DB가 없는 전투 서버는 메모리 outbox (유실 범위는 3.4) |
| 멱등 키 | 메시지를 만든 쪽이 생성. UUID v7 (7장) |
| 수신 처리 | 키를 DB에 기록하는 것과 효과를 반영하는 것을 **같은 DB 트랜잭션**으로. 이미 있는 키면 이전 결과를 그대로 회신 |
| 재전송 | 링크 재연결 후, 또는 일정 시간 확인이 없으면 같은 키로 재전송 |

### 3.3 한 방향과 양방향

| 흐름 | 예 | 중계자 | 이유 |
|---|---|---|---|
| **한 방향 전달** | 루팅, 던전 보상, 방문자 보상 | 필요 없음 | 주는 쪽이 이미 결정했고 받는 쪽은 받기만 하면 됨 |
| **양방향 교환** | 아이템 거래, 아이템 ↔ 재화 | **필요함** | "둘 다 되거나 둘 다 안 되거나"가 보장되어야 함 |

금융 비유: 한 방향 전달은 **일반 이체**, 양방향 교환은 결제기관을 통한 **DVP(Delivery Versus Payment)**.

### 3.4 DB가 없는 쪽(전투 서버)이 보내는 메시지 (확정: A + D, 보완 E)

전투 서버는 DB가 없고 상태가 메모리에만 있다. 조사한 방식(직접 전달, 큐 경유, DB 직접 기록, 결과만 전달, 우편함)을 비교한 뒤 아래 조합으로 정했다.

| 보상 종류 | 방식 | 경로 |
|---|---|---|
| **중요한 보상** (클리어 보상, 유료 재화, 시즌 보상) | **D. 결과만 보내고 본 샤드가 계산** | 전투 서버는 `DungeonResult { result_id, 클리어 여부, 기록 }`만 본 샤드에 보낸다. 본 샤드 플레이어 액터가 보상을 굴리고 DB에 지급한다 |
| **전투 중 드롭** (바닥 루팅) | **A. 직접 전달** | 전투 서버 → 서버 간 링크 → 본 샤드 플레이어 액터(`GrantItem`, 4.1) |
| 인벤토리가 가득 찼을 때 (중요한 보상) | **E. 우편함** | 본 샤드가 인벤토리 대신 우편으로 지급한다. 드롭은 기존대로 바닥에 되돌린다(4.1) |

**직접 전달(A)의 규칙**

- 전투 서버는 메시지를 만들면 즉시 보내고, 본 샤드의 확인을 받을 때까지 **메모리 outbox**에서 재전송한다.
- 모든 메시지에 멱등 키(`grant_id`, `result_id`)가 있어서, 재전송되어도 본 샤드 DB에서 한 번만 반영된다(3.2).
- 본 샤드가 재시작 중이라 닿지 않으면 전투 서버가 계속 들고 재시도한다. 링크가 복구되면 이어서 보낸다.

**남는 유실**

- 전투 서버가 확인을 받기 전에 죽으면 그 메시지는 사라진다. 이때는 던전 진행 자체가 사라지므로 **"던전 실패"로 처리**한다(입장권 반환 등은 운영 정책).
- 버그로 인한 드문 상황이라, 지금은 큐를 하나 더 거치는 비용을 들이지 않는다. 운영해 보고 유실이 실제로 문제가 되면 **Redis Streams 경유(9.9)를 켜는 선택지**를 남겨 둔다.

**DB 직접 기록(C)을 쓰지 않는 이유**

전투 서버가 플레이어 샤드 DB에 직접 쓰면, 플레이어 액터가 메모리에 들고 있는 인벤토리와 DB가 어긋난다. "플레이어 데이터의 주인은 본 샤드 플레이어 액터 하나"(2장)라는 원칙이 깨지므로 쓰지 않는다.

## 4. 경계를 넘는 흐름

### 4.1 루팅

```
클라 ──Loot(drop_id)──> 존 (InGameSpace 호스트. 전투 서버일 수 있음)
존:  드롭을 이 플레이어에게 "예약" (다른 사람이 못 가져가게)
존 ──GrantItem { grant_id, player, item, source }──> 플레이어의 본 샤드 컨텐츠
컨텐츠: 인벤토리 자리 확인 → DB 기록 (grant_id 유니크)
컨텐츠 ──GrantResult { grant_id, Ok | InventoryFull }──> 존
존:  Ok → 드롭 제거      InventoryFull → 예약 해제, 드롭을 되돌림
컨텐츠 ──InventoryChanged (Reliable)──> 클라
```

- 파티원이 서로 다른 샤드라면 `GrantItem`이 각자의 본 샤드로 따로 나간다.

### 4.2 장착과 해제 (존에서)

```
클라 ──Equip(item_id, slot)──> 존 (Zone 카테고리)
존:  전투 규칙 확인 (시전 중, 쿨다운, 장비 교체 금지 구역) → 안 되면 즉시 거절
존 ──EquipRequest { req_id, player, item_id, slot }──> 본 샤드 컨텐츠
컨텐츠: 소유 확인 → DB에 장착 변경 → compute_combat_profile
컨텐츠 ──CombatProfile { version, stats, visuals }──> 존
존:  version이 지금보다 새것이면 적용 (다음 틱부터 반영, 주변에 외형 브로드캐스트)
```

- 장착을 빠르게 여러 번 바꾸면 회신 순서가 섞일 수 있으므로, 존은 **더 새로운 version만** 적용한다.
- 존에서 구매한 아이템: 구매는 Content 메시지라 본 샤드에서 처리되고, 인벤토리에 들어온 뒤 장착은 위 흐름을 탄다. 클라이언트는 구매 응답을 받은 뒤 장착 요청을 보낸다(카테고리 사이 순서는 보장되지 않으므로, 02 문서 3.2).

### 4.3 지연이 문제 되는 경우: 임대(checkout)

위 흐름은 매번 서버 간 왕복이 필요하다. 같은 데이터센터라면 수 ms라서 루팅과 장착에는 충분하다. 빠른 PvP에서 소모품을 연타하는 경우처럼 지연이 실제로 문제 되면 **임대 방식**을 쓴다.

| | A. 본 샤드가 계속 주인 (기본) | B. 입장할 때 일부를 존에 임대 |
|---|---|---|
| 방식 | 매번 본 샤드에 확정 요청 | 입장 시 소모품 N개를 존에 체크아웃. 존이 로컬에서 차감하고, 퇴장할 때 정산 |
| 지연 | 서버 간 왕복 | 없음 |
| 장애 시 | 단순. 멱등 키로 재시도 | 정산 규칙 필요 (임대 만료, 미정산 복구) |
| 금융 비유 | 건별 승인 | 가승인(홀드) 후 정산 |

**A를 기본으로 하고, 측정해서 지연이 문제 되는 항목만 B로 처리한다.**

## 5. InGameSpace 배치 규칙

**영구 상태가 있는 InGameSpace는 그 상태의 주인 샤드에, 일회성 InGameSpace는 전투 서버 풀에** 둔다.

| InGameSpace | 호스트 | 이유 |
|---|---|---|
| 로비 | **주인의 샤드** 고정 | 로비 상태가 주인 DB에 저장됨 (데이터 지역성) |
| 길드 던전 | **부하가 낮은 Game 서버** | 길드는 샤드에 속하지 않고 Common DB에 있음. 상태는 Common DB에서 로드하고 저장 (04 문서 5장) |
| MMO 필드 | 각 샤드 (채널) | 샤드별 공용 필드. 다른 샤드 플레이어는 **친구를 따라가는 경우만** 친구가 있는 채널로 입장 (O10) |
| 인스턴스 던전 | **전투 서버 풀** (파티 구성과 무관하게 항상) | 일회성. 상태 저장 없음 |
| PvP 필드 | **전투 서버 풀** | 일회성 |

**모든 인스턴스 던전을 풀에서 돌리는 이유.** "같은 샤드 파티는 샤드에서, 섞인 파티는 풀에서"로 나누면 경로가 둘이 되고, 드물게 타는 경로에 버그가 숨는다. 항상 풀에서 돌리면 샤드를 넘는 경로(루팅, 장착 메시지)가 **매일 모든 던전에서 쓰이므로** 늘 검증된 상태가 된다. 전투 부하도 샤드와 분리되어 풀만 늘려서 대응할 수 있다. 대가는 같은 샤드 파티도 서버 간 메시지를 쓴다는 것인데, 같은 데이터센터 안이라 체감되지 않는다.

InGameSpace를 찾고 배치하는 일은 클러스터 단위가 된다("친구 로비가 어느 서버에 떠 있나"). 그래서 **클러스터 단위 Directory(Redis의 `space:{key}`, 9.6) + 프로세스 안 InGameSpaceManager**의 2층 구조다. 상세는 05(공간 수명), 06(클러스터) 문서에서 다룬다.

## 6. 샤드 간 기능

### 6.1 섞인 파티 던전

5장의 배치 규칙으로 해결된다. 파티원 각자의 본 샤드가 전투 서버로 `CombatProfile`을 보내고, 루팅과 보상은 각자의 본 샤드로 돌아간다.

### 6.2 다른 샤드 친구의 로비 방문과 기여

로비는 주인의 샤드에서 돈다. 방문자의 행동 하나를 **조각으로 나눠** 각 조각을 주인 DB 하나에만 쓴다.

| 방문자의 행동 결과 | 기록되는 곳 | 방식 |
|---|---|---|
| 로비 상태 변경 (예: 주인의 농장을 도와줌) | **주인의 DB** | 로컬 쓰기 (로비가 주인 샤드에서 돌기 때문) |
| 방문자 개인 보상, 퀘스트 진행 | **방문자의 DB** | 멱등 메시지로 방문자 본 샤드에 (4.1과 같은 흐름) |
| 로비에서 아이템 줍기 | 방문자의 DB | 4.1 루팅 흐름 |

- 로비 상태가 **정답이고 먼저** 기록된다. 방문자 보상은 그 결과로 **나중에, 확실히** 도착한다. 둘이 원자적일 필요는 없다.
- **방문자 권한 (확정: 주인이 방문자별로 설정)**
  - 기획은 **가능한 권한 항목**(예: 도와주기, 채집, 수확, NPC 대화)과 **새 방문자의 기본값**을 정의한다.
  - 로비 주인은 방문자(친구)마다 항목을 켜고 끈다. 설정은 로비 상태의 일부로 **주인의 DB**에 저장한다.
  - 서버는 방문자의 행동마다 `(방문자, 권한 항목)`을 검사한다. 설정이 없는 방문자는 기본값을 따른다.
  - 주인이 방문 중에 권한을 바꾸면 로비 InGameSpace에 즉시 반영된다. 로비가 주인 샤드에서 돌고, 설정도 같은 곳에 있기 때문이다.

### 6.3 샤드 간 아이템 거래

두 샤드 DB를 한 번에 바꾸지 않는다. **거래 서비스(클러스터 서비스. 거래 상태는 Common DB의 거래 테이블, 04 문서 D7)**가 중계자(에스크로)가 된다.

```
1. A의 본 샤드:  A의 물건을 "거래 보관"으로 이동 (A의 DB만)  ──Deposit(trade_id)──> 거래 서비스
2. B의 본 샤드:  B의 물건을 "거래 보관"으로 이동 (B의 DB만)  ──Deposit(trade_id)──> 거래 서비스
3. 거래 서비스:  양쪽 입금 확인 → "체결" 기록 (Common DB의 거래 테이블만)
4. 거래 서비스 ──Deliver(trade_id)──> A의 본 샤드: B의 물건을 A에게 (A의 DB만)
               ──Deliver(trade_id)──> B의 본 샤드: A의 물건을 B에게 (B의 DB만)
   취소 또는 시간 초과 → 각자에게 자기 물건을 반환 (Return)
```

거래 상태 기계 (Common DB의 거래 테이블에 기록):

```
Open ──양쪽 Deposit──> Settled ──양쪽 Deliver 확인──> Completed
  │
  └─취소, 시간 초과──> Cancelling ──입금분 Return 확인──> Cancelled
```

- 모든 메시지에 `trade_id`가 붙어 재전송해도 한 번만 반영된다.
- 서버가 죽어도 재시작 후 거래 테이블의 상태에서 이어서 진행한다. 거래 이력은 CS 대응 근거가 된다.
- 지급(Deliver)을 **우편 배달**로 구현하면 거래, 경매장, 운영자 보상 지급이 같은 배달 장치를 쓴다.

### 6.4 구현 순서

공통 기반(3.2) → 섞인 파티 던전(6.1) → 로비 방문(6.2) → 거래(6.3). 거래는 마지막에 구현하지만, 설계는 지금 이 원칙으로 확정한다.

## 7. 전역 ID (확정: UUID)

샤드를 넘나드는 ID가 샤드 DB의 자동 증가 값이면, 1번 샤드의 플레이어 100번과 2번 샤드의 플레이어 100번이 같은 InGameSpace에서 충돌한다. 그래서 **데이터 ID는 UUID**로 한다.

| ID | 형식 |
|---|---|
| `PlayerId`, `GuildId`, `AccountId`, `CommunityId` | **UUID v7** |
| 아이템 인스턴스 ID (거래로 샤드를 넘을 수 있음) | **UUID v7** |
| 멱등 키 (`grant_id`, `trade_id`, `req_id`) | **UUID v7** |
| `SessionId`, `ConnId`, `ServerId` (인프라 ID, 데이터가 아님) | 기존대로 (02 문서 2.1, 4.4) |

### 7.1 UUID v7을 쓰는 이유

- UUID에는 여러 버전이 있다. 완전 무작위인 **v4**는 DB 인덱스에 무작위 위치로 삽입되어 페이지 분할이 잦고 쓰기 성능이 떨어진다.
- **v7**은 앞부분이 생성 시각(밀리초)이라 **시간 순으로 증가**한다. 자동 증가 키처럼 인덱스 끝에 붙으므로 UUID의 인덱스 성능 단점이 크게 줄어든다. 생성 시각을 ID에서 바로 읽을 수 있어 운영 조회에도 쓸모가 있다.
- Rust `uuid` 크레이트가 v7 생성을 지원한다. 13장 의존성 목록에 추가한다.
- DB에는 문자열이 아니라 **16바이트 이진값**으로 저장하고, 패킷(Protobuf)에서도 `bytes`(16바이트)로 보낸다. 사람이 읽는 로그에만 문자열 형식을 쓴다.

### 7.2 UUID를 고르면서 생기는 일: 본 샤드를 ID로 알 수 없다

샤드 번호를 ID에 넣는 방식과 달리, UUID만 보고는 그 플레이어의 본 샤드를 알 수 없다. "이 보상을 어느 샤드로 보내나"를 다른 곳에서 알아내야 한다.

| 상황 | 본 샤드를 아는 방법 |
|---|---|
| 접속 중인 플레이어 (대부분의 경우) | 로그인할 때 정해져서 계속 들고 다닌다. Gateway는 `Routes.content`(02 문서 3.2), InGameSpace는 `CombatProfile.home_shard`(1.1) |
| 오프라인 플레이어에게 보내기 (우편, 거래 지급, 길드 보상) | **플레이어 디렉터리**(8장): `PlayerId → 본 샤드` 조회. 정답은 게임 Account DB(Entry 서버 소유)이고 Redis 호환 저장소에 캐시한다(`home:{player}`, 9.3) |

- 플레이어 디렉터리는 캐릭터를 만들 때 한 번 기록하고, 서버 이전이나 통합 때만 바뀐다. 읽기가 대부분이라 캐시가 잘 맞는다.
- 장점도 있다. 서버 통합이나 캐릭터 서버 이전을 해도 **ID가 바뀌지 않는다.** 플레이어 디렉터리의 값만 바꾸면 된다.

## 8. 클러스터 서비스

샤드 하나가 볼 수 없는 것은 샤드 밖에서 다룬다. Redis 호환 저장소(9장)를 "공용 게시판"으로 쓰고, **판정은 우리 액터가, 정답은 DB가** 맡는다. 별도 서비스 프로세스는 최소로 둔다.

| 기능 | 판정하는 곳 | Redis에 적는 것 | 정답 |
|---|---|---|---|
| InGameSpace Directory | host 서버의 **InGameSpaceManager 액터** | 누가 host인가 (`space:{key}`), fencing 번호 (9.6) | Redis (일시 상태) |
| 서버 등록과 발견 | 각 서버 자신 | 살아 있는 서버 목록 (9.7) | Redis (일시 상태) |
| 계정 디렉터리 (중복 로그인) | 새 Gateway의 **세션 처리 코드** (`SET ... GET`으로 받은 옛 값을 보고 판단) | 계정이 어느 Gateway, 어느 세션에 있나 (9.4) | Redis (일시 상태) |
| 플레이어 디렉터리 (`PlayerId → 본 샤드`) | Entry 서버 | 캐시 (7.2) | **게임 Account DB** (04 문서, 07 문서 6장) |
| 길드 | **길드 액터** (길드마다 하나, 04 문서 5.1) | 길드 액터가 어느 서버에 있나 | **Common DB** |
| 파티 | **파티 액터** (파티를 만든 서버에 하나) | 파티 액터가 어느 서버에 있나 (9.8) | 파티 액터의 메모리 (일시 상태) |
| 친구 관계 | 본 샤드 컨텐츠 | 온라인 표시만 | **DB** |
| 채팅 | - | Pub/Sub 채널 (9.8) | 일반 채팅은 없음(휘발). 보관이 필요한 것은 DB |
| 매치메이킹, 로그인 대기열 | 매칭 액터 / Gateway | 정렬 집합 (9.8) | Redis (일시 상태) |
| 거래 서비스 (샤드 간 교환) | **서비스 프로세스** (6.3) | - | **Common DB** 거래 테이블 (04 문서 D7) |

정답이 DB에 있어야 하고 상태 기계가 긴 거래만 서비스 프로세스로 남긴다. 나머지는 Game 서버와 Gateway 안의 코드(액터)로 존재한다.

## 9. 공유 키-값 저장소 (Redis 호환): 공용 게시판

- 상태: **확정** (2026-11-18). Lua 스크립트를 쓰지 않는 방식으로 정리했다.

### 9.0 한 줄 정의

**Redis는 모든 서버가 같이 보는 게시판이다.** 사실을 적어 두고 같이 보며, 적은 쪽이 죽으면 글이 TTL로 저절로 지워진다. 줄 세우기(정렬 집합)와 여러 서버에 뿌리기(Pub/Sub) 같은 자료구조를 덤으로 쓴다.

| 층 | 맡는 것 | 하는 곳 |
|---|---|---|
| **판정** | 누가 이기나, 정원이 찼나, 상태 전이 | **우리 액터** (세션 액터, 파티 액터, InGameSpaceManager 등) |
| **정답** | 재화, 아이템, 인벤토리, 거래, outbox, 멱등 키 | **DB** |
| **정합성 보장** | 중복 반영 방지, 옛 주인의 늦은 쓰기 차단 | **DB** (멱등 키, fencing 번호) |
| **공유 사실** | "어디 있나", 잠깐 맡겨 둔 데이터, 대기열, 알림, 캐시 | **Redis** |

Redis가 없어도 이 설계는 성립한다. 그 경우 주소록, 대기열, 랭킹, 채팅 중계, 세션 보관을 서비스로 직접 만들고 각각의 이중화를 직접 구현해야 한다. Redis는 그 여러 서비스를 이미 검증되고 이중화가 되는 부품 하나로 대신한다(build vs buy).

제품(Redis 8.x 또는 Valkey)은 운영 단계에서 정한다(O13). 우리가 쓰는 명령은 둘 다 같다.

### 9.1 원칙

1. **정답으로 쓰지 않는다.** Redis의 디스크 기록(AOF)은 보통 1초 단위라 장애 시 마지막 1초가 사라질 수 있고, 복제가 비동기라 장애 조치 때 직전 기록이 없을 수 있다.
2. **판정을 Redis 안에서 하지 않는다. 단일 명령만 쓴다.** Lua 스크립트와 `MULTI`/`EXEC`는 쓰지 않는다. "읽고, 판단하고, 쓰기"가 필요하면 그 판정의 주인인 **액터**가 한다.
   - 이유: Lua 스크립트는 실행 중 Redis 전체를 멈추고, 중간 에러에 롤백이 없고, Lua 엔진 자체의 보안 취약점 이력이 있다(예: CVE-2025-49844). 판정을 Rust 액터에 두면 컴파일러의 도움을 받고 Redis 없이 테스트할 수 있다.
   - 쓰는 명령: `GET`, `SET`(`NX`, `GET`, `PX` 옵션), `DEL`, `PEXPIRE`, `INCR`, 해시, 리스트, 정렬 집합(`ZADD`, `ZPOPMIN` 등), Pub/Sub. 모두 명령 하나가 원자적이다.
3. **Redis의 값이 사라져도 더 보수적인 경로로 떨어지게** 설계한다. 세션 미러가 없으면 Replay 대신 Resync, 공간 임대가 사라지면 DB에서 다시 로드한다.
4. **모든 키에 TTL 또는 명시적 삭제 경로가 있다.** 주인이 죽으면 키도 결국 사라진다.
5. **두 단계 명령 사이의 좁은 틈은 DB가 막는다.** 예: 임대 연장(`GET` 확인 후 `PEXPIRE`) 사이에 주인이 바뀌는 경우. 데이터 쓰기에는 fencing 번호를 붙이고 DB가 옛 번호의 쓰기를 거부한다(9.6).

### 9.2 Redis가 하는 일

| # | 역할 | 쓰는 곳 |
|---|---|---|
| 1 | **"어디 있나" 공용 주소록** (TTL로 자동 정리) | 계정의 접속 위치, 세션의 현재 Gateway, InGameSpace의 host, 파티 액터의 위치, 살아 있는 서버 목록 |
| 2 | **서버 사이에 잠깐 맡겨 두는 데이터** | 세션 미러 (Reliable 재전송 버퍼) |
| 3 | **줄 세우기, 순위** (정렬 집합) | 매치메이킹 대기열, 로그인 대기열, 랭킹 |
| 4 | **여러 서버에 한 번에 뿌리기** (Pub/Sub) | 채팅, 친구 접속 알림 |
| 5 | **캐시** | 플레이어의 본 샤드, 온라인 표시, 다른 샤드 플레이어 프로필 |

### 9.3 키 목록

| 키 | 값 | TTL / 삭제 | 용도 (절) |
|---|---|---|---|
| `online:{account}` | `{gateway, session}` | Gateway가 주기적으로 갱신 | 중복 로그인 (9.4) |
| `sess:{session}:owner` | 지금 세션을 가진 Gateway | 유예 시간 + 여유 | 세션 이어받기 (9.5) |
| `sess:{session}` | `{routes, last_server_seq, last_client_seq, ...}` | 위와 같음 | 세션 미러 (9.5) |
| `rbuf:{session}` | 리스트: 미확인 Reliable 프레임 (원래 seq 포함) | 위와 같음. ACK 시 앞에서 제거 | 세션 미러 (9.5) |
| `space:{key}` | `{host, epoch}` | host가 주기적으로 연장 (임대) | InGameSpace Directory (9.6) |
| `space_epoch:{key}` | 정수 (fencing 번호) | 삭제하지 않음 (단조 증가) | 옛 host의 늦은 쓰기 차단 (9.6) |
| `server:{id}` | `{role, addr, load, state}` | 서버가 주기적으로 갱신 | 서버 등록과 발견 (9.7) |
| `home:{player}` | 본 샤드 | 캐시 TTL | 플레이어 디렉터리 캐시 (7.2) |
| `presence:{player}` | 접속 여부, 위치 요약 | 짧은 TTL, 갱신 | 친구 온라인 표시 |
| `party:{party}` | 파티 액터가 있는 서버 | 파티 액터가 주기적으로 연장 | 파티 위치 (9.8) |
| `mm:{queue}`, `loginq:{shard}` | 정렬 집합 | 항목별 만료 정리 | 매치메이킹, 로그인 대기열 (9.8) |
| `rank:{board}` | 정렬 집합 | 시즌 종료 시 삭제 | 랭킹 (원천 점수는 DB) |
| `bsout:{shard}` | Streams | 소비 확인 후 정리 | (선택 사항) 전투 서버 보상 outbox (9.9) |

키 이름 앞에는 환경과 클러스터 접두사(예: `live:c1:`)를 붙인다.

### 9.4 중복 로그인: `SET ... GET` 명령 하나

```
새 로그인 → 새 Gateway:
  SET online:{account} "{내 gateway, 새 session}" GET PX 30000
    → 새 값을 쓰면서 옛 값을 돌려받는다 (원자적, 명령 하나)
  옛 값 없음 → 처음 접속
  옛 값 있음 → 옛 Gateway에 Kick (서버 간 링크) → 02 문서 3.1의 중복 로그인 절차
```

- 늦게 도착한 옛 처리(예: 옛 Gateway가 뒤늦게 보낸 정리 요청)는 **SessionId를 비교해서** 걸러낸다. 새 로그인마다 SessionId가 새로 생기므로 별도 번호가 필요 없다.
- Gateway는 접속 중인 계정의 키 TTL을 주기적으로 연장한다. 옛 Gateway가 죽으면 키는 TTL로 사라진다.
- Redis 장애 조치 중 마지막 기록이 사라지면 아주 드물게 판정이 틀릴 수 있다. 그래도 Player는 Game 서버에 하나만 존재하고 인계는 Player가 있는 서버를 거치므로 **캐릭터가 둘로 복제되지는 않는다.** 최악의 경우는 옛 기기가 늦게 끊기는 정도다.

### 9.5 세션 미러: 아무 Gateway로나 재접속

세션 정보와 **Reliable 재전송 버퍼**를 Redis에 맡겨 둔다. 원래 Gateway가 죽었거나 줄어들어도(스케일 인) 다른 Gateway가 세션을 이어받아 **Replay**할 수 있다. Reliable은 구매, 보상 같은 드문 메시지라서(02 문서 7.1) Redis 쓰기량이 작다.

**기록 순서 (먼저 Redis, 그다음 전송):**

| 방향 | 순서 | 이유 |
|---|---|---|
| 서버 → 클라 Reliable | Gateway가 seq를 매김 → `rbuf`에 추가 → **그다음** 클라이언트로 전송 | 클라이언트가 볼 수 있었던 프레임은 모두 Redis에 있으므로 다른 Gateway에서도 빠짐없이 Replay 가능 |
| 클라 → 서버 Reliable | Gateway가 받음 → `sess.last_client_seq` 갱신 → **그다음** 백엔드로 전달 | 다른 Gateway에서 재개해도 이미 처리한 요청을 다시 넘기지 않음 |
| ACK 수신 | `rbuf`에서 그 seq까지 제거 | 버퍼 크기 유지 |

Volatile 메시지는 Redis에 쓰지 않는다.

**다른 Gateway에서 재개:**

```
Client ──Resume(session_key, last_server_seq)──> Gateway G2
G2: SET sess:{session}:owner G2 GET   → 옛 주인 G1을 돌려받음 (명령 하나)
G2 ──Superseded(session)──> G1        (서버 간 링크. G1이 이미 죽었다면 생략)
G1: 자기 쪽 세션 액터를 Superseded로 정리 (커넥션 닫기, 메모리 버퍼 폐기)
G2: rbuf에서 last_server_seq + 1부터 꺼내 Replay. 빠짐이 있으면 Resync
G2 ──SessionResumed { gateway: G2, mode }──> 백엔드 (PlayerLink 주소 갱신)
```

- 원래 Gateway로 재접속한 경우는 메모리에서 바로 Replay한다. Redis는 **다른 Gateway로 왔을 때**와 **원래 Gateway가 죽었을 때**를 위한 것이다.
- `session_key` 검증도 `sess` 키로 하므로 어느 Gateway든 검증할 수 있다.

### 9.6 InGameSpace Directory: 선점, 임대, fencing

"어느 InGameSpace가 어느 서버에 있나"는 `space:{key}`에 적는다. **수명 상태(Loading / Active / Unloading)와 입장 대기열은 host 서버의 InGameSpaceManager 액터가 메모리에 들고 판정한다**(01 문서 6장). Redis에는 "누가 host인가"만 있다.

| 동작 | 명령 |
|---|---|
| **선점** | ① `INCR space_epoch:{key}`로 fencing 번호를 받는다 ② `SET space:{key} "{내 서버, 번호}" NX PX 15000`. 성공하면 내가 host. 실패하면 이미 host가 있으므로 `GET`으로 host를 읽어 그쪽으로 입장 요청을 넘긴다 |
| **임대 연장** (host가 5초마다) | `GET space:{key}` → 내가 맞으면 `PEXPIRE space:{key} 15000` |
| **해제** (언로드 저장이 DB에 커밋된 뒤) | `GET space:{key}` → 내가 맞으면 `DEL space:{key}` |
| **입장 요청** | `GET space:{key}` → 있으면 host로, 없으면 선점부터 |

- **host가 죽으면** 연장이 끊겨 키가 TTL로 사라지고, 다음 입장 요청이 다른 서버에서 선점해 DB로부터 다시 로드한다.
- **연장 확인에서 다른 주인이 보이면** host는 그 InGameSpace의 새 입장을 즉시 멈추고 플레이어를 정리한다. Redis에 닿지 않아 연장에 실패해도 새 입장을 멈춘다(9.10).
- `INCR`로 번호만 받고 선점에 실패하면 번호가 하나 비지만 문제없다. 번호는 커지기만 하면 된다.

**fencing: 좁은 틈은 DB가 막는다**

임대 연장과 해제는 `GET`과 `PEXPIRE`/`DEL` 두 명령이다. 그 사이에 키가 만료되고 다른 서버가 선점하는 **아주 좁은 틈**이 있다. 이 틈이 생기려면 host가 15초 가까이 멈추거나 네트워크에서 끊겨야 한다. 이 경우에도 데이터가 망가지지 않게 한다.

- host는 InGameSpace 상태를 DB에 저장할 때 **자기 fencing 번호**를 함께 보낸다.
- DB는 InGameSpace마다 마지막으로 받은 번호를 기록하고, **그보다 낮은 번호의 저장을 거부**한다(조건부 `UPDATE ... WHERE epoch <= $mine`, 영향받은 행이 0이면 거부. 가이드 8장).
- 그래서 옛 host가 남아 있어도 그 저장은 버려진다. 최악의 경우 몇 초 동안 두 서버에 같은 로비가 보이는 정도이고, 데이터는 새 host의 것만 남는다.
- 금융 쪽 감각으로 말하면, **정합성은 DB가 지키고 Redis는 "누가 담당인가"만 알려 준다.**

### 9.7 서버 등록과 발견

- 모든 서버는 시작할 때 `server:{id} = {role, addr, load, state}`를 기록하고 주기적으로 갱신한다(TTL). `state`는 `Active` 또는 `Draining`이다.
- Gateway는 이 목록을 보고 백엔드에 연결하고, 백엔드끼리도 이 목록으로 서버 간 링크를 맺는다(02 문서 4.4).
- 서버가 죽으면 TTL로 목록에서 빠진다. 스케일 아웃은 "새 서버를 띄우면 자동 등록"이다.
- 스케일 인은 `state = Draining`으로 바꿔 새 배치를 막고, 기존 InGameSpace를 정리한 뒤 종료한다(06 문서).

### 9.8 파티, 채팅, 대기열

| 기능 | 방법 |
|---|---|
| **파티** | 파티를 만든 서버에 **파티 액터** 하나가 생긴다. 초대, 수락, 탈퇴, 파티장 위임, 정원 검사는 모두 이 액터의 Job 큐에서 한 줄로 판정한다. Redis에는 `SET party:{id} 서버 NX PX`로 위치만 적고 액터가 주기적으로 연장한다. 액터가 있는 서버가 죽으면 파티는 해산되고 멤버들에게 알린다(파티는 일시 상태) |
| 온라인 표시 | `presence:{player}` TTL 키. 친구 목록(DB)과 조합해 보여 준다 |
| 채팅 | 채널별 Pub/Sub. 각 Gateway가 자기 세션이 속한 채널만 구독해서 전달. 놓쳐도 되는 메시지만. 귓속말 보관, 신고용 기록은 DB |
| **매치메이킹** | `mm:{queue}` 정렬 집합에 `ZADD`(점수 = 대기 시작 시각 또는 MMR). **매칭 액터**가 꺼내서(`ZPOPMIN`은 명령 하나라 여러 곳에서 꺼내도 같은 항목이 두 번 나오지 않음) 매치를 만들고, 전투 서버에 PvP InGameSpace를 선점한다(9.6). 매칭 규칙(MMR 범위 확장, 파티 단위, 지역)은 매칭 액터의 코드로 바꾼다. 샤드와 무관한 **전역 매칭**이다 |
| 로그인 대기열 | 동접 상한을 넘으면 `loginq:{shard}`에 `ZADD`하고 순번(`ZRANK`)을 알려 준다. 자리가 나면 앞에서부터 입장 |

### 9.9 (선택 사항) 전투 서버 보상 outbox: Redis Streams

**기본으로는 쓰지 않는다.** 전투 서버 보상은 본 샤드 플레이어 액터로 직접 전달하는 것이 기본이다(3.4). 운영 중 전투 서버 장애로 인한 보상 유실이 실제로 문제가 될 때 켜는 선택지다.

켜면: 전투 서버가 본 샤드로 보낼 메시지(`GrantItem`, `DungeonResult`)를 **먼저 Redis Streams `bsout:{본 샤드}`에 기록**하고, 본 샤드가 소비자 그룹으로 읽어 간다. Streams는 "최소 한 번" 전달이므로, 본 샤드는 멱등 키로 DB에서 중복을 걸러낸다(3.2).

### 9.10 Redis가 멈췄을 때

Redis는 **이중화 구성(Sentinel 또는 Cluster)이 필수**다. 그래도 멈추는 경우의 기본 방침은 **"새로 시작하는 것은 막고, 진행 중인 플레이는 유지한다"**이다. 판정과 정답이 Redis에 없으므로 진행 중인 플레이는 영향을 받지 않는다.

| 기능 | Redis가 멈추면 |
|---|---|
| 새 로그인 (9.4) | **거절.** "잠시 후 다시 시도" 안내 |
| 재접속 (9.5) | 원래 Gateway로 온 재접속은 메모리로 처리. 다른 Gateway로 온 재접속은 `ResumeFail` → 재로그인(이것도 Redis 복구 후) |
| 새 InGameSpace 입장 (9.6) | **거절.** 이미 있는 InGameSpace 안의 플레이는 계속됨. host는 임대 연장이 안 되면 새 입장을 멈춤 |
| 서버 발견 (9.7) | 마지막으로 알던 목록으로 계속. 새 서버는 합류하지 못함 |
| 파티, 채팅, 대기열 (9.8) | 새로 만들기와 매칭 정지. 이미 있는 파티 액터는 계속 동작(위치 연장만 실패) |
| 전투 서버 보상 (3.4) | **영향 없음.** 기본 경로(직접 전달)는 Redis를 쓰지 않음 |
| 컨텐츠 (구매, 인벤토리) | **영향 없음.** DB만 씀 |

### 9.11 코드 구조

- 존 스레드는 Redis를 **직접 호출하지 않는다.** I/O 런타임의 KV task가 비동기로 처리하고 결과를 메시지로 돌려준다. 플레이어 액터는 async이므로 `db` 크레이트의 KV 함수를 직접 `.await`한다(01 문서 5.3).
- Redis 접근 코드는 SQL과 같이 **`db` 크레이트(저장소 계층)에만** 둔다. 명령은 키 종류별 함수로 감싸서(예: `claim_space(key, me) -> ClaimResult`) 다른 크레이트에서 임의의 Redis 명령을 보내지 못하게 한다.
- Lua 스크립트, `MULTI`/`EXEC`, `WATCH`는 쓰지 않는다(9.1).
- Rust 클라이언트(`redis` 또는 `fred`)는 구현 단계에서 정한다.
