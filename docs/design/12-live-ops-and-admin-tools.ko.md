# 설계 12. 라이브 운영과 관리 도구

- 상태: **확정** (2026-11-20)
- 관련 문서: [11-design-data.ko.md](11-design-data.ko.md), `08-operations-observability.md`, `01-threading.md` 5.7, `03-data-ownership.md`, `docs/research/admin-web-platform.ko.md` (보안 조사)

[English](12-live-ops-and-admin-tools.md) | **한국어**

이 문서는 운영자가 돌고 있는 서비스를 어떻게 바꾸고, 그 일에 쓰는 웹 도구가 어떤 모습인지 정한다. 아래 결정은 2026-11-20에 소유자가 확정했다. 요구 사항은 과거 라이브 서비스에서 나왔다. "성공"이 "신호를 보냈다"는 뜻이던 변경, 두 번 지급될 수 있던 보상, 변경과 따로 기록되던 감사 로그, 게임 DB에 직접 쓰던 관리 도구다. 이 설계는 그 구멍을 하나씩 막는다.

## 1. 라이브 운영 상태가 사는 곳

라이브 운영 상태는 "지금 무엇이 켜져 있는가"에 답한다. 공지, 점검 창, 콘텐츠와 상점 스위치, 이벤트 일정, 제재다.

- 게임 전역 항목(공지, 점검, 스위치, 이벤트 일정)은 Common DB에 둔다.
- 계정 제재는 Account DB에 둔다.

각 레코드는 다음을 담는다.

- 세대 번호
- 대상 (전체, 샤드 하나, 플랫폼 하나)
- 적용 기간
- 변경한 운영자
- 사유

Redis 호환 저장소(Valkey)에는 이 데이터가 하나도 없다. Valkey는 게시판이지 정답이 아니다. 이 프로젝트 전체의 규칙과 같다. 정답 데이터는 DB에 있다.

## 2. 세대 번호와 변경 전달 경로

```
운영 도구 ──► 상태를 소유한 서비스의 관리 API ──► DB 커밋 (세대 N+1, 감사 행을 같은 트랜잭션에)
                                            └─► Valkey PUBLISH (힌트일 뿐)
게임 서버: 힌트 수신, 재접속, 주기 점검 때 → 최신 세대까지 읽기 → 적용 → "applied N+1" 보고
운영 도구: 서버별 요청됨 / 적용됨 / 실패 표시
```

PUBLISH는 Valkey 단일 명령 하나이고, 변경이 빨리 보이게 하는 힌트로만 쓴다. 정확성은 절대 힌트에 의존하지 않는다. 힌트를 놓쳤거나 재시작 중이거나 끊겨 있던 서버는 다음 주기 점검이나 재접속 때 세대 번호로 따라잡는다. 주기 점검 간격은 힌트를 놓쳐도 실패가 아니라 몇 초 지연으로 끝나게 짧게 잡는다.

각 서버는 새 세대를 적용하고 자기가 적용한 세대를 보고한다. 세대를 올리는 커밋과 감사 행은 하나의 트랜잭션에 함께 기록되므로, 기록 없는 변경이 존재할 수 없다.

## 3. 제어 경로

운영 도구는 게임 DB에 절대 직접 쓰지 않는다. 모든 변경은 해당 상태를 소유한 서비스의 관리 API(설계 08 2장의 사설 관리 포트)를 거친다. 소유 서비스가 자기 DB로 정상 경로를 밟아 커밋한다.

이것은 경계다. 도구가 DB에 직접 쓰면 소유 서비스는 자기 상태가 바뀐 것을 모르고, 변경은 fencing과 멱등 규칙을 우회하고, 감사 행은 변경과 다른 쓰기에 남는다.

## 4. 지급

지급은 아이템, 재화, 우편을 한 명 또는 명단의 플레이어에게 주는 일이다.

- 지급 요청마다 요청 ID가 있다. 요청 안의 수령인마다 멱등 키가 있다.
- 실행은 수령인의 본 샤드로 가는 기존 지급 경로를 따르고, 수령인마다 한 트랜잭션으로 처리하며, 멱등 INSERT를 같은 트랜잭션에 넣는다. 재시도는 실패한 것만 다시 보내고 두 번 지급하지 않는다.
- 모든 일괄 지급에는 대상 미리보기, 사유, 제2 승인자가 필요하다. 이것은 금액 기준보다 엄격한 규칙이고, 게임 경제가 금액 기준을 정할 때까지 유지한다. 그때 가서 금액 기준 규칙으로 바꿀 수 있다. 그 전에는 제2 승인자 없는 일괄 지급은 없다.

요청, 지급 원장, 감사 이벤트는 따로 성공할 수 없는 방식으로 함께 기록한다.

## 5. 점검

점검은 단계적 흐름을 따른다. 각 단계는 라이브 운영 레코드이자 명령이고, 도구는 서버마다 어느 단계인지 보여 준다.

1. 신규 입장 차단 (ready 끄기, 로드밸런서가 새 연결을 보내지 않게)
2. 접속 중인 플레이어에게 점검 안내
3. 드레인 또는 연결 종료
4. 서버가 비었는지 확인
5. 패치
6. 준비 상태 확인
7. 단계적 재개

## 6. 두 개의 웹 도구

두 도구는 별도로 배포하고 별도로 인증한다. DB도 세션도 공유하지 않는다.

| 도구 | 범위 |
|---|---|
| 게임 운영 도구 | 게임 쪽 운영만. 로그인이나 결제 데이터에 접근하지 않는다. |
| 퍼블리셔 백오피스 | 계정, 로그인 수단, 플랫폼 제재, 결제와 환불. 게임 DB에는 접근하지 않는다. |

게임 운영 도구는 최소 형태(서버 상태, 공지, 점검, 킥, 지급)로 파일럿의 샤드 간 메시지 단계 바로 뒤에 만든다. 개발 후반의 운영 단계까지 기다리지 않는다. 완전한 도구는 여기서 자란다.

**프로그램 하나로 시작한다 (소유자 방향, 2026-11-20).** 한 사람이 개발하는 동안에는 두 도구를 웹 서버 하나, `ops` 크레이트로 시작한다. 이 도구도 다른 서버와 같은 서버다. 자기 설정 파일과 실행 스크립트가 있고, 런처가 다른 서버와 함께 띄운다. 메뉴에서 게임 쪽 화면과 퍼블리셔 쪽 화면을 다른 묶음으로 두고, 계정 데이터는 퍼블리셔의 운영자 API를 통해서만 읽는다. 그래서 위에서 말한 두 도구로 나누는 일은 배포를 나누는 일이 된다. 나누는 시점은 베타 전이다.

환경은 도구 안에서 고르는 것이 아니라 도구의 설정 파일이 정한다. 개발 환경에서는 이 PC에서만 접속을 받고, 설정에 적힌 운영자로 로그인된 상태가 된다. 그래서 조작 기록에는 누가 했는지가 그대로 남는다. 다른 환경 이름으로는 8장의 정식 운영자 로그인이 만들어질 때까지 도구가 뜨지 않는다.

## 7. 기술 스택

2026-11-20에 확정했다. 두 도구 모두 `axum`과 빌드 시점에 컴파일되는 Askama 템플릿을 쓰고, 부분 갱신에는 htmx를 쓴다.

이유는 보안 조사 문서([docs/research/admin-web-platform.ko.md](../research/admin-web-platform.ko.md))에 있다. 2025~2026년 사고 기록에는 Node 서버 프레임워크와 npm 공급망을 뚫은 사례가 반복된다. 미들웨어의 인가 우회, 역직렬화를 통한 서버 코드 실행, 도난당한 배포 계정으로 올라온 악성 패키지다. Node 서버도 npm 빌드도 없는 서버 렌더링 Rust 도구는 이 공격 경로를 없앤다. 남는 것은 이 프로젝트가 이미 운영하는 Cargo와 운영체제뿐이다.

htmx는 버전을 고정하고 해시를 기록한 JavaScript 파일 하나를 도구가 직접 제공한다. npm 의존성이 아니고 CDN도 쓰지 않는다. Askama 템플릿은 컴파일 시점에 검사되므로 깨진 템플릿은 빌드를 실패시킨다.

서버 렌더링으로 감당하기 어려운 화면이 생기면 대안은 같은 출처의 Rust API를 둔 정적 SPA다. 그 도구에만 적용하고, 거기에 따라오는 npm 공급망 검토를 함께 한다. 그때 가서 구체적 화면을 놓고 정하는 미래의 결정이다.

## 8. 보안 기준

스택과 무관하게 두 도구는 같은 기준을 따른다. 보안 조사 문서에서 나온 항목들이다.

- 공개 인터넷에서 접근할 수 없다. 관리되는 단말에서 VPN 또는 제로트러스트 접근 프록시로만 들어온다.
- 운영자 로그인은 피싱 방지 MFA(패스키 또는 보안 키)를 강제한다. 세션은 짧게. 시작값은 유휴 15분, 최대 8시간이다. 지급과 환불 직전에는 재인증을 요구한다.
- 역할 기반 최소 권한. 조회, 공지, 점검, 킥과 제재, 지급, 환불, 감사 조회는 각각 따로 권한을 준다. 버튼을 숨기는 것은 인가가 아니다. 관리 API는 모든 요청에서 운영자 권한을 검사한다.
- 모든 운영 행위를 감사한다. 누가, 언제(UTC), 어떤 대상에, 무엇을, 변경 전후 값과 함께, 사유, 결과, 요청 ID를 남긴다. 감사 기록은 별도 권한으로 보호한다. 감사 이벤트를 남길 수 없는 위험 변경은 실행하지 않는다.
- CSRF 보호, 서버 쪽 출처 확인, 엄격한 콘텐츠 보안 정책. 같은 출처 스크립트만 허용하고 `frame-ancestors 'none'`, `object-src 'none'`, `form-action 'self'`를 적용한다.
- 비밀은 저장소 밖에 둔다(설계 08 8장). 두 도구에는 게임 DB 자격 증명을 아예 주지 않는다.
- `Cargo.lock`을 커밋하고, 의존성 보안 권고는 `cargo-audit`이나 `cargo-deny`로 확인한다. 둘 다 아직 품질 게이트에 없다. 첫 도구를 만들 때 하나를 넣는다.

## 9. 첫 화면

게임 운영 도구:

- 서버 상태와 적용된 세대
- 공지
- 점검 일정
- 콘텐츠와 상점 스위치
- 킥
- 제재
- 플레이어 조회 (지원용 읽기 전용 역할)
- 승인이 붙는 지급
- 감사 로그

퍼블리셔 백오피스:

- 계정 조회
- 로그인 수단과 연동
- 플랫폼 제재
- 결제와 환불
- 지원 이력
- 감사 로그

## 10. 관측 추가

설계 08의 지표에 다음을 더한다.

- 서버별 상태 표본의 나이. 보고가 오래된 서버는 살펴봐야 할 서버다.
- 정책 커밋과 적용 사이의 지연, 서버별로. "변경이 모든 서버에 실제로 닿았는가"에 답하는 숫자다.
- 지급 부분 실패율. 일부 수령인에게만 지급되고 나머지는 실패한 건은 즉시 보여야 한다.

경보: 상태 표본이 기준보다 오래된 경우, 적용 지연이 기준을 넘은 경우, 지급 부분 실패가 0보다 큰 경우.
