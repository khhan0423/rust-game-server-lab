# 설계 11. 기획 데이터

- 상태: **확정** (2026-11-20)
- 관련 문서: [12-live-ops-and-admin-tools.ko.md](12-live-ops-and-admin-tools.ko.md), `01-threading.md` 5.7과 10.0, `04-database.md`, `docs/protocol/session-contract.md`

[English](11-design-data.md) | **한국어**

이 문서는 기획자가 작성한 표가 서버와 클라이언트에 도달하는 경로를 정한다. 아래 결정은 2026-11-20에 소유자가 확정했다. 과거 라이브 서비스에서는 이 파이프라인이 없을 때 무슨 일이 생기는지 이미 보았다. 표마다 손으로 쓰는 파싱, 런타임의 문자열 키, 클라이언트와 서버의 데이터 불일치, 그리고 실패해도 로그만 남기는 검증이다. 이 설계는 그 실패 경로를 없앤다.

## 1. 기획 데이터란

기획 데이터는 "게임에 무엇이 존재하는가"에 답한다. 아이템, 상점, 몬스터, 보상, 던전, 필드 정원, 일정이다. 기획자가 작성하고, 빌드와 함께 버전을 관리하며, 런타임에는 읽기만 한다.

두 종류의 데이터를 혼동하면 안 된다.

| 구분 | 대답하는 질문 | 사는 곳 | 바꾸는 사람 |
|---|---|---|---|
| 정적 표 (기획 데이터) | 게임에 무엇이 존재하는가 | 빌드와 함께 배포되는 번들 파일 | 기획자 (내보내기와 검토를 거쳐) |
| 라이브 운영 데이터 | 지금 무엇이 켜져 있는가 | 데이터베이스 (Common DB, Account DB) | 운영자 (운영 도구로) |

운영 도구는 정적 표를 절대 고치지 않는다. 상점 아이템을 끄고 켜는 일은 아이템 정의를 고치는 것이 아니라 데이터베이스의 라이브 운영 변경이다. 그 경로는 설계 12에 있다.

## 2. 결정

연구 제안서의 열린 여섯 질문은 2026-11-20에 모두 확정됐다.

- 번들은 표마다 JSON 파일 하나에 매니페스트를 더한 것이다. JSON은 비교와 검토가 쉽다. 로드 시간이 문제가 되면 번들 형식만 같은 매니페스트와 로더 뒤에서 바꿀 수 있다.
- 표마다 작은 TOML 스키마를 둔다. 스키마가 컬럼 타입과 규칙의 원천이다. Rust 타입은 스키마에서 생성하고 손으로 쓰지 않는다.
- 라이브 운영 변경은 Valkey에 단일 PUBLISH 명령 하나를 힌트로 알린다. 서버가 따라잡는 보장은 세대 번호가 주고, 힌트가 아니다. 설계 12 참고.

## 3. 스키마

표마다 TOML 파일 하나를, 내보낸 데이터 옆 저장소에 둔다. 스키마는 컬럼마다 다음을 정한다.

- 타입 (정수, 소수, 문자열, bool, enum, 참조)
- 단위가 있는 경우 그 단위 (밀리초, 골드, 천분율)
- 필수인지 선택인지
- 유효 범위 또는 허용 값
- 참조 컬럼이 가리키는 표
- 클라이언트가 봐도 되는 컬럼인지

스키마에는 표의 ID 타입 이름도 정의돼 있어, 코드 생성이 typed ID(`ItemId`, `MonsterId`)를 만든다. 가이드 4.1장의 newtype이다. `ItemId` 자리에 `MonsterId`를 넘기면 라이브 버그가 아니라 컴파일 에러가 난다.

## 4. 코드 생성

빌드 시점의 생성기가 스키마를 읽어 다음을 만든다.

- 표마다 하나의 typed ID
- 표마다 하나의 row 구조체 (컬럼과 필드가 일치)
- 스키마에 정의된 enum 타입

생성기는 `build.rs`나 빌드가 부르는 커밋된 도구로 돈다. `.proto`에서 프로토콜 타입을 만들던 방식과 같다. 같은 스키마로 나중에 클라이언트 쪽 타입도 만들 수 있어, 양쪽이 리뷰가 아니라 구조 자체로 일치하게 된다.

생성된 코드는 `game` 크레이트에 둔다. 로드와 파싱은 서버 계층에 둔다. `game`은 I/O를 하지 않기 때문이다.

## 5. 작성과 내보내기

기획자는 스프레드시트에서 작업한다. 내보내기 도구가 시트를 번들로 바꾼다.

```
tables/
  items.json
  monsters.json
  rewards.json
  ...
  manifest.json
```

기획자가 쓰기 편한 문자열 별칭은 내보내기에서 typed ID로 변환된다. 내보내기가 끝나면 런타임에 문자열 이름으로 찾는 코드는 없다.

매니페스트는 표 목록, 콘텐츠 버전, 모든 표 파일에 대한 콘텐츠 해시를 담는다.

## 6. 검증

같은 검증을 세 지점에서 돌린다. 내보내기, CI, 서버 기동이다.

검사 항목:

- 표 안의 중복 키
- 선언된 범위를 벗어난 값
- 대상 표에 없는 행을 가리키는 참조
- 필수 컬럼 누락, 알 수 없는 컬럼
- 선언된 집합 밖의 enum 값

에러는 표, 행, 컬럼을 짚어 준다. 기획자가 서버 코드를 읽지 않고 시트를 고칠 수 있어야 한다.

내보내기와 CI에서는 검사가 실패하면 내보내기나 빌드가 실패다. 기동 시에는 서버가 실제로 받은 번들을 검증하고, 실패하면 뜨지 않는다. 이것은 설계 01 10.0장의 기동 배리어 일부다. 잘못된 번들이 플레이어에게 닿을 방법이 없다. 실패를 로그만 남기는 검사는 인정하지 않는다. 과거 라이브 서비스에서 그렇게 나쁜 데이터가 플레이어에게 닿는 것을 이미 보았다.

## 7. 버전과 콘텐츠 해시

앱 버전과 콘텐츠 버전은 분리한다. 매니페스트가 콘텐츠 해시를 담는다.

로그인할 때 클라이언트는 자기가 로드한 번들의 해시를 보낸다. 서버의 해시와 다르면 이유를 명확히 알려 주며 로그인을 거절하고 업데이트를 안내한다. 불일치를 로그만 남기는 것으로는 부족하다. 그런 클라이언트는 서버와 다른 데이터로 시뮬레이션하게 되고, 아무도 재현할 수 없는 문의가 쌓인다.

## 8. 로드와 조회

서버는 기동 배리어 동안 번들을 읽고, 검증하고, typed ID 기준 인덱스를 만든다. 런타임 조회는 그 인덱스를 통해서만 한다. 표마다 손으로 쓴 파싱도, 문자열 조회도 없다.

## 9. 재로드

정적 표는 자주 바뀌지 않지만, 재시작 없이 새 번들을 반영할 수 있어야 한다. 재로드는 설계 01 5.7장의 스냅샷 교체를 따른다.

1. 관리 task가 새 번들을 읽고 검증한다. async 직접 호출 방식(A)을 쓴다. 그동안 게임은 옛 데이터로 계속 돈다.
2. 검증이 실패하면 옛 세대를 유지하고 실패를 보고한다. 아무것도 바뀌지 않는다.
3. 성공하면 새 데이터를 읽기 전용 `Arc` 스냅샷으로 만들어, 그 데이터를 쓰는 존 스레드와 액터에 메시지로 보낸다.
4. 받은 쪽은 자기 차례에 참조를 통째로 바꾼다. 진행 중이던 요청은 시작한 세대를 유지한다. 옛 번들과 새 번들이 절반씩 섞여 보이는 상태는 생기지 않는다.

재로드에 블로킹 래퍼(설계 01 5.7장의 C 방식)를 쓰지 않는다. 재로드는 게임이 돌고 있는 동안 일어난다.
