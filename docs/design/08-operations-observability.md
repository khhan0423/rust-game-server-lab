## 1. 네 가지 관측

| 구분 | 질문 | 방법 |
|---|---|---|
| 헬스 체크 | 살아 있나? 일을 받아도 되나? | `/health/live`, `/health/ready` |
| 지표 | 얼마나 잘 돌고 있나? | `/metrics` → Prometheus → Grafana |
| 로그 | 무슨 일이 있었나? | JSON 파일 → Fluent Bit |
| 경보 | 사람이 봐야 하나? | Prometheus 경보 규칙 → Alertmanager → Discord |

## 2. 관리 포트

| 경로 | 내용 | 쓰는 쪽 |
|---|---|---|
| `/health/live` | 프로세스가 응답하는가. 응답만 하면 OK | 프로세스 감시자(systemd 등). 실패하면 재시작 |
| `/health/ready` | 일을 받아도 되는가. 필수 연결(DB, Redis, 필요한 서버 간 링크)이 정상이고 드레인 중이 아님 | **로드밸런서.** 준비 안 된 Gateway, Entry에는 연결을 보내지 않음 |
| `/metrics` | 지표 (Prometheus 텍스트 형식) | Prometheus |
| `/admin/...` | 드레인 시작, 점검 모드, 로그 레벨 변경, Kick | 운영 도구. **인증 필수** |

- 관리 포트는 **사설망에만** 연다. `/admin`은 운영 도구 계정의 인증(서명된 토큰 또는 mTLS)을 요구한다.
- 관리 HTTP는 I/O 런타임 위의 task로 돈다. 존 스레드와 플레이어 액터는 관리 요청을 직접 받지 않고, 필요하면 메시지로 전달받는다.
- **운영 명령은 게임을 멈추지 않는다.** `/admin` 처리 중 DB가 필요하면 관리 task가 직접 `.await`하고, 결과는 메시지나 스냅샷 교체로 존과 액터에 넘긴다(01 문서 5.7). 운영 명령 하나가 게임 스레드에서 DB를 기다리면 서버 전체가 멈추기 때문이다.
- `ready`는 기동 배리어(01 문서 10.0)가 끝난 뒤에만 켜진다.
- `ready`는 상태가 바뀔 때 Redis의 `server:{id}.state`(03 문서 9.7)와 함께 갱신한다. 드레인을 시작하면 `ready`가 실패로 바뀌어 새 연결이 오지 않는다.

## 3. 지표

```rust
metrics::counter!("tick_overrun_total", "zone" => zone_label).increment(1);
metrics::histogram!("tick_duration_ms").record(elapsed_ms);
metrics::gauge!("ccu", "shard" => shard_label).set(ccu as f64);
```

- `metrics`는 내부적으로 원자 변수를 써서 락이 없다. 존 스레드와 플레이어 액터에서 매 틱 기록해도 된다.
- 지표 이름은 `snake_case`, 단위를 이름 끝에 붙인다(`_ms`, `_bytes`, `_total`). 라벨 값의 종류는 적게 유지한다(플레이어 ID 같은 값을 라벨로 쓰지 않는다).

| 영역 | 지표 |
|---|---|
| 접속 | 샤드별, Gateway별 동접. 로그인 성공/실패. **끊김 이유별 횟수**(02 문서 2.3) |
| Entry | 퍼블리셔 A​PI 응답 시간과 실패, 신규 캐릭터 생성 수, 샤드별 배정 수 |
| 존 스레드 | **틱 소요 시간, 틱 초과 횟수**, 활성/휴면 InGameSpace 수 |
| 플레이어 액터 | 액터 수, inbox 대기 명령 수, 명령 처리 시간, DB 함수 소요 시간, 재시도 횟수, **느린 명령 횟수** (01 문서 5.8) |
| 채널 | 스레드 간 채널 사용률, 가득 참 횟수 |
| DB | 커넥션 풀 대기 시간, 쿼리 시간, 실패 수, 재시도 수(데드락) |
| DB (B 방식, 존과 InGameSpaceManager) | **세 구간을 따로** 잰다: DB task 채널에서 기다린 시간, 실행 시간, 결과(`DbResult`)를 존에서 처리한 시간. 느려졌을 때 DB 문제인지 결과 처리 코드 문제인지 바로 구분하기 위해서다 |
| 기동 | 단계별 소요 시간, 기동 복구로 처리한 건수 (01 문서 10.0) |
| Redis | 응답 시간, 실패 수, 임대 연장 실패 |
| 세션 | 재전송 버퍼 사용량, Replay/Resync 횟수 |
| 서버 간 | outbox 미확인 메시지 수, 재전송 횟수, 링크 재연결 수 |

### 3.1 경보 (출발점)

| 경보 | 조건 (예) |
|---|---|
| 서버 사라짐 | Prometheus 수집 실패 1분 |
| 틱 초과 | 1분 동안 틱 초과 비율 5% 이상 |

## 4. 로그

경로는 `04-database.md` 1.1을 따른다. 여기서는 코드 쪽 규칙을 정한다.

| 로그 | 만드는 방법 | 파일 |
|---|---|---|
| **운영 로그** | `tracing` 매크로. `tracing-subscriber`의 JSON 형식 | `logs/ops.jsonl` (날짜별 회전) |
| **게임 분석 로그** | 타입이 있는 이벤트 enum을 `serde_json`으로 직렬화 | `logs/game-analytics.jsonl` (날짜별 회전) |
| 거래성 로그 | Game DB의 같은 트랜잭션 (로그 파일 아님) | - |

### 4.1 운영 로그

```rust
let (ops_writer, _guard) = tracing_appender::non_blocking(
    tracing_appender::rolling::daily("logs", "ops.jsonl"),
);
tracing_subscriber::fmt().json().with_writer(ops_writer).init();
```

- `non_blocking`은 로그를 채널에 넣고 바로 돌아온다. 파일 쓰기는 백그라운드 스레드 하나가 한다. **존 스레드가 디스크 I/O로 멈추지 않는다.**
- 버퍼가 가득 차면 버린다(게임을 막지 않음). 버린 수는 지표로 남긴다.

### 4.2 게임 분석 로그: 타입이 있는 이벤트

```rust
#[derive(Serialize)]
#[serde(tag = "log_type")]
pub enum AnalyticsEvent {
    ItemAcquired { player: PlayerId, item: ItemTemplateId, source: AcquireSource },
    DungeonCleared { player: PlayerId, dungeon: DungeonId, duration_ms: u32 },
    SessionEnded { player: PlayerId, reason: CloseReason, play_ms: u64 },
}
```

- 분석 로그는 기획과 분석이 쓰는 데이터라 필드가 틀리면 안 된다. 이벤트를 enum으로 정의하면 **필드 이름과 타입이 컴파일 시 검사**된다.
- `log_type`이 Fluent Bit의 라우팅 키가 된다.
- 모든 이벤트에 공통 필드(시각, 샤드, 서버 ID)를 붙인다.
- 쓰기 방식은 운영 로그와 같다(채널 + 백그라운드 스레드). 버퍼가 가득 차면 버리고 지표로 남긴다.

### 4.3 패닉과 로그

`panic = "abort"`(01 문서 10.2)이므로 패닉이 나면 백그라운드 스레드가 아직 쓰지 못한 마지막 몇 줄은 사라진다. 정상 종료 때는 남은 로그를 모두 쓰고 끝난다. 사라지는 부분은 코어 덤프로 보완하고, 정확해야 하는 기록은 Game DB 거래성 로그에 있다.

## 5. Fluent Bit

### 5.1 구성

| 단계 | 구성 |
|---|---|
| 개발, 소규모 | 서버마다 Fluent Bit 하나가 파일을 읽어 바로 목적지(Log DB, 파일 보관)로 보낸다 |
| 서버가 늘면 | **에이전트 + 집계기 2단.** 각 서버의 Fluent Bit는 읽어서 넘기기만 하고(forward), 운영 VM의 집계기(1~2대)가 라우팅하고 Log DB에 쓴다 |

```
[각 서버]  게임 서버 → JSON 파일 → Fluent Bit (에이전트)
                                        │ forward
[운영 VM]                     Fluent Bit 집계기 (라우팅 규칙은 여기에만)
                                ├─ analytics.* ──> Log DB (pgsql 출력, 커넥션 = 집계기 수 × 워커 수)
                                ├─ analytics.* ──> 파일 보관 (압축, 장기)
                                └─ ops.*       ──> 파일 보관 (DB에 쓰지 않음)
```

- Fluent Bit의 PostgreSQL 출력은 **워커 하나당 커넥션 하나**다. 2단으로 두면 Log DB 커넥션 수가 서버 수와 무관하게 고정된다.
- Fluent Bit는 게임 서버와 **별도 프로세스**다. CPU와 메모리 상한은 systemd(`CPUQuota`, `MemoryMax`)와 Fluent Bit의 버퍼 한도로 묶는다. 버퍼는 파일 시스템 버퍼를 써서 재시작에도 남게 한다.
- 1단에서 2단으로 바꿀 때 **게임 코드는 바뀌지 않는다.** Fluent Bit 설정만 바뀐다.

### 5.2 Log DB 쪽

- Fluent Bit는 로그 한 건을 `tag`, `time`, `data JSONB` 한 행으로 쓴다.
- 테이블은 **시간 기준 파티셔닝**(월별 또는 일별)을 한다. 오래된 파티션은 떼어 내 보관하거나 지운다.
- 정형 테이블이 필요하면 **주기적으로 도는 변환 작업**으로 옮긴다. 트리거는 쓰지 않는다(가이드 8장).
- DB에는 분석에 필요한 태그만 보내고, 원본 전체는 압축 파일로 보관한다.
- 분석 로그는 **최소 한 번** 전달이라 중복이 있을 수 있다.

## 7. 운영 도구에서 보는 것

운영 도구(GM 툴)는 정보를 직접 모으지 않고 조합한다.

```
운영 도구 화면
 ├─ 서버 목록과 상태    ← Redis server:{id} (역할, 주소, 부하, Active/Draining)
 ├─ 그래프              ← Grafana (임베드 또는 링크)
 ├─ 경보 현황           ← Alertmanager
 └─ 운영 명령           ← 각 서버의 /admin (드레인, 점검 모드, 공지, Kick)
```

## 8. 설정과 비밀

설정 파일에 실제 DB 계정, 내부 호스트, 담당자 연락처를 넣어 저장소에 올리면, 저장소를 받은 사람은 누구나 운영 DB에 접근할 수 있다. 그래서 설정과 비밀을 나눈다.

| 구분 | 어디에 두나 | 예 |
|---|---|---|
| 일반 설정 | 저장소의 설정 파일 | 포트, 스레드 수, 채널 용량, 틱 주기 |
| 비밀 | **저장소 밖.** 환경 변수 또는 비밀 저장소(파일 권한을 제한한 별도 파일 포함) | DB 접속 문자열, Redis 비밀번호, 서버 간 공유 비밀키, 토큰 서명 키, 경보 웹훅 주소 |

- 저장소에는 비밀값 자리를 비워 둔 예시 파일(`*.example`)만 둔다.
- 비밀값은 로그와 에러 메시지에 찍지 않는다. 설정 구조체의 `Debug` 출력에서도 가린다.
