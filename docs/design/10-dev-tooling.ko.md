## 1. 지금 상태

저장소에는 설계 문서와 도구 설정(`rust-toolchain.toml`, `rustfmt.toml`, `clippy.toml`)만 있고 Rust 코드는 없다. 그래서 세 가지 모두 **워크스페이스 뼈대**부터 시작한다.

## 2. 워크스페이스 뼈대와 유닛 테스트

### 2.1 만드는 것

가이드 2장의 구조를 따르되, 크레이트는 처음 필요한 단계에서 만든다(빈 크레이트를 미리 만들지 않는다). 처음에는 `infra`, `db`, `server`, `gateway`만 만든다.

```
Server/
├─ Cargo.toml        [workspace], [workspace.dependencies], [workspace.lints] (가이드 부록 A)
├─ crates/
│  ├─ protocol/      패킷 정의 (prost)
│  ├─ game/          게임 규칙 (I/O 없음)
│  ├─ db/            sqlx 쿼리
│  ├─ net/           프레이밍 코덱, 링크
│  ├─ gateway/       Gateway 바이너리
│  ├─ server/        Game/전투/Entry 등 역할별 바이너리
│  └─ bot/           테스트 클라이언트
└─ migrations/
```

뼈대가 생기면 품질 게이트 세 줄이 처음으로 실제로 돌아간다.

### 2.2 테스트 종류

| 종류 | 대상 | 방법 | 외부 의존 |
|---|---|---|---|
| 단위 테스트 | `protocol`, `game` (순수 로직) | 같은 파일의 `#[cfg(test)] mod tests`. 인코딩 왕복, 경계값 | 없음 |
| 액터 테스트 | 플레이어 액터, 존 로직 | 채널로 명령을 넣고 결과 메시지를 확인. 시간은 `tokio::time::pause()`로 가상 시간 (가이드 11장) | 없음 |
| DB 통합 테스트 | `db` 크레이트의 함수 | `sqlx::test`가 테스트마다 빈 DB를 만들고 마이그레이션을 적용한 뒤 실행 | **PostgreSQL 필요** |
| 서버 통합 테스트 | 여러 프로세스가 함께 도는 흐름 | 런처로 띄우고 테스트 클라이언트 시나리오로 확인 (3, 4장) | PostgreSQL, Valkey |

- 테스트에서 `sleep`으로 타이밍을 맞추지 않는다. 이벤트나 채널을 기다린다.
- DB 통합 테스트는 실제 PostgreSQL을 쓴다. 가짜 DB로 바꾸면 트랜잭션, 제약 조건, 멱등 키 같은 핵심 동작을 검증할 수 없기 때문이다.

## 3. 서버 런처

### 3.1 하는 일

개발 PC에서 서버군 전체를 명령 하나로 띄우고 내린다. 운영 환경은 systemd가 맡으므로(08 문서 M8) 런처는 **개발과 테스트용**이다.

```
launcher                   서버 제어, 상태, 최근 출력을 보는 창 열기
launcher --headless up     의존 순서대로 띄우고 Ctrl+C에서 역순으로 종료
launcher --headless check  의존 순서대로 띄운 뒤 역순으로 종료하고 결과 출력
```

서버를 띄울 때는 자식 프로세스의 표준 출력에 `ready admin=<주소> ...`가 나온 뒤 다음 서버를 띄운다. 정상 종료는 자식마다 생성한 인증값으로 관리 포트에 요청하고, 기한이 지나면 강제로 종료한다. 창에서는 서버 하나를 재시작하거나 강제로 종료할 수 있고, 운영 도구가 알린 주소를 브라우저에서 열 수 있다.

### 3.2 토폴로지 파일 (예)

기본 파일은 `dev/config/launcher.toml`이다. `--topology <파일>`로 다른 파일을 선택할 수 있다. 경로는 실행 디렉터리 기준이며 실행 스크립트는 작업 디렉터리를 워크스페이스 루트로 설정한다.

```toml
bin_dir = "target/debug"
env_file = ".env"
ready_timeout_seconds = 60
stop_timeout_seconds = 15

[process]
name = "launcher"
environment = "development"
log_level = "info"

[[services]]
name = "publisher"
binary = "publisher"
config = "dev/config/publisher.toml"
args = ["run"]

[[services]]
name = "server"
binary = "server"
config = "dev/config/server.toml"
args = ["run"]
depends_on = ["publisher"]
```

- DB 접속 정보 같은 비밀값은 이 파일에 넣지 않는다. 환경 변수로 넘긴다(08 문서 8장).
- 기본 설정은 `gateway`와 `ops`도 띄우며 `ops`가 마지막이다. 이름은 중복될 수 없고, 의존 대상은 모두 존재해야 하며 순환할 수 없다.

### 3.3 서버는 각자 뜬다. 런처는 돕기만 한다 (소유자 결정, 2026-11-20)

런처는 이미 혼자 뜰 수 있는 서버들 위에 얹는 편의 도구다. 서버를 띄우는 유일한 방법이 되어서는 안 된다.

- **서버마다 설정 파일이 따로 있다.** `dev/config/` 아래에 서버마다 TOML 파일 하나를 둔다(`publisher.toml`, `server.toml`, `gateway.toml`, `ops.toml`). 서버는 자기 파일만 읽는다. 비밀값은 환경 변수에 둔다.
- **서버마다 실행 스크립트가 따로 있다.** `scripts/run-<서버>.sh`와 `.ps1`이 환경을 올리고 그 서버 하나를 자기 설정 파일로 띄운다. 서버는 다른 서버가 하나도 떠 있지 않아도 떠야 하고, 헷갈리게 실패하는 대신 무엇을 기다리는지 알려야 한다.
- **런처는 스크립트와 같은 설정 파일, 같은 명령을 쓴다.** 여기에 순서, 상태, 로그, 그리고 종료, 재시작, 강제 종료 버튼을 더한다.

서버를 띄우는 것 외에 런처가 맡는 일은 다음과 같다.

| 일 | 뜻 |
|---|---|
| 기획 데이터 패치 | 새 기획 데이터 묶음(설계 11)을 실행 중인 서버에 적용한다. 검증하고, 서버들에 다시 읽으라고 알리고, 어느 서버가 받았는지 보여 준다 |
| 고른 폴더의 데이터로 띄우기 | 런처에서 고른 기획 데이터 폴더로 서버군을 띄운다. 기본 묶음을 건드리지 않고 기획자의 작업본이나 예전 묶음을 돌려 볼 수 있다 |
| 고른 버전으로 띄우기 | 빌드한 버전 여러 개를 나란히 보관하고 그중 하나로 서버군을 띄운다. 예를 들어 지난주 빌드에서 버그를 재현할 때 쓴다 |

이 세 가지는 기획 데이터(설계 11)와, 빌드한 버전을 폴더별로 보관하는 일에 기대므로 기본 런처 다음에 들어간다.

## 4. 테스트 클라이언트 (`bot` 크레이트)

### 4.1 하는 일

- **세션 계약의 참조 구현이다.** 접속, 인증, 재접속, 끊김 복구를 세션 계약 문서대로 한다. 클라이언트(Unity 등) 개발자가 "서버가 정말 이렇게 동작하나"를 이것으로 확인한다.
- 두 가지 모드를 둔다.

| 모드 | 용도 | 모양 |
|---|---|---|
| 대화형 | 개발자가 패킷을 하나씩 보내 보며 확인 | 텍스트 명령창. `login`, `enter`, `buy 1001`, `move 10 20`, `disconnect` 같은 명령 |
| 시나리오 | 같은 흐름을 자동 반복, 여러 봇 동시 실행, 부하 테스트 | 시나리오를 Rust 코드로 작성하고 봇 N개로 실행. 결과는 지연 시간 분포(`hdrhistogram`)와 실패 수 |

### 4.2 첫 시나리오

승인된 샤드 시뮬레이션(04 문서 2장)을 그대로 시나리오로 만든다.

1. 봇 3개가 처음 접속 → 서로 다른 샤드에 배정되는지 확인
2. 각자 아이템 구매 → 각자의 Game DB에 저장되는지 확인
3. 봇1이 봇2에게 우편 → 봇2의 우편함에 한 번만 들어오는지 확인 (메시지를 일부러 두 번 보내 멱등성도 확인)
4. 봇2의 Game 서버에서 **Kill**을 누른다 → 재시작 후 우편이 사라지지 않았는지 확인
