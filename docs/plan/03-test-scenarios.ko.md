## 1. 읽는 법

시나리오 번호는 `단계-종류-번호`다. 예: `P4-D-02`는 파일럿 4단계의 DB 테스트 2번이다.

| 종류 | 뜻 | 어떻게 돌리나 | 외부 의존 |
|---|---|---|---|
| U | 단위 테스트 | `cargo test`. 순수 로직 | 없음 |
| A | 액터, 틱 테스트 | `cargo test`. 채널로 명령을 넣고 결과 메시지를 확인. 시간은 가상 시간 | 없음 |
| D | DB 테스트 | `sqlx::test`. 테스트마다 빈 DB를 만들고 마이그레이션 적용 | PostgreSQL |
| I | 통합 테스트 | 런처(창 없는 모드)로 서버군을 띄우고 봇 시나리오로 확인 | PostgreSQL, Valkey |
| F | 장애 테스트 | 통합 테스트 중 런처로 서버를 강제 종료하거나 연결을 끊는다 | 같음 |
| L | 부하 테스트 | 봇 다수 + 지연 분포 수집 | 같음 |
| M | 수동 확인 | GUI에서 사람이 체크리스트로 확인 | 같음 |

**공통 규칙**

- 테스트에서 `sleep`으로 타이밍을 맞추지 않는다. 기다릴 이벤트를 먼저 구독하고, 동작을 일으킨 뒤, 그 이벤트를 제한 시간 안에 기다린다.
- 시간이 걸리는 규칙(인증 제한, 유예, 임대)은 통합 테스트에서 설정으로 짧게 준다. 단위와 액터 테스트에서는 가상 시간을 쓴다.
- 정합성 테스트는 끝에 **총량 검사**를 한다. 시작 때의 재화와 아이템 합계가 끝과 같은지(의도한 증감 제외) DB에서 직접 센다.
- 문장이나 로그 문구 자체를 테스트로 고정하지 않는다. 기계가 읽는 값(필드, 코드, 개수)만 검사한다.

|---|---|---|

| P0-A-01 | 관리 포트: 준비 전과 후 | 준비 전 `/health/live` 200, `/health/ready` 503. 준비 후 `/health/ready` 200 |
| P0-A-02 | 관리 포트: `/metrics` | 기록한 지표가 Prometheus 형식 줄로 나온다 |
| P0-D-01 | 빈 DB의 스키마 확인, 마이그레이션 적용 후 확인 | 적용 전에는 "버전이 다르다"로 거부, 적용 후에는 통과 |

| P0-I-02 | 마이그레이션이 적용되지 않은 DB로 `server` 기동 | 0이 아닌 코드로 끝나고 준비 통지가 없다 |
| P0-I-03 | DB 주소를 틀리게 주거나 DB 비밀 환경 변수 없이 기동 | 0이 아닌 코드로 끝나고 준비 통지가 없다 |
| P0-I-04 | `server migrate`를 빈 DB에 실행 | 성공으로 끝나고 스키마 확인을 통과한다 |

### P2. 서버 런처

| 번호 | 시나리오 | 기대 결과 |
|---|---|---|
| P2-U-01 | 이름이나 포트가 겹치는 토폴로지 파일 | 로드 실패. 겹친 항목이 에러에 있다 |
| P2-U-02 | 기동 순서 계산 | Entry, 게임서버, Gateway 순. 서로 의존하는 순환이면 에러 |
| P2-I-01 | `up` | 앞 서버가 `ready`가 된 뒤에 다음 서버가 시작된다 (기동 기록의 순서로 확인) |
| P2-I-02 | 한 서버가 `ready` 전에 죽는 토폴로지로 `up` | `up` 실패. 이미 띄운 서버를 모두 정리한다 |
| P2-I-03 | `down` | 역순으로 종료 신호. 시간 안에 안 끝난 서버는 강제 종료. 남은 프로세스 0 |
| P2-I-04 | `kill game-2` | game-2만 죽은 상태로 표시되고 나머지는 그대로 |
| P2-I-05 | `restart game-2` | 새 PID로 뜨고 `ready`로 돌아온다 |
| P2-I-06 | 창 없는 모드의 종료 코드 | 성공 0, 실패는 0이 아닌 값 |
| P2-M-01 | GUI 상태판, 로그 창, 버튼 | 상태 변화가 화면에 반영되고 한글이 보인다 |

| 번호 | 시나리오 | 기대 결과 |

| P3-U-03 | 샤드 배정: 친구 코드 없음, 동률 | 누적 인원 최소. 동률이면 정해진 규칙으로 항상 같은 결과 |

| P3-D-01 | 첫 입장 | 계정, 캐릭터 번호, 본 샤드가 한 트랜잭션으로 기록된다 |
| P3-D-02 | 같은 계정의 첫 입장 2건을 동시에 | 계정은 1개. 둘 다 같은 캐릭터 번호를 받는다 |
| P3-D-03 | 퍼블리셔: 게스트 계정 생성 | 계정과 로그인 수단이 한 트랜잭션으로 기록된다. 비밀값은 해시만 저장된다 |
| P3-U-06 | 퍼블리셔: 입장 티켓 검증 (변조, 만료, 다른 게임용) | 모두 거절 |
| P3-I-01 | 정상 접속 (퍼블리셔 게스트 로그인 → 티켓 → Entry → Gateway 인증 → 게임 입장) | 봇이 세션 키와 타이머 값을 받고 본 샤드 게임서버에 연결된다 |
| P3-I-02 | 로그아웃 후 재로그인 | 본 샤드가 바뀌지 않는다 |
| P3-I-03 | 접속만 하고 인증을 보내지 않음 | 인증 제한 시간 뒤 서버가 끊는다 |
| P3-I-04 | 같은 계정으로 두 번째 접속 | 첫 세션이 "교체됨" 사유로 끊기고, 정리가 끝난 뒤 두 번째가 활성화된다 |

| P3-I-07 | Content 메시지와 Zone 메시지 전송 | Content는 본 샤드로 간다. 장소 배정 전의 Zone 메시지는 버려지고 지표가 오른다 |
| P3-I-08 | Valkey를 내린 상태에서 Gateway 기동 | `ready`가 켜지지 않는다 |
| P3-I-09 | 퍼블리셔 로그인 서버를 내린 상태에서 신규 입장 | 신규는 거절. 이미 접속한 봇은 계속 동작 |
| P3-I-10 | 게스트 재로그인 (같은 비밀값) | 같은 계정, 같은 캐릭터, 같은 본 샤드 |
| P3-I-11 | 틀린 비밀값으로 게스트 로그인 | 거절. 티켓이 나오지 않는다 |
| P3-I-12 | 이미 쓴 티켓으로 다시 입장 | 거절 |
| P3-I-13 | 클라이언트가 Entry에 다른 계정 번호를 직접 보냄 | 무시된다. 퍼블리셔가 확인해 준 계정만 쓴다 |

| P4-I-03 | 구매 요청 하나의 로그 추적 | 같은 `request_id`가 Gateway, 액터, DB 호출 로그에 모두 있다 |
| P4-I-04 | 구매 요청을 같은 요청 번호로 두 번 전송 | 응답은 같고 DB에는 한 번만 반영 |
