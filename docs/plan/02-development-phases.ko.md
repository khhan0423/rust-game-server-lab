# 개발 단계와 구현 순서

[English](02-development-phases.md) | **한국어**

- 상태: **초안** (2026-11-19)
- 상위 문서: [실행 계획](README.ko.md). 앞 단계: [파일럿](01-pilot.ko.md). 테스트: [03-test-scenarios.md](03-test-scenarios.ko.md)

파일럿이 판정을 통과한 뒤의 계획이다. 파일럿에서 만든 뼈대 위에 컨텐츠와 운영 기능을 올린다.

## 1. 전체 순서

```
파일럿 (P0~P9)
   │
   ▼
D1 기획 데이터 ─► D2 전투 서버와 던전 ─► D3 필드와 채널 ─► D4 소셜 ─► D5 길드
                                                                        │
              D6 스팀 로그인과 결제 (D2 이후 언제든 병행 가능) ◄────────┤
                                                                        ▼
                                             D7 거래 ─► D8 클러스터와 운영 ─► D9 출시 준비
```

순서를 이렇게 잡은 이유는 세 가지다.

1. **뒤 단계가 앞 단계의 것을 쓴다.** 던전은 기획 데이터(몬스터, 보상표)가 필요하고, 길드 던전은 던전과 길드가 모두 필요하다.
2. **위험한 것을 먼저 한다.** 샤드가 섞인 파티의 던전(D2)은 서버 간 경로를 가장 많이 쓰므로 일찍 검증한다.
3. **돈이 걸린 것은 기반이 굳은 뒤에 한다.** 결제(D6)와 거래(D7)는 멱등 처리와 복구가 여러 단계에서 검증된 뒤에 올린다.

### D1. 기획 데이터

- 설계 11 문서(2026-11-20 확정)를 그대로 구현한다.
- **만드는 것:** 표마다 TOML 스키마와 스키마에서 생성된 typed ID와 row 타입, 스프레드시트 내보내기 도구(표마다 JSON 파일 하나와 매니페스트), 내보내기/CI/기동 3중 검증, 콘텐츠 해시 로그인 확인, 운영 중 재로드는 스냅샷 통째 교체(01 문서 5.7).
- **구현 순서:** 스키마와 코드 생성 → 내보내기 도구와 검증기 → 기동 배리어에 연결 → 로그인 해시 확인 → `/admin` 재로드 → 테스트 클라이언트에 콘텐츠 버전 표시.
- **완료 기준:** 잘못된 표로는 서버가 뜨지 않는다. 해시가 다른 클라이언트는 로그인이 거부된다. 운영 중 재로드해도 진행 중인 요청이 끊기지 않는다.

### D2. 전투 서버와 던전

- **만드는 것:** 전투 서버 역할(컨텐츠 런타임과 DB 없음), 인스턴스 던전 모드, 파티 액터(Valkey로 위치 공유), 입장 시 `CombatProfile` 전달과 Gateway의 존 목적지 전환, 루팅(`GrantItem`, 인벤토리가 가득 차면 되돌리기), 클리어 보상(결과만 보내고 본 샤드가 계산), 중요한 보상이 인벤토리에 안 들어가면 우편으로.
- **구현 순서:** 전투 서버 기동과 등록 → 던전 생성과 입장(같은 샤드 파티) → 존 목적지 전환 → 몬스터와 기본 전투(스킬 1~2개) → 루팅 → 클리어 보상 → 샤드가 섞인 파티 → 전투 서버 강제 종료 시 처리.
- **완료 기준:** 서로 다른 샤드 유저 3명이 던전을 돌고, 보상이 각자의 게임 DB에 정확히 한 번 들어간다. 전투 서버를 죽여도 이미 확정된 보상은 남는다.

### D3. 필드와 채널, NPC

- **만드는 것:** MMO 필드 모드, 채널(소프트 정원, 하드 정원, 자동 배정, 수동 이동과 쿨다운, 빈 채널 닫기), 채널 인원을 Valkey에 게시, NPC AI(상태 기계), AOI 칸 단위 활성화, 같은 서버 안 장소 이동과 이동 중 패킷 넘기기.
- **구현 순서:** 필드 모드와 상주 채널 1 → NPC 스폰과 AI → 칸 단위 활성화 → 채널 추가와 자동 배정 → 수동 이동 → 로비와 필드 사이 이동.
- **완료 기준:** 정원을 넘는 인원이 들어오면 새 채널이 열리고, 파티원은 같은 채널로 들어간다. 플레이어가 없는 칸의 NPC는 갱신되지 않는다.

### D4. 소셜

- **만드는 것:** 친구(요청, 수락, 삭제. Common DB), 친구 코드와 샤드 배정 연결, 접속 상태 표시, 친구 로비 방문(다른 샤드 포함)과 방문 보상, 채팅(귓속말, 파티, 장소), 랭킹판.
- **구현 순서:** 친구 관계 → 접속 상태 → 친구 코드 → 로비 방문 → 채팅 → 랭킹.
- **완료 기준:** 다른 샤드 친구의 로비에 들어가 함께 있고, 방문 보상이 방문자의 본 샤드에 한 번만 들어간다.

### D5. 길드

- **만드는 것:** 길드 액터(Common DB, 담당 서버 선점과 fencing), 가입과 탈퇴, 직위와 권한 목록, 정원 30명, 길드 재화, 길드 창고(재화와 아이템, 직위별 권한, 하루 한도, 입출고 기록), 길드 점수와 랭킹, 길드 던전(개설 권한, 길드당 동시 5개, 요일/상시/주말 일정), 아무도 접속하지 않았을 때 깨워서 처리, 정해진 시각의 배치(주간 정산, 만료 정리).
- **구현 순서:** 길드 생성과 가입 → 직위와 권한 → 길드 재화 → 창고 넣기와 빼기 → 길드 점수와 랭킹 → 길드 던전 개설과 일정 → 배치 작업 → (나중) 길드 타운.
- **완료 기준:** 서로 다른 샤드 길드원이 창고에 아이템을 넣고 빼도 아이템 총량이 맞는다. 권한 없는 길드원은 던전을 열 수 없다. 요일 던전은 그 요일에만 열린다.

### D6. 스팀 로그인과 결제

- **만드는 것:** 퍼블리셔 로그인 서버에 스팀 로그인 수단 추가(스팀 티켓 확인, 게스트 계정과의 연동), Commerce 서비스, 인게임 구매(주문 생성 → 승인 → 확정 → 지급), 정산 보고서 주기 조회와 환불 회수(마이너스 잔액과 유료 상점 제한), 스팀 아이템(외형만)의 지급과 동기화.
- **구현 순서:** 스팀 로그인 → 주문 상태 기계와 Commerce DB → 샌드박스로 구매 끝까지 → 끊김과 타임아웃 처리 → 환불 회수 → 스팀 아이템 정의와 로그인 시 동기화 → 서버 지급.
- **완료 기준:** 샌드박스에서 결제 확정 뒤 어느 시점에 서버를 죽여도 결국 한 번 지급된다. 환불되면 재화가 회수된다.

### D7. 거래

- **만드는 것:** 거래 서비스(중계자, 에스크로), 양쪽 입금 → 교환 확정 → 양쪽 지급, 취소와 시간 초과 시 반환.
- **구현 순서:** 거래 상태 기계 → 같은 샤드 거래 → 다른 샤드 거래 → 취소와 시간 초과 → 거래 서비스 강제 종료 복구.
- **완료 기준:** 어느 단계에서 누구를 죽여도 아이템이 복사되거나 사라지지 않는다.

### D8. 클러스터와 운영

- **만드는 것:** 한 샤드에 게임서버 여러 대(플레이어 액터를 어느 서버가 맡을지), 드레인과 무중단 교체, 서버가 죽었을 때 이어받기, Valkey 이중화와 장애 시 동작, 배포(systemd), 감시와 경보(Prometheus, Grafana, Alertmanager), 로그 수집(Fluent Bit)과 Log DB, 운영 도구 전체 확장(공지, 강제 종료, 점검 모드, 지급은 설계 12. P6.5 최소 도구 위에 화면을 더한다), DB 백업과 복구 연습.
- **구현 순서:** 06 클러스터 문서 → 드레인 → 한 샤드 다중 서버 → 장애 이어받기 → Valkey 장애 동작 → 배포 스크립트 → 감시와 경보 → 로그 수집 → 운영 도구 → 백업 복구 연습.
- **완료 기준:** 서버 한 대를 드레인으로 교체해도 유저가 끊기지 않는다. Valkey를 내려도 이미 접속한 유저의 플레이가 이어진다. 백업에서 복구하는 절차를 실제로 한 번 돌린다.

### D9. 출시 준비

- **하는 일:** 운영 사양 서버에서 프로세스당 동접 1만 부하 시험, 72시간 연속 시험, 장애 주입 시험(서버, DB, Valkey, 네트워크), 보안 점검(패킷 위조, 속도 조작, 요청 재전송, 관리 포트 노출), 필드 정원과 스레드 수 최종 결정, 탈퇴 데이터 보관 정책 확정(법무), 이용약관에 환불 재화 처리 명시, 스팀 출시 절차.
- **완료 기준:** 출시 판정표(부하, 장애, 보안, 운영 절차)를 모두 채운다.

## 3. 단계마다 지키는 것

| 항목 | 내용 |
|---|---|
| 설계 먼저 | 설계 문서에 없는 구조가 필요하면 문서를 먼저 고치고 승인받는다 (AGENTS.md) |
| 완료 정의 | 코드 + 테스트 + 문서 갱신 + 품질 게이트 통과 + GUI 테스트 클라이언트에서 직접 확인 |
| 테스트 순서 | 순수 로직 단위 테스트 → 액터 테스트 → 실제 DB 테스트 → 서버 여러 대 통합 테스트 → 강제 종료 테스트 |
| 회귀 | 앞 단계의 자동 시나리오는 계속 통과해야 한다. 고친 버그는 시나리오로 추가한다 |
| 봇과 클라이언트 | 새 기능마다 봇 시나리오와 GUI 패널을 함께 추가한다 |
| 지표 | 새 기능은 처리 시간, 실패 수, 대기열 길이를 지표로 낸다 |
| 새 라이브러리 | 쓰기 전에 승인받고 가이드 13장 표에 적는다 |
