# 파일럿 계획

- 상태: **초안** (2026-11-19)
- 상위 문서: [실행 계획](README.md). 테스트 시나리오: [03-test-scenarios.md](03-test-scenarios.md)

## 1. 파일럿이 무엇인가

**설계의 뼈대가 실제 코드에서 맞물리는지 확인하는 작은 완성품**이다. 컨텐츠는 거의 없지만, 접속부터 DB 저장까지 모든 층을 한 번씩 지나간다.

```
GUI 테스트 클라이언트 / 봇
        │
     Gateway ──────────── Valkey (접속 상태, 장소 담당 서버)
        │
  ┌─────┼──────────┐
게임서버1  게임서버2  게임서버3        Entry 서버 ── Account DB
  │         │         │
게임DB1   게임DB2   게임DB3
```

파일럿에서 유저가 할 수 있는 일은 다섯 가지뿐이다.

1. 로그인한다 (개발용 계정). 처음이면 샤드를 배정받는다.
2. 자기 로비에 들어가 돌아다닌다. 다른 사람이 보인다.
3. 상점에서 아이템을 산다.
4. 다른 샤드 유저에게 우편으로 아이템을 보낸다.
5. 연결이 끊겼다가 다시 붙는다.

### 1.1 파일럿이 증명해야 하는 것

| # | 증명할 것 | 근거 설계 |
|---|---|---|
| V1 | 존 스레드(동기, 10Hz)와 플레이어 액터(async)가 락 없이 함께 돈다 | 01 4장, 5장 |
| V2 | 클라이언트는 Gateway 하나에만 붙고, 메시지 종류에 따라 맞는 서버로 간다 | 02 3.2 |
| V3 | 게임서버 N은 게임DB N에만 붙고, 샤드를 넘는 일은 메시지로 한 번만 반영된다 | 04 2장, 03 3장 |
| V4 | 재화는 DB 커밋 후에만 바뀌고, 같은 요청을 다시 보내도 한 번만 처리된다 | 01 5.5 |
| V5 | 서버를 강제로 죽였다 살려도 커밋된 데이터와 보내던 메시지가 사라지지 않는다 | 01 10장 |
| V6 | 장소(InGameSpace)는 한 서버만 맡고, 비면 유예 뒤 저장하고 내려간다 | 01 6장, 05 |
| V7 | 멈춘 요청을 유저번호와 요청 번호로 로그에서 찾을 수 있다 | 01 5.8 |
| V8 | 끊긴 연결이 유예 시간 안에 이어지고, 중요한 응답은 빠지지 않는다 | 세션 계약 |
| V9 | 개발 PC에서 봇 2,000개가 기준 지연 안에 돈다 | 01 9장 (가정값 검증) |

### 1.2 파일럿에 넣지 않는 것

| 넣지 않는 것 | 이유 | 넣는 시기 |
|---|---|---|
| 스팀 로그인과 결제 | 외부 연동 없이 구조부터 검증한다. 개발용 인증으로 대신한다 | 개발 단계 D6 |
| 전투 서버, 던전, PvP | 존 구조가 검증된 뒤 같은 틀로 추가한다 | D2 |
| MMO 필드와 채널, NPC AI | 로비 하나로 존 구조를 먼저 검증한다 | D3 |
| 길드, 친구, 채팅, 랭킹 | 샤드 간 메시지 기반이 검증된 뒤 올린다 | D4, D5 |
| 기획 데이터 파이프라인 | 파일럿은 작은 TOML 표 몇 개로 충분하다 | D1 |
| 서버 여러 대로 한 샤드 운영, Valkey 이중화 | 06 클러스터 문서가 먼저 필요하다 | D8 |

## 2. 단계

파일럿은 열 단계다. 각 단계는 **코드, 테스트, 문서 갱신, 품질 게이트 통과**가 모두 끝나야 완료다.

```
P0 기반 ─► P1 프로토콜 ─► P3 접속 ─► P4 컨텐츠 ─► P5 존 ─► P6 샤드 간 ─► P8 재접속 ─► P9 측정
   └────► P2 런처 ─────────┘            P7 GUI 클라이언트 (P3부터 나란히 진행)
```

| 단계 | 이름 | 만드는 것 (요약) | 규모(추정) |
|---|---|---|---|
| P0 | 기반 | 워크스페이스, 품질 게이트, 개발용 DB/Valkey, 설정, 로그, 지표, 관리 포트 | 1주 |
| P1 | 프로토콜과 프레임 | 메시지 정의, 16바이트 프레임 코덱, 서버 간 봉투 코덱 | 1주 |
| P2 | 서버 런처 | GUI 런처와 창 없는 모드, 토폴로지 파일, 순서 기동, 강제 종료 | 1주 |
| P3 | 접속과 세션 | Entry 서버, Gateway 세션, 샤드 배정, 중복 로그인, 봇 기본 | 2주 |
| P4 | 컨텐츠 액터와 DB | 플레이어 액터, Game DB 스키마, 구매, 멱등 키, 기동 배리어, 추적 로그 | 2주 |
| P5 | 존과 로비 | 존 스레드, 틱, AOI, 로비 입장과 이동, 장소 담당 선점, 저장과 언로드 | 3주 |
| P6 | 샤드 간 메시지와 복구 | 서버 간 링크, outbox, 샤드 간 우편, 정상 종료, 강제 종료 복구 | 2주 |
| P7 | GUI 테스트 클라이언트 | Bevy 화면: 로그인, 로비 보기, 이동, 상점, 우편, 패킷 로그 | 2주 (병행) |
| P8 | 재접속 | Reliable 순번과 확인, 재전송 버퍼, Resume, 다른 Gateway로 이어 붙기 | 2주 |
| P9 | 부하 측정과 판정 | 봇 부하 시나리오, 대시보드, 설정값 결정, 파일럿 보고서 | 1~2주 |

규모는 1인 개발 + AI 보조 기준의 추정이다. 실제 진행은 [README](README.md)의 진행표에 기록한다.

### P0. 기반

- **워크스페이스:** 루트 `Cargo.toml`에 버전과 lint를 모은다(가이드 부록 A). 크레이트는 **처음 필요한 단계에서 만든다**(빈 크레이트를 미리 만들지 않는다). P0에서는 `infra`, `db`, `server`, `gateway`를 만들고, `protocol`과 `net`은 P1, `launcher`는 P2, `bot`은 P3, `game`은 P4, `client`는 P7에서 만든다.
- **공용 운영 코드:** 설정 로드, 로그 초기화, 지표, 관리 포트는 `infra` 크레이트에 둔다. 서버는 준비가 끝나면 표준 출력에 `ready admin=<관리 포트 주소>` 한 줄을 쓴다. 런처와 통합 테스트는 이 줄을 기다린다(주기적으로 찔러 보지 않는다).
- **개발 환경:** `dev/compose.yaml`로 PostgreSQL 1개(데이터베이스 `account`, `common`, `game_1`, `game_2`, `game_3`)와 Valkey 1개를 띄운다. 운영에서는 DB가 따로 떨어지지만 개발 PC에서는 한 인스턴스에 모은다. 비밀번호와 테스트용 접속 문자열은 루트의 `.env`(저장소에 올리지 않음, 예시는 `.env.example`)에 둔다.
- **마이그레이션:** `migrations/game`부터 시작한다(모든 샤드에 같은 것을 적용). `account`, `common`은 그 DB를 처음 쓰는 단계(P3)에서 추가한다. 적용은 `server migrate` 명령으로 한다.
- **설정과 비밀:** 일반 설정은 TOML, 비밀은 환경 변수. 비밀 타입은 `Debug` 출력에서 가린다(08 문서 8장).
- **관측:** `tracing` JSON 로그(비동기 파일 쓰기), `/health/live`, `/health/ready`, `/metrics`.
- **품질 게이트 스크립트:** `scripts/gate.ps1`, `scripts/gate.sh`가 fmt, clippy, test를 순서대로 돌린다.
- **완료 기준:** 게이트 통과. 빈 `server`와 `gateway` 바이너리가 떠서 헬스 체크에 응답. 실제 PostgreSQL에서 `sqlx::test` 1개 통과.

### P1. 프로토콜과 프레임

- `.proto`로 System 메시지(Auth, AuthOk, Resume, Ping, Close, EnterGame 등)와 파일럿용 Content, Zone 메시지를 정의한다. 메시지 ID는 종류별 대역 안에서 생성한다(02 문서 3.2).
- 클라이언트 프레임(16바이트 헤더)과 서버 간 봉투 코덱을 `net`에 만든다(02 문서 8.1, 4.2).
- **완료 기준:** 모든 메시지의 인코딩 왕복, 경계값, 깨진 입력 테스트 통과.

### P2. 서버 런처

- `topology.toml`을 읽어 Entry → 게임서버들 → Gateway 순으로 띄운다. 각 서버의 `/health/ready`가 켜진 뒤 다음으로 넘어간다.
- 화면: 서버별 상태, PID, 포트, 로그 창, 시작/종료/재시작/강제 종료 버튼. 서버의 준비 여부는 표준 출력의 `ready admin=<주소>` 줄로 안다.
- **창 없는 모드**를 반드시 둔다(`launcher --headless up` 등). 자동 통합 테스트가 이것으로 서버군을 띄우고 죽인다.
- **완료 기준:** 빈 서버 5개를 순서대로 띄우고, 하나를 강제 종료하면 상태판에 반영되고, 전체 종료 후 남은 프로세스가 없다.

### P3. 접속과 세션

- **Entry 서버:** 개발용 인증(계정 이름만으로 통과, 개발 빌드에서만 켜짐), AccountDB 조회와 첫 입장 처리, 샤드 배정(친구 코드 우선, 없으면 누적 인원 최소), `login_token` 서명 발급.
- **Gateway:** 접속 수락, 세션 상태 전이, 토큰 검증, Valkey `online:{account}`로 중복 로그인 처리, 메시지 ID 대역으로 라우팅, 하트비트, 크기와 빈도 제한.
- **게임서버:** Gateway 링크 수락, 세션 연결 통지(`SessionBound`).
- **봇:** 세션 계약대로 접속하는 참조 구현과 시나리오 실행기.
- **완료 기준:** 봇이 로그인해서 본 샤드 게임서버까지 연결된다. 재로그인해도 샤드가 바뀌지 않는다. 중복 로그인하면 먼저 붙은 쪽이 정리된 뒤 새 쪽이 붙는다.

### P4. 컨텐츠 액터와 DB

- 컨텐츠 런타임과 `ContentManager`, 플레이어 액터(inbox 상한 있음).
- Game DB: 플레이어, 지갑, 인벤토리, 우편함, 멱등 키, outbox, 거래성 로그.
- `db` 크레이트 함수: 로드, 구매(한 트랜잭션), 멱등 재실행 결과 반환.
- **기동 배리어:** 설정 → DB 연결과 마이그레이션 버전 확인 → 공용 데이터 로드 → 런타임 기동 → `ready`. 하나라도 실패하면 기동 실패. 블로킹 DB 도구는 기동 후 버린다.
- **추적:** 명령마다 `player_id`, `request_id` span. 느린 명령 경고, inbox 적체 경고.
- **완료 기준:** 봇이 아이템을 사면 DB에 반영되고, 같은 요청을 다시 보내도 잔액이 한 번만 줄어든다. 로그에서 요청 번호 하나로 Gateway부터 DB까지 이어서 볼 수 있다.

### P5. 존과 로비

- 존 스레드와 `ZoneHost` 틱 루프(10Hz, 틱당 명령 상한, 밀리면 건너뜀).
- `InGameSpace`(공통 코어 + 로비 모드), 2D 격자 AOI, 입장, 퇴장, 이동.
- `InGameSpaceManager`: Valkey로 담당 서버 선점과 임대 연장, 로딩 중 입장 대기열, 유예 10분 뒤 최종 저장과 언로드.
- 로비 상태 저장: 존은 DB를 직접 부르지 않고 DB task에 요청을 보낸다. 저장에는 fencing 번호와 버전 번호를 붙인다.
- 존과 컨텐츠 사이: `CombatProfile` 전달, 장착 요청의 대기 상태.
- **완료 기준:** 봇 여러 개가 같은 로비에서 서로의 이동을 본다. 시야 밖의 봇에게는 이동이 가지 않는다. 모두 나가면 유예 뒤 저장되고 내려가며, 다시 들어오면 저장된 상태로 뜬다.

### P6. 샤드 간 메시지와 복구

- 서버 간 링크(인증 포함), outbox 전송기, 멱등 수신.
- 샤드 간 우편: 보내는 쪽에서 아이템 삭제와 outbox 기록을 한 트랜잭션으로, 받는 쪽에서 우편함 추가와 멱등 키 기록을 한 트랜잭션으로.
- 오프라인 유저 앞 메시지는 액터를 잠깐 깨워 처리한다.
- 정상 종료 순서(01 문서 10.1)와 강제 종료 뒤 재기동 복구.
- **완료 기준:** "유저 3명, 샤드 3개" 시나리오가 자동으로 통과한다. 중간에 어느 서버를 죽였다 살려도 우편은 정확히 한 번 도착한다.

### P7. GUI 테스트 클라이언트 (P3부터 병행)

- Bevy 창 하나에 로비를 그린다. 자기, 다른 유저, AOI 격자를 볼 수 있다.
- egui 패널: 로그인(계정, 친구 코드), 인벤토리, 상점, 우편, 패킷 로그(송수신, 필터), 연결 끊기와 다시 붙기 버튼, 지연 표시.
- 네트워크 계층은 봇과 같은 코드를 쓴다.
- **완료 기준:** 사람이 창에서 로그인, 이동, 구매, 우편, 재접속을 해 볼 수 있고, 한글이 제대로 보인다.

### P8. 재접속

- Reliable 프레임의 순번과 확인 응답, 재전송 버퍼(상한 있음), 끊김 감지와 유예, `Resume` 핸드셰이크, 재개 시 장소 스냅샷.
- 세션 미러를 Valkey에 두어 다른 Gateway로도 이어 붙는다.
- `Suspend`(앱을 내렸을 때 더 긴 유예).
- **완료 기준:** 세션 계약 문서의 시나리오 A~H가 봇으로 자동 통과한다.

### P9. 부하 측정과 판정

- 봇 부하 시나리오와 지연 분포 수집, Prometheus와 Grafana 대시보드(개발용 compose).
- 측정으로 정하는 값: 컨텐츠 워커 수, 존 스레드 수, 로비 정원 출발값, 풀 크기, 할당자(mimalloc) 채택 여부.
- **완료 기준:** 3장의 판정 기준을 채우고, 결과를 `docs/plan/pilot-report.md`로 남긴다.

## 3. 파일럿 판정 기준

| 구분 | 기준 |
|---|---|
| 기능 | 테스트 시나리오 문서의 P0~P8 자동 시나리오가 모두 통과한다 |
| 정합성 | 강제 종료 시나리오(P6-F, P8)에서 재화와 아이템의 총량이 맞는다. 중복 지급 0건, 유실 0건 |
| 성능 (개발 PC, 봇 2,000개, 샤드 3개) | 존 틱 p99 50ms 이하. 컨텐츠 요청 지연 p99 150ms 이하(DB 포함). DB 풀 대기 p99 1초 이하. 오류 0건 |
| 밀집 | 한 장소에서 틱 p99 50ms를 지키는 최대 인원을 잰다. 이 숫자가 정원의 출발값이 된다 |
| 격리 | 일부 유저의 DB 호출을 일부러 느리게 했을 때 다른 유저의 요청 지연이 늘지 않는다 |
| 안정성 | 4시간 연속 부하에서 메모리가 계속 늘지 않고, 채널 가득 참 0건 |
| 운영성 | 일부러 멈추게 한 요청 하나를 로그만으로 5분 안에 찾는다 |
| 품질 | fmt, clippy(-D warnings), test 통과. `unsafe`, `unwrap`(테스트 밖) 0건 |

성능 숫자는 출발점이다. 최종 목표(프로세스당 동접 1만)는 출시 준비 단계에서 운영 사양 서버로 다시 잰다.

### 3.1 판정에서 떨어졌을 때

| 떨어진 항목 | 대응 |
|---|---|
| 존 틱 | 브로드캐스트 직렬화 공유, 수신자별 묶음 전송, 먼 대상 갱신 빈도 낮추기를 차례로 적용하고 다시 잰다. 그래도 안 되면 정원을 낮춘다 |
| 컨텐츠 지연 | 컨텐츠 워커 수와 DB 풀 크기를 조정한다. 무거운 계산은 블로킹 풀로 옮긴다 |
| 격리 실패 | 액터 안에서 워커를 붙잡는 코드(동기 호출, 긴 계산)를 찾아 고친다 |
| 정합성 | 출시를 막는 문제다. 원인을 고치고 해당 시나리오를 회귀 테스트로 굳힌다 |

## 4. 위험

| 위험 | 영향 | 줄이는 방법 |
|---|---|---|
| Rust 숙련도 | 초반 속도가 느리다 | 단계마다 작은 크레이트부터 시작하고, 새 개념은 보고서에서 C++와 견줘 설명한다(AGENTS.md) |
| Bevy 버전 변화가 빠르다 | 클라이언트 유지 비용 | 클라이언트는 도구로만 쓰고 서버 코드와 분리한다. 버전을 고정한다 |
| 통합 테스트가 느리거나 불안정해진다 | 개발 흐름이 끊긴다 | 시간에 기대지 않고 이벤트를 기다린다. 타이머는 설정으로 짧게 준다. 서버군은 런처의 창 없는 모드로 띄운다 |
| 개발 PC 한 대에 서버, DB, 봇이 모두 돈다 | 성능 숫자가 실제와 다르다 | 파일럿 숫자는 상대 비교와 출발값으로만 쓴다 |
| 재접속(P8)이 예상보다 크다 | 일정 지연 | P8은 P6 뒤에 두어, 늦어져도 앞 단계 검증은 끝나 있게 한다 |
