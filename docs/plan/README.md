## 한눈에 보기

```
[파일럿]  설계의 뼈대 검증. 컨텐츠는 최소
  P0 기반 → P1 프로토콜 → P2 런처 → P3 접속 → P4 컨텐츠와 DB → P5 존과 로비
  → P6 샤드 간 메시지와 복구 → P6.5 최소 운영 도구 → P8 재접속 → P9 부하 측정과 판정
  (P7 GUI 테스트 클라이언트는 P3부터 나란히)

[개발]  뼈대 위에 컨텐츠와 운영
  D1 기획 데이터 → D2 전투 서버와 던전 → D3 필드와 채널 → D4 소셜 → D5 길드
  → D6 스팀 로그인과 결제 → D7 거래 → D8 클러스터와 운영 → D9 출시 준비
```

## 원칙

1. **얇게 끝까지 먼저.** 한 층을 완성한 뒤 다음 층으로 가지 않는다. 접속부터 DB까지 가장 얇은 경로를 먼저 뚫고 넓힌다.
2. **세션 구조가 먼저다.** 세션의 생성, 조회, 종료가 정해진 뒤에 그 위에 존과 컨텐츠를 올린다(P3이 P4, P5보다 앞).
3. **도구를 먼저 만든다.** 테스트, 런처, 테스트 클라이언트가 있어야 뒤 단계를 믿고 진행할 수 있다(P0, P2, P7).
4. **죽여 본다.** 정상 흐름만이 아니라 서버를 강제로 죽이는 테스트가 단계 완료의 조건이다.
5. **재 본다.** 성능 숫자는 추측하지 않고 측정해서 정한다(P9, D3, D9).
6. **설계가 기준이다.** 설계와 다르게 만들어야 하면 설계 문서를 먼저 고치고 승인받는다.

## 단계 완료의 정의

한 단계는 아래가 모두 끝나야 완료다.

- 그 단계의 자동 테스트 시나리오(U, A, D, I, F)가 모두 통과한다
- 앞 단계의 자동 시나리오도 계속 통과한다
- `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace` 통과
- 수동 시나리오(M)를 GUI에서 확인했다
- 바뀐 내용이 설계 문서와 아래 진행표에 반영됐다

## 시작 전 결정 (2026-11-19 모두 권장안으로 확정)

아래는 소유자가 권장안대로 확정했다. 가이드 2장, 13장과 AGENTS.md에 반영했다.

| # | 정할 것 | 왜 | 확정 |
|---|---|---|---|
| C1 | 공용 운영 코드를 둘 크레이트 | 설정 로드, 로그 초기화, 지표, 관리 포트를 Gateway와 서버가 같이 쓴다. 지금 크레이트 구성에는 둘 곳이 없다(`net`은 네트워크 코드, `gateway`는 `game`과 `db`를 모른다) | `crates/infra` 추가. `gateway → infra`, `server → infra`. `infra`는 게임 크레이트에 의존하지 않는다 |
| C2 | 토큰 서명 방식 | Entry가 서명하고 Gateway가 검증한다 | Ed25519(`ed25519-dalek`). Gateway에는 공개 키만 두면 되므로, Gateway가 뚫려도 토큰을 위조할 수 없다 |
| C3 | 프로토콜 코드 생성 도구 | `.proto`에서 Rust 코드를 만든다 | `prost-build` (빌드 때만 쓰는 의존성) |
| C4 | Valkey 클라이언트 | 가이드에 `redis` 또는 `fred` 중 구현 때 결정이라고 적혀 있다 | `redis` 크레이트 (가장 널리 쓰이고, 단일 명령만 쓰는 우리 용도에 충분) |
| C5 | 난수 | 세션 키 생성 | `rand` (운영체제 난수원 사용) |
| C6 | 명령줄 인자 처리 | 런처의 창 없는 모드, 봇 시나리오 선택 | `clap` |
| C7 | 개발용 인증 | 스팀 연동 전까지의 로그인 | **변경 (2026-11-19):** 가짜 인증을 만들지 않는다. 퍼블리셔 로그인 서버를 파일럿 P3에서 만들고 게스트 로그인을 쓴다 |
| C8 | 퍼블리셔 로그인 서버의 크레이트 | 설계 07의 퍼블리셔 영역(계정, 로그인 수단, 입장 티켓)을 구현할 곳이 필요하다 | `crates/publisher` 바이너리. Login DB의 SQL은 `db` 크레이트의 별도 모듈에 둔다. 게임 서버 크레이트는 Login DB에 접근하지 않는다 |
